# 受信 Webhook

任意の機能で、**既定ではオフ**です。GitHub から変更をモニターに知らせ、次の問い合わせを待たずに次のサイクルでリポジトリを更新できます。

## 動作(更新のみ)

受け付けたイベントは、そこに書かれたリポジトリを次のサイクルで更新するようにマークするだけです。GitHub にもディスクにも何も書き込まず、イベントの文面は保存も表示もされず、モニターがすでに監視しているリポジトリだけが受け付けられます。扱うイベント:`workflow_run`、`workflow_job`、`push`、`release`、`check_run`, `check_suite`、`ping`。それ以外は `202` を返して無視します。

## 安全性

- モニターは引き続き `127.0.0.1` だけで待ち受けます。GitHub は、あなたが意図して用意したトンネル経由でのみ到達できます。ツールが自らトンネルを開くことはありません。
- `webhook.enabled` がオンで、**かつ** 共有シークレット（32 文字以上）が `webhook.secret_env` で指定した環境変数に入るまでオフのままです（既定は `MONITOR_WEBHOOK_SECRET`。`MONITOR_WEBHOOK_SECRET_FILE` で、コンテナのシークレットのように 1 行目がシークレットのファイルを指定することもできます）。シークレットは `actions_monitor.json` に書かれず、表示も記録もされず、モニターが起動するプログラムにも引き継がれません。設定タブは定義済みかどうかだけを示します。従来の方法（ファイル内の `secret`）は `webhook.allow_config_secret` が true のときだけ読まれ、使用中はライブ表示が警告します。
- 共有シークレットが唯一の防壁です。GitHub はアクセストークンを送れないため、受信側はトークンを求めず、署名だけを信頼します。受信を有効にしてシークレットが未設定の場合は、すべての配信を `401` で拒否し、doctor が赤で知らせます。アドレスは自分で管理するトンネルまたはプロキシの背後に置いてください。
- すべてのリクエストに、そのシークレットで作られ一定時間で比較される `X-Hub-Signature-256: sha256=<hmac>` が必要です。それ以外は `401` となり、署名を確認するまで内容は一切見られません。
- `webhook.max_body_kb`(既定 1 MiB、最大 25 MiB)を超える本文は、読み取りや計算の前に `413` になります。拒否は `stats.too_big` に数えられます。
- 一覧は閉じています。処理されるのは `workflow_run`、`workflow_job`、`check_run`、`push`、`release`、`check_suite`、`ping` だけで、イベントから保持されるのは検証済みの短いフィールドだけです（コミットメッセージや自由文は保持しません）。それ以外は `202` を返して破棄します。

## オンにするには

1. 32 文字以上のランダムなシークレットを作ります。例：`python -c "import secrets; print(secrets.token_hex(32))"`。
2. ファイルではなく環境経由でモニターに渡します。モニターを起動する前に PowerShell で `$env:MONITOR_WEBHOOK_SECRET = "<シークレット>"`、シェルでは `export MONITOR_WEBHOOK_SECRET=...`、サービスでは `Environment=` または `EnvironmentFile=`（自分だけが読めるファイル）、コンテナでは `-e` または `MONITOR_WEBHOOK_SECRET_FILE` で指定するシークレットファイルを使います。
3. 受信をオンにして（設定 > 受信 Webhook > 受信オン、または `actions_monitor.json` に `"webhook": {"enabled": true}`）、モニターを再起動します。
4. アドレスに到達できるようにします。GitHub は `127.0.0.1` に届きません。意図して用意したトンネル（`/api/webhook` で終わる HTTPS アドレス）を使うか、このコンピューターでは `gh webhook forward` で `http://127.0.0.1:ポート/api/webhook` へ転送します（コマンドラインに書かずに同じシークレットを渡す方法は GitHub CLI のドキュメントを参照）。
5. GitHub でリポジトリ（または組織）> Settings > Webhooks > Add webhook を開きます。**Payload URL**：`/api/webhook` で終わるトンネルのアドレス。**Content type**：`application/json`。**Secret**：同じシークレット。**SSL verification**：有効。**Events**：「Let me select individual events」を選び、Workflow runs と Workflow jobs、必要に応じて Check runs、Pushes、Releases。**Active**：オン。組織の Webhook 1 つでその全リポジトリをカバーでき、モニターは監視していないものを無視します。
6. 確認：GitHub の Recent deliveries で最初の `ping` が `200` になること。モニターのライブ表示には、受信オン、カウンター、カバレッジが表示されます。

## リアルタイムイベント

- `webhook.record_events` がオン(既定)のとき、署名付きの `workflow_run` イベントはそのリポジトリの実行リストを 先に GitHub を読まずに即座に更新します。実行は既に持っているイベントの種類を保つので色は変わらず、確認のためリポジトリは次のサイクルで再び読み取られます(受け付けたイベントごとに1回)。`workflow_job` イベントは分析用に待ち時間と各ステップの時間ももたらします。
- 保存されるのは検証済みの短いフィールド(ワークフロー、実行、状態、結論、ブランチ、短いコミット、実行へのリンク、所要時間)のみで、コミットメッセージや作成者は保存しません。ワークフロー、ブランチ、ジョブ、ステップの短い名前も保存されますが、1行にして、モニターから出る他のテキストと同様に整えられます。最新の `webhook.live_events_keep` 件は `GET /api/live-events`(ネットワークモードではアクセストークン付き)で読めます。
- `webhook.record_events` がオン(既定)のとき、署名付きの `workflow_run` イベントはそのリポジトリの実行リストを GitHub を読まずに即座に更新します。ただしそのリポジトリは次のサイクルで改めて読み取られます(イベントは知らせ、読み取りが裏付けです)。配信は変更を即座に示しますが、読み取りの節約にはなりません。`workflow_job` イベントは分析用に待ち時間と各ステップの時間ももたらします。
- 保存されるのは検証済みの短いフィールド(ワークフロー、実行、状態、結論、ブランチ、短いコミット、実行へのリンク、所要時間)のみで、コミットメッセージは保存しません。ワークフロー、ブランチ、ジョブの名前は第三者が書いた最大 100 文字のテキストで、そのまま保存され、プレーンテキストとして表示されます。ステップ名は統計に入ります。最新の `webhook.live_events_keep` 件は `GET /api/live-events`(ページを開ける人:ネットワークモードではアクセストークン、チームモードではセッション)で読めます。
- 任意機能（既定ではオフ）：`live.sse.enabled` をオンにすると、`GET /api/live-events/stream` が同じイベントを受理した順にサーバー送信イベントとして送ります（`hello`、続いてイベントごとに 1 つの `live` フレーム。連番の `id` により `Last-Event-ID` または `?since=` で再開でき、保持用コメントと最後の `bye` が付きます）。読み取り専用で、ネットワークモードでは他のリクエストと同じくアクセストークンが必要です。接続数は最大 `live.sse.max_clients`、各接続は `live.sse.max_seconds` までです。Lite 版にはありません。
- 赤で終わった実行は、通知が有効なら `workflow_failed` も送ります。`webhook.record_events` をオフにすると、上で説明した更新のみのモードに戻ります。
- GitHub は `127.0.0.1` に届きません。`gh webhook forward`(GitHub CLI のドキュメント参照)か、意図して用意したトンネルで `http://127.0.0.1:PORT/api/webhook` へ転送してください。

## 時間上のカバレッジ

ライブ表示は、イベントが状態をどれだけの時間カバーしているかを示します。**イベントで把握中**（最後のイベントが `savings.webhook_window_minutes`（既定 60 分）より新しい）、**... の間イベントなし**（それより古い：静かなリポジトリ、またはトンネル切断）、**最初のイベントを待機中**のいずれかです。ポーリングは常にフォールバックです。届かなかった配信（モニター停止中、トンネル切断）は次のリポジトリ読み取りで補われるため、イベントは読み取りを減らしますが置き換えることはありません。同じ数値は `GET /api/live-status` の `coverage` と `secret_source`（`env`、`config`、`none`。シークレット自体は含みません）にもあります。

## うまくいかないとき

| 応答 | 意味 |
|---|---|
| `404` | 受信がオフ、または環境変数のシークレットがないか 32 文字未満です。 |
| `401` | 署名が一致しません。両側で同じシークレットを使い、Content type は `application/json` にします。 |
| `413` | 本文が `webhook.max_body_kb`(既定 1 MiB)を超えています。 |
| `503` | イベントのキューが満杯です。GitHub またはあなたが後で再送します(`Retry-After`)。その配信は重複として記憶されません。 |
| `400` | 有効な `X-GitHub-Delivery` ID がないか、内容を解釈できません。 |
| `202` | 受理して無視：監視していないリポジトリ、一覧にないイベント、重複配信、または毎分の上限を超えたリポジトリ。 |
| `429` | 1 つのアドレスが 1 分間に、正しく署名されたリクエストを 120 件より多く、または署名が検証できないリクエストを `webhook.max_bad_per_minute`（既定 120）件より多く送りました。 |

## リプレイと大量送信

誰かが傍受した有効な署名付きリクエストを再送しても、応答はしますが処理はしません。すべての配信に `X-GitHub-Delivery` の ID が必要で、受理済みの ID と署名された本文そのものは `webhook.replay_seconds`（既定 1 時間、メモリは上限あり）の間記憶されるため、別の ID で再送された傍受済みリクエストも同じ配信として扱われ、重複には `202 {"duplicate": true}` を返します（GitHub の画面からの手動再配信は同じ本文を繰り返すため、この期間内は無視されます）。1 つのリポジトリが 1 分間に引き起こせる受理イベントは最大 `webhook.max_per_minute` 件で、超過分は応答のみで無視されます。ペイロードに `full_name` がある場合、その所有者は監視中のアカウント（または `webhook.allowed_owners` の 1 つ）でなければなりません。1 つのアドレスから 1 分あたり、正しく署名されたリクエストは 120 件まで、署名が検証できないリクエストは `webhook.max_bad_per_minute` 件までです。この 2 つはどのモードでも別々に数えられるため、不要なリクエストが本物の配信の枠を使い切ることはありません（`listen.trusted_proxy` を使うと、プロキシが見たアドレスで数えます）。受理したイベントの後、そのリポジトリの保存済み条件付き読み取りは破棄され、次のサイクルで再読み込みされるため、ライブイベントは常に GitHub と照合されます。 配信の記憶はデータフォルダー内の非公開ファイルに保存されます(`webhook.persist_deliveries`、既定でオン。上限あり、壊れたファイルは空の記憶として扱います)。そのため再起動しても、傍受された配信が再び有効になることはありません。`webhook.reject_stale` をオン(既定はオフ)にすると、イベント自身の時刻が `webhook.replay_seconds` より古い署名付きワークフローイベントは、応答のみで無視されます。1 つのアドレスから送れる正しく署名されたリクエストの枠は `webhook.max_verified_per_minute`(120)です。`webhook.secret_env` は、システムや GitHub ログインの変数(PATH、GH_TOKEN など)も、ほかの設定に属するシークレットも受け付けず、1 つの名前は 1 つの設定にしか書けません。

使う時計は常にこのコンピューターのもので、配信側のものではありません。`webhook.clock_skew_s`(既定 300 秒、0〜3600)は 2 つの時計が違ってよい幅です。ウィンドウに対してこれだけ古く見えるイベントは、それだけでは古いとされず(`webhook.reject_stale`)、このコンピューターの時計が進んでいたときに記録され、その後時計が戻されたイベントも到着したものとして数えられるため、時計のせいでリポジトリが停止と表示されることはありません。気づかれた時点から古くなっていきます。1 日以上先の記録は信用されません。

## 順序、キュー、失われた配信

- **順序。** GitHub は配信の順序を保証しません。実行やジョブは前にしか進みません(待機、実行中、完了)。同じ実行について既に分かっていること(直前のサイクルが読んだ内容も含む)より少ないことを言うイベントは何も変えず、`GET /api/live-status` の `stats.out_of_order` に数えられます。実行の新しい試行は最初からやり直しです。
- **キュー。** 受理したイベントは最大 `webhook.queue_max` 件(既定 500、1 から 10000)のキューで待ち、ワーカーが適用するため、GitHub にはすぐ応答します。キューが満杯のときは `Retry-After` 付きの `503` を返して配信を忘れるので、GitHub が再送したものは受理されます。イベントが黙って捨てられることはありません。深さは `GET /api/live-status` の `queue`、拒否は `stats.queue_full` です。
- **失われた配信。** イベントが開いたまま残した実行(待機または実行中)が `webhook.stale_after_h` 時間(既定 6、1 から 168)以内に最終イベントを受け取らない場合、実行一覧で `stale` と印が付き、次のサイクルでそのリポジトリが再び読まれます(`stats.stale`。`open_runs` は開いたままの実行を数えます)。
- **準備完了。** `GET /readyz`(このコンピューターからのみ)は、モニターが仕事を受けられるときに `200`、そうでないときに失敗した確認項目付きの `503` を返します。`loaded`(最初の読み取りが済んでいる)、`cycle`(更新ループが止まっても消えてもいない)、`store`(データフォルダーに書き込める)、`queue`(キューに空きがある)。`GET /api/health` はプロセスが生きていることだけを示します。

## Webhook なしで:アカウントのイベント(既定ではオフ)

`events_feed.enabled` をオンにすると、モニターは `events_feed.interval_seconds`(既定 60。`X-Poll-Interval` の方が長ければそちらが優先)ごとに、アカウントのイベント(`GET /orgs/OWNER/events` または `/users/OWNER/events`。どちらを使うかは `events_feed.owner_kind` で、`auto` はまず組織を試します)を ETag 付きで読みます。新しいものがない読み取りは `304` を返して割り当てを消費せず、変化があったとき(push、プルリクエスト、タグ、リリース)は、イベントに書かれたリポジトリだけが次のサイクルで再読み込みされます(1 ターンあたり最大 `events_feed.max_per_tick`)。最初の読み取りは一覧の位置を知るだけです。Webhook もトンネルも不要で、併用もできます。カウンターは `GET /api/live-status` の `feed` にあります。

## ライブ表示のチェックリスト

1. `webhook.secret_env` で指定した環境変数に 32 文字以上のシークレットを入れ、Webhook を有効にします。
2. ポートを転送（`gh webhook forward`）するかトンネルを開き、`/api/webhook` で終わるそのアドレスを GitHub に設定します。
3. ワークフローを実行する（または監視対象リポジトリに push する）と、`?view=live` にそのイベントが出るか確認します。GitHub の `ping` は署名の確認だけで、`200` で応答され、一覧には載りません。GitHub からの再送は重複として無視されます。
4. ヘッダーの割り当てに注意します。Webhook があれば周期は遅くて十分です。
