# 更新日志

工具本身(监视器 + 哨兵 + 批处理工具)的版本,采用自己的语义化版本号。源文件是英文的 CHANGELOG.md,本文件包含相同的版本和章节。

## [1.8.1]

### 修复

- 读完最后一个仓库后,“正在加载仓库”框仍留在页面上:现在读取一结束,完成的画面就会送达页面,不再等待随后的维护工作(给 AI 工具的简报、警报中心);Sentinel 面板列表很长时,这份简报也不会再无限循环(正是这个循环让最后的部分画面 131 / 131 一直留在页面上)。
- 刷新页面(F5)不再需要几分钟才能拿到数据:简报的无限循环占满了监视器的处理器时间,页面因此中止放弃;此外,数据端点的响应是在持有全局锁的情况下写入连接的,所以一个停滞的连接(关闭的标签页)会冻结其他所有页面和刷新周期。现在只在取画面时持有该锁。浏览器测试检查该框在加载时显示、并随最后一个仓库消失;服务器测试检查简报会结束、完成的画面先于维护工作发布、停滞的连接不会阻塞刷新。

## [1.8.0]

### 变更

- **新的文件夹布局,行为不变**:代码现在是位于 `src/github_actions_monitor/` 的可导入包(`app`、`accounts`、`sentinels`、`security`、`data_pipeline`、`integrations`、`cli`、`ui`、`i18n`、`util`);网页、中性示例与 `quotas.json`、八种语言目录位于 `assets/`(`static`、`examples`、`locales`);`make_release.py` 位于 `tools/`。启动脚本仍在产品文件夹中,运行 `python -m github_actions_monitor`(完整版)或 `python -m github_actions_monitor.lite`(lite 版):地址和端口相同。使用者的数据(`actions_monitor.json`、缓存、日志、`accounts/`、目录文件)仍在启动脚本旁边,绝不放进 `src/`。

- 指南中的命令(`python read_report.py`、`python actions_monitor.py --doctor`、`python monitor_cli.py status` 等)继续有效:产品文件夹里保留了同名的小型入口文件,因此已按路径注册的钩子和 MCP 服务器也继续工作。发布 zip 保持原文件夹名,现在包含 `src/`、`assets/` 和 `tools/`。

- **路线图说明 1.8.0 包含什么以及之后每个版本将带来什么**:已在主分支的内容、已完成等待合并的内容、仍在收尾的内容,以及按实施顺序排列的从 1.8.2 到 2.0.0 的计划,共八种语言。

### 新增

- `tools/migrate_layout.py`,用于原本是平铺安装的文件夹:默认试运行;`--apply` 会把你的配置复制到 `layout_backup_<时间戳>/config/`,并把旧模块、旧网页、旧示例和 `locales/` 移动(绝不删除、绝不覆盖)到 `layout_backup_<时间戳>/old_code/`。只要还有此类遗留,`--doctor` 就会提醒。`MIGRATING.md` 以八种语言说明。

- **存储层**(`src/github_actions_monitor/storage/`):一个 `Storage` 接口(配置、哨兵状态、事件流、分析、小型文档,以及用户、其账户和会话的全局记录),对每种后端都遵守“写入是原子的,损坏的项目按空处理”的规则。第一个后端 `FileStorage` 完全保持原来的 `accounts/<id>/` 布局(以及启动器旁边的扁平安装):同样的文件、同样的名称,通过先刷到磁盘再改名的临时文件写入。`create_storage` 是唯一选择后端的地方;精简版始终使用文件。

- 任何后端都能恢复的存储备份:一个 `.zip`,包含转储和清单(账户数、大小、SHA-256);恢复前先校验副本,并且除非强制,否则拒绝写入已有账户的存储。

- **SQLite 后端**(可选,默认关闭):同样的数据放进数据库,每个账户一个文件(`accounts/<id>/storage.sqlite3`),只有该账户的进程会写它。WAL 日志和等待时间,每次写入都是短事务,带版本的架构迁移与版本号更新在同一个事务中执行(被中断的迁移让数据库保持原样;更新版本的数据库会被拒绝),按时间为账户事件建立索引,中途被终止的进程在下次启动时恢复。迁入数据库的有:事件流、事件流已通报的内容、分析、哨兵状态、静音设置和更新提示;配置仍是 JSON 文件,缓存和日志仍是文件。精简版没有此选项。

- 整个安装共用一个数据库(多个账户和进程使用同一个文件)已经备好并经过测试:WAL、等待时间、两个进程同时运行周期,以及页面通过 HTTP 应答而不必等待写入方。

- `tools/migrate_storage.py` 在文件与 SQLite 之间双向迁移状态:默认试运行;`--apply` 一步复制每个账户,然后比较每一项和每条事件;你的文件绝不会被修改或删除;被中断的运行让每个账户要么完整、要么保持原样,再次运行同一命令即可继续。`tools/backup_storage.py` 为两种后端创建、检查和恢复备份。

- **保留与轮转**(完整版):`retention.events_days`(90)和 `retention.analytics_days`(180)决定事件和分析历史日期的保留时长;`retention.mode` 为 `archive`(默认;旧事件先写入账户 `events/archive/` 中的 `.gz`,再从事件流中移除)或 `delete`;`retention.enabled` 是开关,`retention.interval_hours`(24)决定在刷新结束时多久快速执行一遍。每次清理都会留下一行审计记录(时间、删除和保留的事件数、归档文件、分析天数、错误)。清理绝不会改动配置、哨兵状态、静音设置或没有时间的事件。`retention.events_max_kb`(512,与以往相同)是事件流文件的大小上限。这些设置在“文件夹与文件”标签页;精简版没有。

- `--doctor` 新增两项检查:存储(SQLite 数据库存在、通过完整性检查、架构为当前版本所能理解;只读)和保留(每个账户事件的大小与 `retention.warn_events_mb` 比较,并对没有保留区块却作为服务运行的监视器发出警告)。

- **团队模式：用户、角色与会话**（`src/github_actions_monitor/security/auth.py`、`auth_http.py`、`auth_cli.py`；通过 `auth.enabled` 默认关闭，因此一个人使用时毫无察觉）：第一位管理员（在 `/login` 或控制台创建，只能在运行监视器的电脑上、只能一次）存在后，每个请求都需要会话。角色 `viewer`（只读）、`maintainer`（还可静音、确认、更改工作模式）和 `admin`（还可更改设置、用户以及一切可触及 GitHub 的内容）；无人列出的路由对除 admin 外的所有人关闭。每个用户有可查看的账户：用 `?account=`、`X-Account-Id` 或导出请求其他账户会返回 403。密码以加盐的 scrypt 哈希保存；会话是 HttpOnly、SameSite=Strict（HTTPS 时加 Secure）的 Cookie，每个 POST 都带 CSRF 令牌，或是供脚本和应用使用的 Bearer 令牌（`auth.allow_bearer`）；错误密码达到 `auth.max_failed_logins` 次后用户被锁定，每个地址有请求频率限制，新的密码、角色或状态会结束该用户的会话，并且始终保留一位有效管理员。端点 `/api/auth/login|logout|me|bootstrap|password`、`/api/auth/users` 和 `/api/auth/audit` 以 `{"error", "code"}` 返回错误；`auth_audit.jsonl` 记录登录、锁定、被拒绝的请求和用户变更，不含任何机密。lite 版从不登录，页面的一次性令牌仍然适用，`python -m github_actions_monitor.security.auth_cli` 可找回丢失的管理员密码。七项设置（`auth.*`）及其八种语言的帮助，以及八种语言的 `docs/ADVANCED.md` 一节；`tests/test_auth.py` 在真实服务器上覆盖规则、各类路由的角色、账户之间的范围、Cookie、CSRF、Bearer、锁定和审计。

- 账户监督器按用户过滤：`GET /api/accounts`、`/api/accounts/<id>/status`、账户页面以及所有带 `?account=` 或 `X-Account-Id` 的请求只显示并访问分配给该用户的账户（admin 可看全部），账户的监视器会知道是谁在操作。“警报”标签页的静音现在会记录是谁做的：`GET /api/alerts` 中的 `muted_by` 和静音历史。

- **团队模式的页面显示当前登录的用户**：页眉中的一个框显示名称和角色（文字，而不只是颜色），点开后可修改密码、查看并管理用户和审计（仅管理员）以及退出登录；开启模式但尚无用户时，首次会指向 `/login`。页面发出的每个更改都带有 CSRF 令牌，会话结束时跳转到 `/login`，错误的令牌会被更新并重试一次。在个人模式和 lite 版中，页面不绘制也不发出任何新请求；`tests/test_auth_page.py` 在 Node 中针对假网络运行 `fetch` 的包装器。

### 安全

- **错误令牌的锁定重新起到限制作用(网络模式)**:不是本机且已被锁定的地址,会在判断其令牌之前就被拒绝,无论令牌以何种方式出示(请求头、Cookie、`?access=` 和 `POST /api/access`);此前被锁定的地址仍可继续猜测,正确的令牌依然能进入。本机上的使用者永远不会被锁在自己的监控之外。

- **声明了反向代理后,回环地址不再等同于“本机”**(`listen.proxy_public_host`、`listen.secure_cookie` 或 `listen.trusted_proxy`):忘记转发请求头的代理不能再把互联网上的任何客户端变成所有者。在监控所在电脑前的人使用新增的、只监听 `127.0.0.1` 的第二个端口(`listen.local_port`,0 = 关闭,需要重启,使用同一个访问令牌)。启用 `listen.trusted_proxy` 时,代理所有客户端的错误令牌还会合计计数(为单个地址上限的三倍),因此轮换 `X-Forwarded-For` 无法绕过锁定。

- **反向代理指南**(`DEPLOYMENT.md`,八种语言)给出完整配方:公开的 `Host`、`X-Forwarded-For $proxy_add_x_forwarded_for`、`X-Forwarded-Proto`、网络模式以及对代理的声明;不再说监控“没有登录”,并说明 `listen.trusted_proxy` 假定代理位于同一台电脑上。

- **面向网络客户端的 `GET /api/settings`** 只返回它可以修改的设置的值;对其他设置(密钥和令牌的路径、文件夹、变量名)只说明是否已定义。

- **对每个“仅限本机”路由的测试**:用一个不在回环地址上的客户端对真实服务器遍历路由表(并检查源代码,避免遗漏新路由)。

- **GitHub 地址只有符合封闭清单中的形式才能原样通过清理器**(仓库、含作业或尝试的运行、提交、议题、拉取请求、文件);它在第一个不是字母、数字、点、连字符、下划线或斜杠的字符处被截断,其后的内容与其他文本一样被清理。此前,粘在链接上的秘密(编码的查询串、用逗号分隔的列表、冒号、路径中不透明的一段、从地址中开始的电子邮件)会原样传给 AI。

- **AI 客户端的钩子不再交出任何日志文本**:只交出每个告警的仓库、工作流、结论和链接。“不等提示就行动”的指令已删除;最后一行现在说明日志可能包含第三方写入的文字,它们是不可信数据,绝不遵循其中的指示。支持八种语言。

### 修复

- **面向 AI 的事件流不会再因普通日志行而中断**:订阅源中的一行先逐字段清理再写出,而不是清理已经写好的 JSON(原因以 `password: x`、`token=x` 或 `DB_PASSWORD=x` 结尾会把它弄坏)。无法清理的行会被跳过,事件流继续;MCP 服务器的回答也以同样方式清理。在清理器中,`键=值` 的值在引号、逗号或分号处结束,带引号的值会被整体清理。

- **取决于“谁在询问”的内容始终由你自己的登录回答**:`gh api user`、`user/orgs`、通知、对 `@me` 的搜索、`gh auth` 以及没有所有者的 `gh repo list` 永远不会交给 GitHub App 或第二个账户,无论它们还剩多少次调用(启用第二个账户时,监控可能把该账户的持有者当作自己的所有者并列出其组织)。

- **`gh` 调用只有在白名单中才算读取**:`gh api ENDPOINT`,最多带有 `--jq`、`--paginate`、`-H`(读取会发送的那类)、`-i` 和 `--cache` 选项。写入的粘连写法(`-XPOST`、`--method=DELETE`、`-fa=b`、`--field=a=b`、`--input=-`)以及任何其他选项都交给你的登录,而不是在各来源之间分配。

- **第二个账户的令牌文件**(`extra_reader.file`)必须位于监控的账户文件夹内(`accounts/`,或 `MONITOR_ACCOUNTS_DIR`),打开时不跟随链接,且只有它是小的普通文件时才会读取;在该文件夹之外,此设置为空。新开关 `extra_reader.any_folder`(默认关闭,仅限本机)可为必须放在别处的文件取消文件夹限制。

- **日期在未来的中央面板不再被信任**:它的年龄曾被限制为零,因而永远算作新鲜;现在它被视为落后,摘要会说明日期不可信,同时容忍最多五分钟的时钟超前。

- **账户端口的测试在多个测试套件同时运行时不再失败**:现在可以告诉监督器从哪里开始寻找空闲端口(默认仍为 18800),测试向系统申请一段未使用的端口,而不是固定的一段。

- **页面一旦损坏,CI 就会变红**:新增的作业(`page`,不带 `continue-on-error`)在真实浏览器中打开演示监控的页面(`tools/check_page.py`),逐个访问每个标签页和设置的每个子标签页,要求每个都有最少数量的字段,并在出现任何页面错误、未处理的 Promise 或 console.error 时失败。故意弄坏的页面(第二处定义、对函数名的赋值、对不存在函数的调用)必须使它失败。查找重复定义函数的测试现在还能发现带缩进的声明、带 `async` 的声明以及对函数名的赋值。

## [1.7.9]

### 修复

- AI 工具（订阅流、摘要、状态、钩子）收到的运行链接曾被截断为“https://github.[blob]”：脱敏器把地址当成了不透明字符串。现在 github.com 的完整 https 地址会原样通过；令牌、密钥、邮箱、IP 和个人路径仍会被清理，链接内也一样。

## [1.7.8]

### 新增

- **`listen.trusted_proxy`**(默认关闭,仅限本机,八种语言):在同一台计算机上自己的反向代理之后,失败的尝试按 `X-Forwarded-For` 的最后一个地址而不是按代理计数,这样一个人的错误令牌不会锁住所有人。它只改变这一计数:经代理到达的请求仍永远不会被当作本机。

### 修复

- 设置页显示“本地监控器无响应”且没有标签页：配额标签页的框与基础标签页中较早的函数同名，被其替换。现已重命名配额框，并新增测试：页面中的函数若被重复定义则测试失败。

## [1.7.7]

### 新增

- **检查任何文字都不会超出所在框**(`tools/check_overflow.py` 以及在没有浏览器时会干净跳过的测试):在无界面浏览器中以八种语言、宽窄两种窗口打开页面,遍历每个标签页和窗口,只要有文字比带边框或背景的框更宽或超出窗口就会失败。
- **`display.blink_red_tiles`**(默认开启,位于设置标签页,八种语言):变红的顶部磁贴和底部状态栏项目会轻柔闪烁,直到问题解决;系统启用“减少动态效果”时,改为显示固定的较粗红色边框。
- **doctor 的时区检查**:系统和内置表都不认识的时区会被报告,时间随后以 UTC 显示(以前会悄悄退回到计算机的时区)。
- **历史标签页显示“共 N 条中的 n 条”**:当列表比顶部统计更短时显示(监视器保留最近 600 次运行;数据带有 `runs_total`)。
- **哨兵标签页的面板作为数据提供**:`GET /api/sentinel/panels`(只读)、MCP 工具 `sentinel_panels` 以及简报中的“Sentinel panels”部分,针对 A1..A13 和第二个哨兵给出级别、一行摘要以及需要处理的行(带仓库和链接);处于“需处理”或“需留意”的面板中的行还会成为信息流中的警报(类别 `real` 和 `watch`),因此事件流、钩子、`alerts_open` 和真实警报计数都包含它们。
- **新失败时的“叮叮”提示音**(`sound` 设置,八种语言):页面仅在出现新的红色或连接中断时播放两声短音(Web Audio),刷新时或对已有项绝不播放;带有最短间隔、音量设置、底部状态栏中可解锁浏览器音频并可静音且会被记住的“声音”标签,以及“此浏览器”中的“测试声音”按钮;还有用于页面关闭时的 `sound.server_beep`(默认关闭,仅限本机;Windows 蜂鸣、macOS `afplay`、Linux `canberra-gtk-play` 或终端响铃,不经过 shell,也不使用网络)。
- **监视器说的一切,以信号形式提供给 AI 工具**:一个统一的清单(`signals.py`),为“现在”标签页及其磁贴、警报、仓库、哨兵面板 A1..A13 和第二个哨兵、配额、连接以及监视器自身的健康状况提供级别(处理 / 留意 / 信息)、摘要,以及带仓库、链接、时长和下一步的行;`GET /api/ai/state`(带版本、只读)、包含“现在该做什么”“待办”“监视器健康”以及待处理信号数量的简报,还有 MCP 工具 `monitor_state`、`signals`、`diagnose` 和 `act`。一个测试会遍历页面,只要有磁贴或标签页既不在清单中也没有标为装饰性就会失败。
- **与 AI 工具的连接在 lite 版和完整版中相同**:相同的通道(简报、信息流、`/api/ai/state`、事件流、MCP 工具、`ai-hook`)、相同的代码和相同的设置;状态中带有 `edition`,并列出 lite 中不存在的面板,避免把缺失的面板当成缺失的数据。
- **节省模式(极端节省配额)**:与正常、快速和涡轮并列,`low` 只每 4 分钟读取一次活跃仓库、其余每 30 分钟读取一次,run 列表很短,并在状态栏和简报中说明数字可能较旧以及有多旧;`modes.auto_low`(默认开启)在剩余调用数低于 1000 时自动进入,超过 2500 或配额恢复时返回(两个不同的数字,避免来回抖动);数值位于文件的 `modes.low` 中。
- **不消耗配额的基线:中央面板**(`central.source`:默认关闭,可选 `git` 或 `http`;`central.max_age_minutes`,八种语言):监视器通过简单的 git fetch 或原始文件读取个人资料仓库的 `data/sentinel.json`(由工作流用自己的令牌每半小时刷新),在状态和简报中显示“来源:中央面板,N 分钟前”,忽略滞后(超过两小时)的文件并予以说明;在节省模式下,只对面板标为红色的仓库、有运行中任务的仓库以及面板不包含的内容进行 API 实时查询。
- **用于读取的可选 GitHub App**(`github_app.enabled`,默认关闭,带 `app_id`、`key_path` 和可选的 `installation_id`,八种语言):监视器的读取使用 App 的安装令牌,其配额与用户的分开,覆盖的仓库越多越大;JWT(最长十分钟)由 `openssl` 根据密钥路径签名,监视器从不读取、复制、打印或记录密钥;令牌有效一小时,保存在内存中并提前五分钟续期;写入和操作仍使用用户的令牌;若 App 失败或缺少权限,会用用户的令牌重新读取;`GET /api/github-app/status`(仅限本机)显示 App 的名称、安装、已授予的权限和配额,绝不显示密钥或令牌;数据中在 App 配额旁带有用户的配额,doctor 会检查 openssl、密钥文件及其权限。
- **两份新指南,八种语言**:`docs/AI_CONNECTION.md`(连接 AI 工具:它能看到什么、五个通道、逐步操作、安全、故障排除、各版本显示的内容)和 `docs/QUOTA.md`(“更多配额,更少消耗”:配额如何运作、监视器节省配额的所有办法、GitHub App 逐步设置、在工具之间共享配额、不要做什么);两者都从 README 和帮助索引链接,并有测试检查其中引用的每个设置都存在。
- **帮助在每次变更时都会被检查**:缺少八种语言的标签和帮助的设置、没有帮助主题的标签页,或更新日志中提到但帮助和指南里没有的设置或端点,现在都会使测试失败;帮助检查清单在 CONTRIBUTING 和拉取请求模板中。
- **设置中的“配额”标签页**(八种语言,lite 版也有):模式和节省模式数值(`modes.*`)、节省(`network.etag`,与 `cache.etag.enabled` 一起生效的别名)、中央面板、GitHub App 和用于读取的第二个账户集中在一处,按钮可显示每个来源的配额和恢复时间、测试 App 和第二个账户、列出 App 缺少的权限,并应用推荐值或默认值。
- **用于读取的第二个只读账户**(`extra_reader.enabled`、`extra_reader.file`):设置中只保存含细粒度令牌的文件**路径**,监视器在使用时读取,保存在内存中,绝不存储、打印或记录;读取按各来源的剩余调用数在你的登录、App 和第二个账户之间分配,被拒绝的来源排除五分钟并用下一个重试,写入和操作从不使用它。
- **读取的统计**:状态、简报和数据会说明进行了多少次条件调用、其中多少次返回 304(不消耗配额),以及每个来源的配额。
- **谁在消耗配额**:监视器在每个小时窗口内,把整个账户的消耗与自己的调用数比较,并在“配额”标签页、状态和简报中说明其他工具消耗了多少,在它们消耗大部分时给出警告(GitHub 不会说明是哪个工具)。
- **事件流也携带其他信号**:配额用尽、连接中断、数据过期、中央面板滞后以及健康警告,在出现、变化或解决时会成为信息流(以及事件流和钩子)的事件,而不仅限于红色工作流和哨兵标签页的面板。
- **批量分发会记录所找到运行的尝试次数**(批次记录中的 `run_attempt`,来自 `gh run list` 的 `attempt` 字段;`gh` 不提供时为空),并且 AI 工具连接指南和配额指南补充了对第二个只读账户的说明。

### 变更

- **重新设计底部状态栏**:每个项目都是带边框的小标签,连接和配额采用其状态颜色,时钟是带框的大号粗体等宽数字,上方为日期,时区为小字,窄窗口中栏的顺序保持不变。
- **每个框都让文字换行而不是溢出**(磁贴、标签、徽章、单元格、标题、窗口按钮):最近一次读取的时间将时区以小字单独显示,警报行在窄窗口中变为两列,磁贴网格可以缩小到内容以下。
- **同一行的磁贴高度一致**,无论其小字需要多少空间。

### 修复

- **未解决故障只有一个数字**:“main 上的红色”磁贴、警报列表、底部状态栏和简报统计的是同一件事,即默认分支上最后一次运行失败的工作流(工作分支上的失败不再显示为未解决警报);只要还有未解决的警报,状态栏就不会显示“无通知”。
- **启动时只显示一次版本**:重复标题的“GitHub Actions v...”一行已去掉,作者和许可证保留在一行中。
- **损坏的状态文件**(形状不对的协作状态、哨兵缓存和历史)会逐条被忽略,不会传到读取它们的代码。
- **GitHub 配额用尽现在是一条通知,而不是每个仓库一个错误**:仓库读取会暂停到配额恢复(并自动继续),警报列表和底部状态栏会显示“GitHub 配额已用尽,HH:MM 恢复 ...(N 个仓库未刷新)”,不会变红,也不会作为失败进入信息流、声音或简报;`gh` 的错误文本被截成一行(不含法律段落和请求 ID),许多仓库的同类错误合并为一行。
- **“关于”(以及所有页面)不再等待网络**:当监视器新版本检查的结果超过一天时,它会在 /api/about 请求内部读取,因此未登录的 `gh` 或缓慢的网络会让“关于”窗口耗时 10 到 25 秒;现在会立即返回缓存的结果,读取由后台线程完成,一次只有一个。

## [1.7.6]

监控器与 AI 工具的联动: 信息流始终与页面一致, 每条告警都说明为何变红, 事件流和三个 MCP 工具推送新消息, 一条命令即可安装联动脚本, 底部栏显示是否有 AI 已连接, 所有状态文件仅其所有者可读。

### 新增

- **摘要和信息流跟随告警页的每次刷新** (以及信息流的每次读取和每个周期): 以前它们落后一个周期, 因此页面显示 6 条时 AI 可能读到 10 条。`ALERTS_BRIEF.md` 现在带有你所在时区的 `Updated:` 和供机器读取的 `updated_epoch:` 行, `GET /api/ai/brief?fmt=json` 另外提供 `updated`、`updated_local` 和 `age_seconds`。数据尚未加载的周期绝不会解决告警。
- **`ai_alerts.diagnose`** (默认关闭, 设置页, 八种语言): 新红色运行的每条告警带有 `diagnosis`, 即第一个失败的步骤和日志中约十行相关内容, 用只读调用读取, 已清除机密, 并限制大小和每周期读取的运行数; 日志中的基础设施错误会使该告警视为临时性。
- **`ai_alerts.cascade`**: 因另一个仓库变红而变红的告警 (在日志或规则 `ai_alerts.cascade.map` 中点名) 会在摘要中列在它之下, 并带有 `origin`。
- **`GET /api/ai/stream`** (`ai_alerts.stream`, 默认关闭): 服务器推送事件, 只读, 网络模式下需要访问令牌, 限制监听者数量和时长, 可用 `Last-Event-ID` 续传; lite 版没有它。
- **MCP 工具 `alerts_open`、`alert_diagnose` 和 `alert_ack`** (最后一个仅在 `--allow-ack` 时提供), 以及 AI 连接时的提示: 在 `instructions` 中并通过一条通知说明有多少真实告警未处理。
- **`monitor_cli.py ai-hook install|status|uninstall [--assistant|--cursor|--generic] [--scope project|user] [--dry-run]`** 和联动脚本 `ai_hook.py` (仅用标准库): 把摘要加入 AI 会话, 并且仅在 `ai_alerts.client_hook.block_on_stop` (默认关闭) 开启时, 在回合结束前提示 AI 查看未处理的真实告警。工具的设置是合并而非替换, 会保留文件备份, 不是有效 JSON 的文件会被拒绝且不改动, 写入的内容全部是纯 ASCII。相关数值在 `ai_alerts.client_hook` 中 (设置页, 八种语言)。
- **AI 心跳** (`ai_alerts.heartbeat`): 事件流、MCP 服务器、联动脚本和端点把最近一次读取记录在一个本地小文件中, 底部栏显示是否有 AI 已连接以及多久前读取过。
- **`monitor_cli.py --token-file FILE`**, 以及在使用 `--token` (它会出现在进程列表中) 或令牌文件可被其他用户读取时在 stderr 发出警告。
- 每项更改都有测试, 在临时文件夹中离线运行, 包括宽松 `umask` 下每个状态文件的模式。

### 变更

- **监控器的所有状态文件都以 0600 模式创建** (创建的文件夹为 0700), 通过唯一的辅助模块 `private_io.py`: 静默记录、事件、信息流、摘要、缓存、设置以及联动脚本安装程序写入的文件。在 Windows 上程序无法强制设置模式 (文件夹继承其父文件夹的权限)。
- **启动网络模式** 时若 `listen.query_access` 仍开启, 现在会打印第一步 (关闭它; 使用 HTTPS 或 VPN), `listen.network` 的帮助和高级指南也用八种语言说明了同样的事。
- **面向 AI 的告警信息流现在默认关闭** (`ai_alerts.enabled`, 以前是开启的): 新安装在你开启之前不会写出任何信息流。文件夹中已有信息流的安装保持开启, 控制台会在启动时说明一次, 因此有意使用它的人不会被关掉。


### 安全

- **发出的通知会忽略环境中的代理变量** (`http_proxy`、`https_proxy`): 有代理时检查判断的是代理的地址而不是目标地址, 而用重定向回应的代理可能把请求引向本地网络 (包括云的元数据地址)。新设置 `network.use_proxy` (默认关闭, 在设置页, 八种语言) 可重新使用它们, 此时会在代理收到任何内容之前检查目标地址和每次重定向的目标。已用一个重定向到元数据地址的代理测试。
- **`/api/ai/actions/confirm`、`/api/ai/actions/unlock`、`/api/ai/test` 和 `/api/notify/test` 在网络模式下仅限本机** (403 `local_only`), 与其他会执行操作的端点一致。
- **`act` 的计划与其工作流绑定**: 计划保存解析后的路径和文件的 SHA-256, 并在启动 `act` 之前再次核对; 确认之后被编辑、替换或删除的工作流不会运行 (`workflow_changed`, 附八种语言的文字)。
- **macOS 钥匙串不再通过命令行接收令牌**: `security -i` 从标准输入读取命令, 因此令牌不会出现在进程列表中。
- **`gh` 输出的所有内容在保存前都会清理**: 面向 AI 的操作日志和被拒绝操作的详情都经过清理器, 现在也覆盖旧的 40 位十六进制令牌以及监控器保存的令牌。
- **被拒绝地址的列表有上限** (`localguard`): 下一次锁定会清除所有已结束的锁, 而不只是发起请求的地址, 并且最多保留 2000 项。
- **未能保存的静默不会被报告为已保存**: 文件无法写入时, `POST /api/alerts/mute` 和 `unmute` 返回 `ok: false`。
- **面对形状错误的响应, 命令行绝不显示回溯**: 用列表、`null` 或数字代替对象, 或字段类型错误, 都以退出码 4 和一条消息结束。
- **网络客户端只能写入一个很短的允许列表中的设置** (语言、时区和页面的刷新节奏): 每个通知渠道、每个路径、每个环境变量名以及签名和分发流程所信任的文件, 都必须在监控器所在的电脑上更改。之后新增的设置在被有意列入之前仅限本机。
- **在同一台机器上的反向代理之后**, 带有转发头 (`Forwarded`、`X-Forwarded-*`、`X-Real-IP`) 或代理公开名称的请求绝不会被当作“这台电脑”, 并且访问令牌先于按地址的封锁被判断, 因此大量错误令牌不会把所有者锁在门外。
- **对本机的调用绝不经过环境中的代理** (`netguard.local_open`, 供命令行、MCP 服务器、终端视图和钩子使用), 命令行也不跟随重定向, 因此访问令牌不会被转发到别的地址。
- **每个响应都禁止被嵌入框架** (`X-Frame-Options: DENY`、`frame-ancestors 'none'`、`nosniff`), 页面像 API 一样检查 `Host`, 通过已弃用的 `?access=` 地址认证的响应都带有 `Deprecation` 头。
- **分发与签名**: 分发之前已存在的运行会被记录, 只有新的运行才可能被认作自己的 (不依赖时钟); 出现两个新候选需要复核; 输入 `ref` 是已检查的提交; 必需的工作流按其文件而不是显示名称匹配; 批次名称使用 UTC。
- **面向 AI 的信息流清理器覆盖更多格式**: 以 `PASSWORD`、`PWD`、`SECRET` 或 `TOKEN` 结尾的名称、地址中的凭据、Slack 和 Discord 的 Webhook、Telegram 机器人令牌、`glpat-`、`npm_` 和 `pypi-` 令牌、私钥、长十六进制字符串以及本监控器的访问令牌。MCP 服务器的 `get_run_failure` 只读取监控器所监视的仓库 (或 `ai.allowed_repos`)。
- **手工编辑的文件** (静默记录、更新状态) 只会丢失其中无效的条目, 无效的更新状态不再阻止启动。
- **时区**: 内置表中的开罗自 2023 年起遵循夏令时, 系统不认识的时区名称会在设置页被拒绝。完整版像 lite 版一样在页头报告红色工作流数量, 没有数据时 `monitor_cli.py status` 像 `health` 一样以退出码 4 结束。

## [1.7.5]

命令行以专用名称读取访问令牌，网络模式默认更安全（对网络隐藏本机地址、可关闭旧的 ?access= 地址、拒绝本地网络上的通知目标、对明文 HTTP 发出警告），面向人的时间使用你自己的时区，警报可以静音到该项目发生变化为止，并修正了给出错误结果的计数和检查。

### 新增

- **`monitor_cli.py --token TOKEN`**,命令行的访问令牌现在使用监视器自己读取的名称:先是 `MONITOR_ACCESS_TOKEN`,再是其别名 `MONITOR_TOKEN`,最后是 `--token`(命令行选项会出现在进程列表中,因此是最后手段)。被拒绝客户端的消息会指出变量名。已针对要求该请求头的模拟监视器测试。
- **stderr 警告**:当 `monitor_cli.py` 指向另一台计算机的未加密 `http` 时(令牌和响应将以明文传输)会打印警告;响应和 `--json` 不受影响。
- **`listen.query_access`**(默认开启,位于设置页,八种语言):关闭后,已弃用的 `?access=` 地址会被拒绝,会话只能通过 `POST /api/access`(正文中的令牌)或请求头打开。仍可用的地址会以 `Deprecation` 响应头回应,控制台会说明它已弃用。
- **“直到该项目发生变化”的静音**:`POST /api/alerts/mute` 对单条警报接受 `until_change`;静音会记住 issue 或拉取请求当时的 `updated_at`,当它变化(新评论、推送)或小时数结束时(以先到者为准)立即结束。Collab 的警报现在带有 `details.updated`。
- **针对多个账户共用同一令牌的 doctor 检查**(`credential`):只比较各账户读取 GitHub 所用令牌的简短指纹(监视器保存的令牌,或环境中的 `GH_TOKEN` / `GITHUB_TOKEN`),并列出共用同一令牌的账户;绝不显示令牌本身。
- 每项改动都有测试,包括一个 webhook 卫生测试:带有密钥、电子邮件、提交信息和令牌的载荷不会到达实时列表、动态流或通知,实时列表现在由允许字段列表过滤。

- **`notify.allow_private_targets`**(默认关闭,在“设置”标签页,八种语言):拒绝属于或解析到回环、私有(10.x、172.16-31.x、192.168.x、fc00::/7)、链路本地(169.254.x,含云元数据地址,fe80::/10)、共享(100.64.0.0/10)或保留地址的通知目标。名称只解析一次,套接字连接到已检查的地址(改变应答的名称无法通过),每次重定向也遵循同一规则。`mqtt` 和 `http_local` 按定义仍仅限本机。已用假服务器和假解析器测试。
- **网络模式下纯 HTTP 的警告**:开关 `listen.network` 的帮助现在以八种语言说明,没有 HTTPS 时令牌和数据以明文传输;在没有证书的情况下以网络模式启动时,控制台已会发出警告。
- **为人而写的时间采用您自己的时区**：`monitor_cli.py` 的 `Last read` 行和静音、日志 `actions_monitor_log.txt`、哨兵的报告、给 AI 的摘要以及通知，以前都以 UTC（`...Z`）显示且不加说明，与墙上的时钟相差一两个小时。现在它们显示为 `11:43:07 CET (10:43:07 UTC)`：计算机的时区、其名称，旁边是 UTC 时间。夏令时也会跟随（已围绕一年中的两次切换，并针对马德里、UTC、东京和纽约测试）。

- **监督程序**（`accounts_supervisor.py`）：存在 `accounts/` 文件夹时，`python actions_monitor.py` 会在常用端口上启动一个小进程，为每个账户运行一个监视器（`account_child.py`），每个都在 `127.0.0.1` 上有自己的端口。某个账户的崩溃、响应缓慢或速率限制绝不会影响其他账户；停止的账户会以逐渐增加的等待时间重新启动（2、5、15、30、60，然后 120 秒），在此期间概览会显示它已停止。它不从 GitHub 读取任何内容，也不写入任何内容；停止它时会结束它启动的所有进程，在 Windows 上也一样。

- `ci_red.json` 的模式 2 现在是有文档的契约：`docs/CI_RED_SCHEMA.md`（形式、“红色”的唯一规则、仅属于所有者的内容）。PC 不会发布任何东西。可选且明确的导出（绝不提交或推送）：`read_report.py --export-status DIR` 仅写出红色列表（`ci_status_public.json/.md`）；`read_report.py --export-sign-queue FILE`（.json/.csv）写出带本地命令的全局签名队列。
- 证明（attestation）：签名队列显示构建是否有证明（按已签名文件的摘要检查是否存在，每个条目一次查询，不验证签名；开关 `sentinel.surface.checks.attestation`）。缺失的会成为报告中的一行。
- 更多已验证的格式：HYDRA 的 `hydra-sign`（`FILE.sig` = 对文件字节做的 base64 Ed25519，固定的发布密钥，分块读取）可被确定性验证；URTC 的 `.imgsig` 会检查其严格格式（152 个十六进制数字 + LF；格式错误 = 无效），格式正确时仍为“unknown”（被签名的消息还需要构建头，而已签名文件夹中没有）；ARMOR 的 APK 由 apksigner 在 APK 内部签名，仍为“unknown”。
- `HYDRA-UMC-OS` 在 `targets.json` 中被有意标记（`"build_only": true` + `reason`）：`plan` 把它列在 BUILD ONLY 下，不再是孤儿。签名工具未改动（其工作流使用其他输入和不同的签名方案）。
- 修复：`ci_red.target_path` 曾拒绝所有用反斜杠书写的 Windows 路径（`C:\...`）；只接受正斜杠。

**B 部分 - A10 层“Actions 与发布的外围”**（`surface.py`，标签页新增部分，`sentinel.surface` 下每项检查一个开关和一个阈值）
- Actions：被手动禁用的工作流、N 天内没有运行的计划任务（仅当运行样本覆盖该窗口时）、未按 SHA 固定的 `uses:`（可复用工作流单独标记）、`permissions: write-all`、检出 PR 的 `pull_request_target`、卡住的并发队列、矩阵中仅一个操作系统上的失败、制品的成本和保留期、红色或缺失的必需状态检查（GraphQL）、带金丝雀（只先运行第一个目标，其余仅在其为绿色时）和配额闸门（`--min-rate`，默认拒绝）的 `dispatch --profile release|nightly|hil`。配置保存在 `profiles.json` 中。
- 发布：按目标类型的预期资产（发布不完整时警报）、标签与清单与 CHANGELOG 的对比、GitHub Packages、被遗忘的草稿和预发布、`release_notes.py`（根据自上一个标签以来的提交生成说明草稿；不会发布任何内容）。
- 安全：按时长排列的严重/高危警报及仓库排名、覆盖率（没有 CodeQL / Dependabot 的技术栈）、机密扫描中未解决与已解决的对比、按优先级排序的 Dependabot（运行时主要版本优先，仅 CI 的最后）。
- Issue 与 PR：对 CI 已恢复绿色的构建 Issue 建议 `gh issue close`（带文字的事件；绝不会关闭任何东西）、逾期的里程碑、陈旧的人工 PR、涉及工作流或 CODEOWNERS 的 PR、合并队列（已批准且检查为绿色）。过期的看板卡片：待定（需要逐项读取和一个阈值）。
- 清单与证据的对比（成熟度）、八种语言 README 的一致性失败、页头、报告和 A7 中按生态系统统计的 Actions 分钟数。
- `finalize --execute` 现在会通知运行中的监视器（127.0.0.1）只刷新已签名的仓库并立即重写 `ci_red.json`（`monitor_link.py`）。
- 可选的已签名 Webhook 接收器（`webhook.enabled`，默认关闭，仅 127.0.0.1，使用配置中的共享密钥做 HMAC，绝不使用 GitHub 令牌）。
- 开销：热周期中没有任何增加。冷调用分散在各个周期并在每小时预算内：每个仓库每天 2 次 REST 调用，每 15 个仓库每天一次 GraphQL 查询，Packages 3 次，另加红色运行的作业和签名队列的证明查询，并且仅当配额高于 `min_rate_remaining` 的两倍时。热 GraphQL 遍历对每个节点多请求 3 个字段（警报日期、评审决定、检查状态）：没有额外的调用。
- 闸门还会把示例文件中的 `sentinel.surface` 与默认值比较，并验证 `profiles.json`。

## [1.1.0]

签名可信度、通向仪表盘的稳定桥梁、批处理工具中的孤儿与约定，以及更实用的页面。

- 签名可信度：`sigverify.py`（标准库、只读、无网络）依据各生态系统固定的公钥（URTC 的 `release_sign.py`、ARMOR 辅助工具的 `PACKAGE_PUBLIC_KEY`、HYDRA 更新器的 `RELEASES_PUBLIC_KEY`，或 `sentinel.signature_pubkeys`）检查已签名文件夹 `_firmados/<REPO>/release-<版本>/`。每个状态现在都带有 `signature_kind`（none | dev | release）和 `signature_verified`（true | false | "unknown"）；除“已发布”外，只有能通过验证的发布签名（`trusted`）才会降低待签名警报。无法通过验证的签名会保留警报并在报告中说明。`sentinel.require_verified_signature`（默认 true；false = 1.0.0 的规则）。本模块无法检查的格式（.sig2、.hdr2、.imgsig、APK、hydra-sign）为“unknown”，绝不是“false”。构建证明仍然需要网络，由签名工具负责。
- `ci_red.json` 模式 2：每个仓库在红色工作流旁增加 `pending_sign` 列表（workflow、hours、state、signature_kind、signature_verified、last_build_at、url），另有 `schema`、`pending_sign_repos` 和阈值；格式在 `ci_red.py` 中有文档，且只会扩展。
- “main 上最后一次运行”只有一个定义（`signstate.completed_runs`），由红色检查、无发布的绿色检查和目标状态共用。
- `ci_red.target_path` 会拒绝 D: 路径、D: 的 WSL / Git Bash 形式，以及运行系统无法使用的盘符 / UNC 路径；测试模拟两种系统，整个测试套件现在在 Linux 上也能通过。
- `gha_dispatch_all.py plan` 总是以“签名孤儿”部分结束（绿色 CI + 已知的 `*-build.yml` + 没有目标）；覆盖范围按仓库和工作流计算。
- 目标的约定（生态系统前缀 -> 默认签名工具，工作流在已知列表中）；`targets.json` 只保存例外，并始终优先。`hygiene --write-candidates` 把建议的条目写入 `targets.candidates.json`（绝不会自动应用，也绝不会被打包）。
- 页面：可点击的页头计数器“main 上为红”和“未签名”（筛选仓库；后者还会聚焦签名队列）、带命令和复制按钮的签名队列、显示已构建 / 已签名 / 已发布、签名类型与验证以及建议命令的仓库面板；当分钟预算达到 80% 时页头出现徽章（超出时为红色）；“昨天与今天”的对比也包含预算警告和报告中的行。

未完成：读取构建证明 / SBOM（需要网络）；`HYDRA-UMC-OS` 有构建工作流，但其签名工具尚不支持（列为孤儿）。

## [1.0.0]

第一个带编号的版本。软件包的功能：

- 面向四个生态系统的 GitHub Actions 监视器（本地网页、运行缓存、卡住的构建、build-failed / build-stuck Issue）。
- 哨兵 A 层（只读，无需 AI）：A1 卡住的构建，A2 红色 CI（唯一标准：每个工作流在默认分支上最后一次完成的运行），A3 CodeQL / Dependabot / 机密警报，A4 Dependabot 拉取请求，A5 发布（候选、没有发布的绿色构建、待签名），A6 卫生，A7 消耗（分钟数和 API 配额），A8 审计与轮次，A9 路线图看板。
- 每个构建目标的明确状态：built_on_gha -> signed_local（none | dev | release）-> published，带有 `last_build_at`、`last_signed_at`、`signature_kind` 和实际等待小时数；本地批处理记录和已签名文件夹记录无需等待 GitHub 就会降低待签名警报。
- 当日签名队列（`a5.sign_queue`）：最紧急的在前，附每个目标确切的 finalize 命令。
- 每个生态系统的 Actions 分钟预算（`sentinel.minutes_budget`，默认为空）：达到 80% 时在报告中警告并产生事件。
- 事件流（`events_monitor.jsonl`）和 `ci_red.json`（仓库 -> 红色工作流 + 待签名小时数），以原子方式写入。
- 批处理工具：`gha_dispatch_all.py plan|dispatch|status|finalize|hygiene`，带 `--only` 或 `--ecosystem`、`plan --json`、`finalize --json`，批次结束时对失败的 dispatch 重试一次，目标作为数据保存在 `targets.json` 中。
- `read_report.py`：从运行中的监视器获取纯文本报告，不消耗 API 配额。
- `make_release.py`：质量闸门（单元测试、干净的 zip、完整的示例配置、版本与更新日志一致）和 SHA256SUMS。

此版本未完成：由哨兵根据公钥验证发布签名以及构建证明（各生态系统的签名格式不同；证明需要网络；签名工具在发布前会验证两者）。
