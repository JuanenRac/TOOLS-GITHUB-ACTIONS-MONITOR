# 更新日志

工具本身(监视器 + 哨兵 + 批处理工具)的版本,采用自己的语义化版本号。源文件是英文的 CHANGELOG.md,本文件包含相同的版本和章节。

## [Unreleased]

### 新增

- **面向 AI 工具的简报现在也可通过命令行和 MCP 服务器使用**：`monitor_cli.py briefs index` 列出已编目的简报，`briefs show 标签页` 输出某个标签页的信号，`briefs all` 在一份文档中输出全部简报；MCP 服务器提供只读工具 `briefs_index` 和 `brief_tab`（标签页名称或 `all`）。测试会检查页面、HTTP 路由、命令和工具列出相同的标签页；不会写入任何内容，文本经过同一个清理器。
- **可选的固定问题助手**:“警报”标签页可以显示一个面板(默认关闭,`ai.assistant.enabled`,并且需要 AI 提供方),由您配置的 AI 仅根据监视器的数据解释警报、总结当前情况或说明某个仓库为什么慢。它有一个只读取的四工具封闭列表(`ai.assistant.tools`,每个问题最多读取 `ai.assistant.max_tool_calls` 次),没有自由聊天,会显示读取的 ID 和发送的内容量(`ai.assistant.max_context`),消耗 AI 唯一的每日预算,把仓库中写下的内容截断到 `ai.untrusted_text_max` 后作为标记之间的数据交出,允许查看者提问,并把每个问题记入操作日志(路由 `GET /api/assistant` 和 `POST /api/assistant/ask`;Lite 版中不存在)。
- **面向客户端的只读 API 在服务模式下自动开启**:`api.v1_enabled` 现在是 `auto`(默认)、`on` 或 `off`。使用 `auto` 时,监视器作为服务运行(团队模式的账户、Docker 镜像、systemd 单元)前缀 `/api/v1/` 会响应,一人一台电脑时保持关闭;旧的 true 和 false 含义不变。`/api/v1/me` 还会给出契约版本(`contract`)和该会话可做的事(`capabilities`)。
- **只读 API 的完整 OpenAPI 文档**:`/api/v1/openapi.json` 现在描述每条已冻结的路由(55 个路径)及契约中的键和类型,由 `docs/schemas/api_contract.json` 生成而非手写;契约未冻结的路由是实验性的,在 `/api/v1/` 下返回 404,仅当新设置 `api.experimental_routes` 开启时才会列出。测试使文档、契约和代码中的路由保持一致。

### 修复

- **文本清理器处理长文本时不再变慢**：五千个字母、点、数字或连字符曾需要两到六秒，因为多个模式会从每个位置尝试匹配；现在前缀和地址的长度限制为真实名称的长度，耗时随文本大小线性增长，并有测试限定上限。长串字符之后的机密仍会被找到。

## [2.1.3]

### 变更

- **README 的图片以 1080p 拍摄并展示最新的标签页**：`tools/make_screenshots.py` 默认以 1920x1080 拍摄每个页面（`--viewport 宽x高` 可更改；4K、超宽、竖屏、手机和墙屏的图片保持各自的尺寸），`tools/demo_monitor.py --rich` 为演示提供交付哨兵和供应链哨兵的发现、每日趋势和时间段比较，README（八种语言）展示交付、供应链、每日趋势、比较时间段和更新页面。
- **“昨天与今天”有了自己的菜单项**：与哨兵上次保存的报告的对比从概要移到了自己的标签页（地址 `#sentinel-yesterday`，在每日趋势旁边），因此哨兵报告占满整个页面；该项跟随 CI 哨兵，带有自己的帮助、八种语言的文本，外观与哨兵的其他标签页一致。

### 安全

- **更新菜单更难被滥用**：十分钟内五次被拒绝或失败的更新或回退尝试会使按钮暂停十分钟（返回 `cooldown`，其文本有八种语言），状态会说明更新被阻止的原因（`blocked_reason`、`cooldown_seconds`），更新程序的进度文件只有在是大小合理的普通文件时才会被读取（链接、巨大、被截断或恶意的文件视为没有更新在运行），更新程序的日志在进程启动后关闭，为供应链和交付哨兵提供数据的工作流检查器会把文件截断到 1 MiB、20000 行、每行 4000 个字符，因此无尽的一行或一百万行都无法拖住周期。测试会在菜单的每条路由上拒绝外来的 Host 或 Origin。

### 新增

- **每个设置都有提示框**：将指针移到设置上、用键盘聚焦或在触摸屏上长按，就会显示它的作用、范围或取值及默认值、开关打开和关闭时会发生什么，以及是立即生效还是重启后生效；会消耗配额或增加页面的设置（时间段比较、检查更新、墙屏）还会说明你将看到什么以及成本。每个设置的帮助文本都会在八种语言中检查，指向不存在设置的条目会被拒绝。
- **两个防止事物自行增长的守卫**：指南在八种语言中必须有相同的标题和代码块，页面标签页的唯一登记簿会检查每个标签页的按钮、八种语言的名称、帮助主题、AI 指南中的条目、信号表中的行以及在精简版中的位置；未登记的新标签页，或没有关闭版本的缺失项，都会使测试失败。

### 修复

- **哨兵标签页的折叠面板不再相互覆盖绘制**：当折叠的面板占满容器时，唯一展开的面板会被压缩到几个像素，其内容被画在下面的面板之上。现在它保留最小高度，容器改为滚动，适用于所有哨兵标签页。浏览器测试会逐个、全部一起、手动以及交替展开每个哨兵标签页的每个面板，在宽屏和窄屏下比较它们的矩形。

## [2.1.2]

### 修复

- **哨兵标签页中展开的面板现在延伸到其框的底部**：在 CI、协作和安全标签页中，唯一展开的面板在窗口高度的 46 % 处被截断，下方留下一条空白；现在它占满框的其余部分，内容更高时在内部滚动。该规则在无窗口浏览器中以八种语言、宽窄两种尺寸进行测量（`tools/check_unfolded.py`）。
- **点击页眉中的计数器不再让“现在”、警报和其他菜单一直处于被截断状态直到刷新页面**：红色工作流和未签名构建的计数器会连同仓库筛选一起跳转到哨兵，而该筛选会保留在所有标签页上；离开所跳转到的标签页时现在会清除它（筛选标签仍可手动清除），浏览器测试会点击每个计数器、回到“现在”并遍历所有标签页，查找被截断的列表、空白标签页或页面错误。
- **从更新工具启动监视器不再为每次 git 和 gh 调用打开一个控制台窗口**：更新后启动的进程没有控制台，因此它运行的每条命令都会打开一个可见的控制台。现在它以其子进程共享的隐藏控制台启动，账户监督进程的子进程也一样；测试会读取所有启动进程的位置，并拒绝分离标志。

### 新增

- **更新工具现在是监视器的一个菜单（系统 > 更新，完整版）**：页面显示已安装的版本和检查发现的版本（设置 `updates.check`：关闭或监视器离线时，不会向 GitHub 请求任何内容），点击“查找版本”会列出已发布的版本及其说明，并在一个说明将发生什么的确认之后更新到最新版或所选版本：zip 的 SHA-256 与 SHA256SUMS 的对照、先做的副本（含其文件夹）、配置迁移和重启。更新在单独的进程中运行：监视器自行停止，应用更新，监视器重新启动，页面重新连接；若新版本无法启动，则恢复并启动之前的版本。“回到上一个版本”反向做同样的事。只有在运行监视器的计算机上的管理员才能应用；同一时间只有一个更新；每一步都写入操作日志；Lite 版、容器中和服务管理器下不提供。路由为 `/api/updates/status`、`progress`、`history`、`check`、`plan`、`apply` 和 `rollback`；独立的 `tools/monitor_updater.py` 仍作为监视器无法启动时的回退途径，并共享同一份代码。
- **更新工具新增两个选项**：`--handover` 等待启动它的监视器停止，应用更新，再启动监视器（启动失败则恢复并启动之前的版本）；`--status-file` 把进度写入页面读取的 JSON 文件，重启后同样可读。
- **交付哨兵和供应链哨兵有了各自的标签页**：与 CI、协作和安全哨兵一样，各自在菜单的哨兵组中有入口（`#sentinel-delivery` 和 `#sentinel-supply`），有一个列出每个仓库未解决发现、其周期状态和无法读取内容的面板、显示错误数的徽标、帮助主题以及八种语言的文本。
- **每日趋势有了自己的菜单入口，并适应其框架**：哨兵摘要中的小曲线移到了自己的标签页（`#sentinel-trend`，从摘要中的按钮打开，摘要只保留它自己的面板），每条曲线和数字现在都会适应其框架的宽度，而不是溢出或被截断，在手机和壁挂屏幕上也一样。
- **时段对比（设置 `compare.enabled`，默认关闭）**：把当前时段与上一时段（7 天、30 天或任意范围，一年前的同一日期，或自定义基准）对比，并可按监控器所在时区只看工作日或周末。它并列比较失败运行占比、耗时中位数、告警解决时间、平均评分及其覆盖率，每项都带有变化和方向；数据不足或没有基准的数值会显示 `insufficient_data` 或 `baseline_unavailable`，而不是显示 0 或 100。它是只读的，由评分的台账和快照生成，不向 GitHub 请求任何内容。开启期间，评分台账会保留两个长度为 `compare.default_window_days` 的时段。指南见 COMPARE.md。
- **两个时段之间发生了什么变化**：变差或变好的仓库、开始或不再失败的工作流，以及已打开的告警，体现在 `GET /api/compare`（支持 `format=ndjson` 和 `format=csv`）、`monitor_cli.py compare`（某项无法对比时退出码为 4，使用 `--fail-on` 且有数值变差时为 5）以及“图表”标签页的一个部分中。
- **定期报告中的简短对比（设置 `compare.include_in_report`，默认关闭）**：每个数值一行，与上一时段对比，支持两种格式和八种语言。
- **用 AI 设置监视器的提示词(`docs/AI_SETUP_PROMPT.md`,八种语言)**:粘贴到 AI 助手中的文本,它在核对 SHA-256 后从 zip 安装监视器,一次一个问题地询问账户、仓库、哨兵、配额、通知、屏幕和 AI,只写入模板中存在的设置,让所有机密远离聊天和文件,让一切会改变事物的功能保持关闭,并在最后说明安装会是什么样子以及如何更新或移除。它随软件包一同发布,测试会检查它提到的每个设置都真实存在。

### 变更

- **多个进程写入的文件由操作系统的锁保护**：操作日志、AI 通道的状态和订阅源、通知账本、分发器、经验教训、计划任务、报告状态和账户存储使用的锁会在其持有者死亡时由系统释放；被终止的进程不再会让其中一个一直锁着，直到标记文件变旧；旧的标记文件如果还在，也不再起作用。

## [2.1.1]

### 修复

- **发布关卡按 unittest 自己给出的数量接受绿色运行**:一次完整绿色运行的记录包含 unittest 报告已运行的测试数量(当某个测试在一行中间输出时,报告的行数可能更少),关卡现在把这个数字与总数比较,而不是与它能读到的行数比较,因此完整的运行不会再因为几行未计数而被拒绝。
- **时钟被调回后,webhook 覆盖状态不再一直显示为在线**:标记时间超前于时钟的事件不被采信,因此指示器会回到等待状态,而不是在时钟追上之前一直显示在线,依赖在线 webhook 的节省机制也不会因此保持开启。

### 新增

- **`make_release.py --progress` 显示测试套件的进度**:使用该选项后,常规套件和干净安装的套件每运行 250 个测试就输出一行,因此关卡不再沉默将近一个小时。
- **供应链哨兵（仅 Complete，默认关闭）**：第四个哨兵不向 GitHub 写入任何内容，通过 API（无需克隆）读取每个仓库的工作流文件（SHA 未变的文件不会再次读取），并为每个仓库和每种信号生成一条警报：`actions.supply.unpinned`（未固定到完整提交的 `uses:`）、`actions.supply.mutable_ref`（跟随 `@main` 或 `@master`）、`actions.supply.permissions_wide`（`write-all`）、`actions.supply.permissions_missing`（没有 `permissions:` 块）和 `actions.supply.pr_target_checkout`（检出拉取请求的 `pull_request_target`）。发现来自工作流检查器（没有自己的规则；查找密钥的规则保持关闭，因此密钥的值从不被读取），每个信号都有开关和级别，工作流无法读取的仓库会列在 `unavailable` 下且绝不算作干净，重启或首次查看不会通知任何内容。成本由 `max_repos_per_tick`、`max_calls_per_tick` 和 `min_rate_remaining` 限定。新增：“哨兵”子标签中的 `sentinels.supply.*` 设置、`GET /api/sentinel/supply`、`alerts --sentinel supply`、`supply_*` 指标，以及 8 种语言的 `docs/SENTINEL_SUPPLY.md`。

- **交付哨兵（仅 Complete，默认关闭）**：第五个哨兵不向 GitHub 写入任何内容，通过 API（无需克隆）读取每个仓库最新的发布、最新的标签、CHANGELOG 以及你指定的版本文件，并按仓库和信号各发出一条警报：`release.unreleased_pending`（`[Unreleased]` 下有条目等待，而最新已发布版本已超过 `unreleased_days` 天）、`release.tag_without_release`（比最新发布更新的版本标签没有自己的发布）、`release.release_without_notes`（最新发布的说明为空）、`release.version_mismatch`（你列出的版本文件与 CHANGELOG 声明的版本不一致）、`release.ecosystem_drift`（仓库固定的版本低于共享契约提供方的最新发布，从就绪度设置的固定表中读取）以及 `release.assets_missing`（最新发布缺少 `expected_assets` 某个模式对应的文件）。每个信号都有自己的开关和级别，关闭的信号不会被读取，无法读取的仓库列在 `unavailable` 下而绝不算作正常，重启或首次查看不会宣告任何内容，评分也不使用它。成本由 `max_repos_per_tick`、`max_calls_per_tick` 和 `min_rate_remaining` 限定。新增：哨兵子页签中的 `sentinels.delivery.*` 设置、事件 `delivery_new` 和 `delivery_fixed`（发布类别，不在任何默认列表中）、`GET /api/sentinel/delivery`、`alerts --sentinel delivery`、指标 `delivery_*`，以及 8 种语言的 `docs/SENTINEL_DELIVERY.md`。

### 变更

- **README 的截图显示当前版本**：页面、墙面屏幕和控制台工具的所有图片都用虚构数据重新拍摄。新图片展示分组菜单、CI 与协作哨兵、车队、报告、使用另一个主题的整个页面，以及带有组织标志、使用其他主题并可自动轮换的墙面屏幕；“关于”面板更高，以便看到运行与备份卡片。
- **要求不显示首次启动向导的地址也会隐藏关于 AI 预算的一次性提示**，因此在干净浏览器中拍摄的图片能显示处于静止状态的页面。
- **doctor 会以红色提示传入 webhook 没有密钥**:接收端已开启但未设置共享密钥时,每次投递都会以 `401` 被拒绝,doctor 现在报告失败而不是警告;webhook 指南说明密钥是唯一的屏障。
- **发布关卡会把 zip 中每个文件的内容与提交比较**:除了名称和干净的工作树之外,每个成员还会与提交所版本化的文件比较(换行符除外),因此与提交不同的文件无法被打包。

## [2.1.0]

### 新增

- **安装的完整备份，经过验证并可选加密（`backup create`）**：`monitor_cli.py backup create` 写出一个备份包（格式 2），包含每个账户的转储、已清理的设置和列表，以及带有每个成员大小和 SHA-256 的清单；放到位之前会先验证，第一种格式的备份包仍可验证和恢复。令牌、密钥、密码、任何 `*_env` 变量的值、webhook 密钥、会话以及密钥库的内容绝不会带上：设置先经过白名单，再清除一切看起来像密钥的内容。使用 `ops.backup.encrypt`（或 `--encrypt`）时，备份包用 `ops.backup.key_env` 所指变量中的密钥以 AES-256-GCM 加密；它需要可选库 `cryptography`，没有该库或密钥不足 12 个字符时，备份会被明确拒绝且不写入任何内容。`backup verify`（加 `--deep` 会恢复到临时文件夹）、`backup list` 和 `backup status` 与之配套。
- **按账户或恢复到文件夹，并附清单（`backup restore`）**：恢复会先验证备份包；只要有监视器在其端口上应答就会被拒绝，对已有账户的存储除非加 `--force` 也会被拒绝；设置会被合并（备份包中没有的键绝不会被删除）；可以只恢复一个账户（`--account`）或恢复到空文件夹（`--to-dir`），并写出报告，说明还需要做的事（GitHub 登录、被排除的设置、重启、doctor）。
- **计划备份、状态以及“关于”面板中的卡片（`ops.backup.enabled`）**：默认关闭；开启后，监视器每隔 `ops.backup.interval_hours` 在独立线程中生成一份备份，保留最新的 `ops.backup.keep` 份并记录结果；失败只会被记录，绝不会让监视器停止。`GET /api/ops/status` 和 `POST /api/ops/backup`（管理员，从本机）以及“关于”面板的**运维**卡片用于查看和运行它。`deploy/github-actions-monitor-backup.service` 及其定时器在 systemd 下生成同样的备份，`deploy/compose.yaml` 把备份放在独立的卷中。指南 `docs/OPS.md` 以八种语言说明了全部内容。
- **doctor 检查运维状态，并以不变的退出码退出（`doctor --strict`）**：完整版会检查数据、日志和备份文件夹是否真的能接受文件，正在运行的监视器及其监督进程是否健康，webhook 密钥（只看长度），每个 SQLite 数据库的完整性（只读且有时间上限，默认 `quick_check`），最近一次备份的时间，可用磁盘空间以及 `/metrics`。一切正常时以 `0` 退出，检查失败为 `1`，只有警告且使用 `--strict`（或 `ops.doctor.strict_exit`）为 `3`，无法运行为 `4`。精简版不会运行也不会加载其中任何内容。
- **在你开启之前并不存在的按需清理（`ops.purge.enabled`）**：`POST /api/ops/purge` 和“关于”面板的按钮会立即运行保留期清理；除非另有要求，否则是试运行，并且在没有比 `ops.purge.require_backup_hours` 更新的有效备份时会被拒绝；记录会写入保留期审计和操作日志。
- **单个账户的备份包（`backup create --account`）**：只包含该账户，没有用户、会话，也没有安装的设置或列表；`backup verify` 会检查它只包含该账户，`backup restore` 恢复它时不会触碰目标处的其他账户、用户或文件，仅当该账户在目标处已存在且没有 `--force` 时才会被拒绝。
- **整个产品使用在设置中选定的主题,每个墙面屏幕也可以有自己的主题**:主题(`ui.theme`:自动、浅色、深色或十六种之一)也由监视器保存,因此墙面屏幕和登录页面都会使用它。屏幕默认继承它(`screens.default_theme` 现在是 `inherit`),并可用 `screens.default_theme`、`screens.theme_overview`、`screens.theme_now` 和 `screens.theme_sentinels` 为所有屏幕或单个屏幕固定另一个主题。墙面屏幕不再写入自己的颜色:它们使用页面的调色板,因此十六种主题在那里同样可用。
- **在墙面屏幕上显示组织标志**:在设置中上传(PNG、JPEG、WebP 或 SVG,最大 1 MB;根据文件的前几个字节检查类型,含有脚本、事件处理程序或指向其他文件的链接的 SVG 会被拒绝),保存在数据文件夹中,绝不写入配置。`screens.logo_overview`、`screens.logo_now` 和 `screens.logo_sentinels` 选择显示的屏幕(默认仅总览),`screens.logo_corner` 选择角落(默认右上角),`screens.logo_max_width` 和 `screens.logo_max_height` 选择最大尺寸(默认 160 x 64 像素)。图片按比例缩放且有专属位置,因此绝不会遮挡内容。
- **一个会轮换并跳转到新红色的墙面屏幕(`screens.mode` = rotate)**:不再是三个分开的屏幕,而是一个窗口每隔 `screens.rotate_every_seconds` 秒(默认 20,5 到 300)在总览、此刻和哨兵之间轮换。新的红色会跳到显示它的屏幕(失败的工作流跳到此刻,红色面板跳到哨兵),并停留 `screens.alert_hold_seconds` 秒(默认 30,5 到 600)或直到红色消失,以先到者为准,然后继续轮换;已经显示过的红色在变化或再次出现之前不会再触发跳转。`?jump=off` 和 `?rotate=0` 可让单个窗口安静下来。默认仍是三个分开的屏幕。
- **总览墙屏显示按分组的车队地图**:在车队的四个方块下方,为车队视图的每个分组(相同的分组方式:按 `fleet.group_by` 的生态系统、标签或状态)显示一条横条,标出其中红色、需要关注、正常和无数据的仓库数量。只显示组名和数字,绝不显示仓库名称,并遵循屏幕的主题和语言。设置 `screens.group_map`(默认开启)。
- **失败的“Dependabot Updates”成为独立警报,Copilot 的活动属于信息**:GitHub 自行执行的依赖更新运行失败时,为每个仓库生成一条中等严重度警报(`ci.dependabot_failed`,开关 `ci.dependabot_alerts`,默认开启);失败的 Copilot 工作流可以成为一条通知(`ci.copilot_activity`,开关 `ci.copilot_alerts`,默认关闭)。两者都不会算作仓库的红灯,并且都可以像其他警报一样静音。
- **本机蜂鸣覆盖页面的各种事件类型,实时连接恢复有了专属提示音**:开启 `sound.server_beep` 后,监视器会为每种类型(新的红灯、连接中断、警告、已解决、安全警报、卡住的运行、评分下降、通知、报告和经验教训)播放各自的模式,使用与页面相同的开关和静音时段,每次最多合并三种。新的提示音(四个上升的音符)会在连接中断后恢复时在页面、墙屏和本机上提醒。设置 `sound.on_live_recovered`(默认开启)。
- **新增更新器：把安装更新到任一已发布版本并迁移其配置（`monitor_updater.py`）**：只用标准库的单个文件，随每个发布版本一同发布（附带 SHA-256），也放在产品中（`tools/monitor_updater.py`），并作为命令 `monitor_cli.py update`。它检测安装、列出 GitHub 上已发布的所有版本、让您选择目标、以演练方式显示您的配置会有哪些变化，并在先备份、校验 SHA-256、安全解压、保留您在启动脚本中的自定义行、失败时自动回退的前提下执行，同时保存历史。可以作为浏览器页面、窗口（Tkinter）或文本菜单打开。迁移注册表（`assets/migrations/`，由 `tools/make_migrations.py` 生成）覆盖从 1.8.1 起的所有发布版本。参见 `docs/UPDATE.md`。

### 变更

- **`tools/backup_storage.py` 写出产品的备份包**：其备份现在就是 `backup create` 的备份包（格式 2，账户数据及已清除机密的设置），并支持 `--account`；第一种格式的备份仍可用它验证和恢复。

### 修复

- **详情面板的状态标签保持在一行**:在哨兵标签页中,“按层详情”每个面板标题里的标签(例如表示需要处理的那个)曾被挤成每行一个字,所有语言都如此,手机上尤其明显。现在它不再收缩,也不会在单词中间折行,并有一项在真实浏览器中的测试在八种语言下以宽窄两种窗口测量它。
- **经由账户监督器转发的 Webhook 对每次投递都返回 400**:当监督器把一次投递转发给某个账户的进程时,由于使用了标准模块却没有导入,该进程无法判断发送者是谁;有效签名、错误签名、缺少签名、重复投递和过大的正文都得到同一个通用响应。现在发送者会像以前一样被读取(监督器的有效密钥给出它报告的地址,其他情况回落到对端),并且有一项测试会检查整个软件包中在函数内使用却未导入的标准模块。

### 安全

- **页面用数据构建的链接通过解析地址来检查,而不是看开头的几个字符**:只有不带用户名和密码的 GitHub https 地址(或你为 GitHub Enterprise 设置的主机,它也可以是 http)才能通过;脚本地址、外观相似的主机、空白、控制字符或反斜杠都会变成空链接。
- **容器指南说明如何打开第一次会话以及有哪些镜像标签**:它曾要求用带访问令牌的地址打开,而自从令牌不再出现在地址里,监视器默认会拒绝这种做法。现在它说明应通过 POST 或访问请求头发送令牌(或为一次访问临时打开该地址再关掉),所引用的标签是本版本的标签。

## [2.0.9]

### 安全

- **访问令牌默认不再出现在地址中(`listen.query_access` 现在默认关闭)**:在网络模式下,带 `?access=` 的地址会打开会话,但令牌会留在历史记录、日志和 `Referer` 中。该设置现在默认关闭,除非你开启它(默认值、示例文件和设置帮助都已说明);会话通过 `POST /api/access`(正文中的令牌)或请求头 `X-Monitor-Access` 打开。自己写过 `listen.query_access` 的安装会保留其值;依赖旧默认值并通过带 `?access=` 的地址打开监视器的,需要开启该设置或改用 `POST /api/access`。环境变量 `MONITOR_QUERY_ACCESS=1` 可为服务开启它。
- **按模式对仓库的静音不再静音非工作流的内容**:只含仓库的模式(`alerts.silences`)曾连带静音该仓库新的安全警报(secret scanning、CodeQL、Dependabot)、红色的必需检查、待签名和发布提醒,且警报标签页不会将其显示为已静音。现在静音只覆盖工作流的红色、已修复、卡住和失败通知,渠道与标签页共用同一份列表,帮助中也已说明。
- **对离开监视器的文本的清理能识别更多真实日志的形式,且不再触碰非机密内容**:现在会清理用双反斜杠书写的 Windows 路径(错误信息和 JSON 的写法)、带 `_PASS` 的名称、`docker login -p`、`sshpass -p`、`curl -u`、`.netrc`、`.pgpass`、`_auth=` 和 `X-Auth`、西班牙语密码、Hugging Face、Docker Hub、Stripe 和 Google OAuth 的令牌、不带 bot 一词的 Telegram 令牌、地址中带 @ 的密码、查询中的会话标识、ntfy 主题、伪装的邮箱以及仅存在于私有网络的名称;只有在文本还原为纯文本后才可见的机密,即使文本中还有诱饵也会被清理。看起来像机密的计数、状态和名称(`max_tokens`、`secret_scanning: disabled`、`cache-key`、名为 secret-santa 的仓库、四个数字的版本)不再被替换,清理后相同的两个键会同时保留。
- **携带机密的请求头不再跟随重定向**:非本机服务器上的 ntfy 主题令牌和本地钩子不再把它转发到重定向指向的地址;重定向以错误结束。
- **会检查 Webhook 投递可以携带的内容**:状态、结论和日期必须具有 GitHub 使用的形式,工作流、分支、作业和步骤的名称会压缩为一行并像离开监视器的任何文本一样清理。不是日期的日期不再能让周期停止。
- **互联网上的提供商只有在你允许时才会进入备用链**:除非其名称在 `ai.fallback_cloud_allowed`(默认为空)中,否则失败构建的文本不再发送给 `ai.fallback` 中写的云提供商。每当链从本机转到互联网,都会写入操作日志并发送通知。
- **私有地址上 AI 提供商的 https 地址需要专门的开关**(`ai.allow_private_targets`,默认关闭):指向私有、局域网或元数据地址的地址会被拒绝,主机前带用户或 @ 的地址同样被拒绝。如果你使用自己网络中的服务器,请打开该开关。
- **Webhook 载荷必须指明其所有者,其链接必须指向其仓库**:不含仓库全名的投递不再被采信,进入通知、实时列表和数据流的运行链接只有在位于该所有者和仓库之下时才保留。

### 新增

- **`logs.failed_step.max_per_minute` 限制失败步骤日志每分钟从 GitHub 读取的不同运行数**(默认 10):连续请求大量运行不再为所有运行消耗你的配额。
- **按模式的静音可以失效,并由一个信号列出需要决定的静音**(`alerts.silences_expire_days`,默认 0 = 永不):设为数字后,静音在审核日期之后该天数后停止生效;已发出的提醒保存在状态文件中,重启不会重复;静音信号会列出已过期限、已失效或没有日期的静音。
- **老化为不活跃的红色会列在“现在”视图中**: 在设定的天数(默认 30 天)内,决定性事件都没有触及的红色仍会从红色列表中移出,但现在会有一行显示其数量,并可从中展开列表(仓库、工作流和失败日期),因此失败不会无声无息地消失。
- **不活跃的工作流也会列在“现在”视图中**: 失败后在 ci.inactive_days 所设天数(默认 90 天)内没有运行的工作流不再计为红色,第二行会显示其数量并可展开列表,位于老化红色那一行旁边。
- **页面会一次性告知 AI 预算已变化**:首次打开此版本时,一条提示栏会说明每日上限和模型上限现在也计入主动通知;点击"知道了"后隐藏,页面会记住。
- **左侧菜单有了带标题的分组，团队和哨兵各自拆分为独立条目**：五个分组（监视、哨兵、团队、报告与学习、系统；可折叠并会被记住）对每个标签页分类；*团队*变为团队健康（`#team-health`）、车队（`#fleet`）和定时报告（`#team-reports`），*哨兵*标签页变为概览（`#sentinel`）加上 CI 哨兵（`#sentinel-ci`，含面板 A1 至 A13）、协作哨兵（`#sentinel-collab`）和安全哨兵（`#sentinel-security`）各一个条目。某个哨兵的条目只在该哨兵开启时出现在菜单中（`sentinel.enabled`、`sentinels.collab.enabled`、`sentinels.security.enabled`）；其地址仍会打开一个说明它已关闭的面板，并打开设置中的对应开关；每个徽标只统计自己哨兵的警报。旧地址（`#team`、`#sent`、`#team/fleet`、`?view=team`）仍会打开正确的面板，每个标签页打开自己的帮助主题，`ui.screen1_tabs` 列出新的标签页（`fleet`、`trep`、`sci`、`scol`、`ssec`）。
- **每种事件一种声音,带主题、按类型的开关和静音时段**:新的红色、严重或安全警报、卡住的构建或队列、评分下降、连接丢失、警告、已解决、新报告、新经验和普通通知,各有自己的音型,由 Web Audio API 生成(无音频文件,任何内容都不会离开浏览器),凭听觉就能知道发生了什么。设置 `sound.on_warning`、`sound.on_resolved`、`sound.on_report`、`sound.on_lesson`、`sound.on_sentinel`、`sound.on_stuck`、`sound.on_score_drop` 和 `sound.on_info` 加入原有的两个(默认全部开启),`sound.theme` 选择 `classic` 或 `soft` 音色,`sound.quiet_enabled` 配合 `sound.quiet_from_hour` 和 `sound.quiet_to_hour` 设定静音时段(默认关闭)。在“设置”的“界面”中,每种类型有一个按钮,以当前音量和主题播放。墙面屏幕使用相同的声音(窗口是否发声仍由 `screens.sound` 和 `?sound=on` 决定)。`docs/SOUNDS.md` 提供八种语言的声音表。
- **来自 Slack 和 Discord 的只读命令(设置 `chatops.enabled`,默认关闭)**:允许的频道中的人可以向监视器询问 `help`、`status`、`alerts`、`red`、`queue` 或 `score`,并得到只有自己能看到、不含提及、且在 `chatops.links` 开启(默认)时除了按原样显示的名称旁的仓库地址外不含链接的简短回复(`chatops.show_repo_names` 默认为 `all`,私有仓库的名称也会到达名单所允许的每个频道和用户;`public` 和 `none` 会隐藏它们)。命令列表是封闭的(`chatops.allowed_words` 只能缩小它),每条命令只读取监视器已经拥有的内容:没有任何命令会向 GitHub 写入、执行操作、更改设置或读取密钥。`POST /api/chatops/slack` 校验 Slack 的 `v0` 签名(时间和正文的 HMAC-SHA256,最多五分钟前,密钥只放在 `chatops.slack.signing_secret_env` 所指的环境变量中);`POST /api/chatops/discord` 用 `chatops.discord.public_key_env` 所指的公钥校验交互的 Ed25519 签名;两者都会应答平台的验证挑战,绝不两次接受同一签名,拒绝超过 16 KB 的正文,并按地址、用户、频道和分钟统计请求。名单 `chatops.allowed_teams`、`chatops.allowed_channels` 和 `chatops.allowed_users` 是必需的(都为空时不会执行任何命令),所有外部文本都会被清理、截断和转义,每条命令都会在操作日志中留下一行,只记录聊天的 ID,绝不记录文本。设置的 Webhook 标签页中的一个区块、八种语言的指南(`docs/CHATOPS.md`),以及使用 RFC 8032 向量的测试。

### 变更

- **钩子中级联的行按字段重新构建**,交给 AI 的工作流名称与自身警报一样截断为 40 个字符:有写权限的任何人所写的名称不能再通过跟随者列表携带一句话。
- **内置 AI 更严格地清理回答,并更少相信提供商对自身的说法**:回答中会移除任何有效方案的链接、HTML 标签和终端控制码;提供商声称消耗的令牌最多按一千万计(错误不再让 AI 关闭一整天);每个模型的数据表最多保留 500 行,手动填写数值的行优先,并拒绝不是主机名或预设的提供商标签。
- **`ai.base_url` 拒绝在主机前带有用户或 @ 的地址**,因此密钥不能保存在地址里,也不能藏在看起来像另一个主机的地址后面。
- **审核日期的提醒包含在新安装的事件中**(`notify.events`),AI 限额的帮助也说明主动通知有自己的每小时上限。Webhook 指南现在如实描述代码的行为:运行保留其事件类型、仓库在下一个周期再次读取、保存哪些名称,以及网络模式下读取实时事件列表需要访问令牌。
- **同时计入主动通知的单一 AI 预算**:每日总数(`ai.daily_limit`)以及模型的上限和成本现在包含主动通知的调用,主动通知仍保留自己的每小时上限。以前主动通知不在这些上限内,所以这会改变消耗:你的设置不会被改写,两个上限中更严格的那个会拦住调用。如果主动通知需要的超过你的每日总数,请调高总数。
- **按数量汇总的摘要只计入渠道会发送的内容,重启后仍保留,并送达请求了其所含内容的渠道**:没有渠道会发送的事件不再计入阈值,被扣留的内容保存在状态文件中,卡住构建的摘要会送到只请求卡住构建的渠道。
- **无人修复的失败会继续影响评分,未关闭的协作警报按已打开的时间计入**: 一直为红色的工作流只会在七天内拉低恢复部分,失败的运行离开窗口后该部分又回到 100。现在会统计红色处于窗口内的那一段(前一个窗口已统计它自己的那一段,任何一天都不会被统计两次),并且只要红色规则仍显示,账本就会保留无人修复的工作流的最后一次失败。窗口结束时仍未关闭的协作哨兵警报按其已打开的时间计入,因此放着不处理的警报会拉低协作部分,而不是让它没有数据。更新后分数可能比以前低;评分指南对此有说明。
- **在默认分支上失败的链式部署会显示为红色**: workflow_run 和 repository_dispatch 事件的运行现在计入仓库的红色,但仅限默认分支,并且来自 fork 时不计入。以前,链接在 CI 之后、在 main 上失败的部署不会出现在任何列表中。指定事件的设置(ci.red_events)仍然起决定作用,其默认值及八种语言的帮助都已说明。
- **读取 API 的冻结契约深入到列表的元素**:`/api/data` 之前被冻结为 `data: any`,因此重命名运行列表或去掉仓库、配额后仍是 `CONTRACT=PASS`;现在契约描述了 `/api/data` 的运行、仓库、配额和数字,`/api/alerts` 中警报的元素(列表可写成 `[{...}]`,检查其前三个元素),以及此前位于两个列表之外的可读路由 `/api/auth/me`。警报字段的类型也被冻结,而不仅是名称。`docs/API.md` 及其翻译已说明。

### 修复

- **在 Windows 上两个进程同时写入时，监视器的共享文件现在可以再次保存**：临时文件有自己的名称，被拒绝的替换会重试，因此 AI 配额的计数不再丢失。
- **墙面屏幕跟随主页面所选的语言**：不带 `?lang=` 打开的屏幕会以监视器的语言（英语）显示，即使用户已在主页面选择了其他语言。现在的顺序是地址中的 `?lang=`，然后是主页面在同一浏览器中保存的语言（语言不同的屏幕会在绘制之前重新加载一次，并保留 `?rotate=` 和其他参数），然后是监视器的语言；设置中的“打开屏幕”链接带有页面的 `?lang=`。这适用于八种语言，并带有日文和中文的字体以及每种语言用于时间、日期和数字的区域设置。测试会在保存了偏好的情况下检查八种语言下的三个屏幕、`?lang=` 优先，以及不会残留英文文本；屏幕指南说明了语言如何决定。
- **两个请求同时到来时内置 AI 不再卡死**:同时进行两次解释,或在读取预算时进行解释,会以相反顺序获取链上的两把锁并互相等待,直到重启监视器。现在锁总是以相同顺序获取,且检查模型预算与计数其调用是同一步,因此并发请求不能突破模型的上限。
- **迟到的 Webhook 投递不再把红色运行变绿或把绿色运行变红**:投递曾把周期已读取的运行替换成事件类型为 "webhook" 的运行,而红色规则不计入该类型,因此颜色会翻转一个周期,渠道会发出错误的"已修复"和错误的"新红色"。现在运行保留 GitHub 发送的事件类型,对已以相同结果结束的运行的投递不改变任何内容,改变其状态的投递会合并到运行而不是替换它。
- **失败步骤的日志为单行、只保留很短时间且不重复失败**:带换行的步骤名曾能在简报中开出一行形似警报的内容;终端链接和标题会从日志中移除;未能读取日志的回答保留五分钟(而非永久),失败保留一分钟,工作流的统计最多保留 200 个步骤名称。
- **按数量汇总的摘要在最近一小时有余量时立即通知,并采用其中最严重的级别**:被扣留的新红色可能等待长达一天,摘要的级别始终是警告,因此只要求严重通知的人永远收不到。
- **实时视图会显示最后一个事件的工作流名称**:最后一个事件的名称此前总是为空。
- **多个进程可以共享 AI 的存储而不会突破其上限**:现在存储在操作系统锁(Windows 和 Linux)之下读取、修改和写入,进程终止时由系统自己释放该锁,因此两个进程不再各自产生自己的配额;现有的锁文件救援机制保持不变。
- **失败作业分组的键会被截断并清理**:当作业没有平台或括号时,整个作业名曾是其分组的键,既没有上限也没有清理;现在它是最多 80 个字符的一行,并像其余内容一样清理。
- **仓库的分支、fork 标记、最后一次推送和 PR 现在会送达每个仓库,而不只是第一个**: 运行记录进入内存之后(从第一个周期起),仓库列表格中被重复使用的一个变量,使除第一个以外的所有仓库都丢失了哨兵所知道的信息。没有自有 CI 的 fork 没有被识别为 fork,因此它们继承的定时任务进入了评分,闲置 fork 的数字只显示 1;默认分支不是 main 或 master 的红色 CI 可能不会出现在未解决故障列表和团队健康中。评分现在会排除全部闲置 fork(而不只是页面显示的 200 个)。
- **团队和机群的健康状况统计周期内的全部运行,而不只是账户最新的 600 条**: 有 250 个活跃仓库时,其中 215 个显示“无数据”,因为它们的运行放不进页面收到的截取结果。现在按仓库在截取之前统计运行数、最近 24 小时的失败数和本周的运行数,活跃账户中健康的仓库也会显示为健康。
- **工作流仍在运行的红色不再老化为“不活跃”**: 早于设定天数(默认 30 天)的失败,即使同一工作流之后的运行被取消、正在进行或等待批准,也会被隐藏。现在只有自失败以来完全没有再运行的工作流才会老化;自然周期长于该天数的工作流(总是失败的每月定时任务)会先等待其通常间隔的两倍。
- **修复 Windows 和文件损坏时存储层的遗留问题**: 报告状态在读取失败后不再被写回(它会丢掉其他账户及其记忆);存在但无法理解的文档(损坏的一个字节、被截断的文件)会先保存为 .damaged 副本,再写入新文档,而不是被擦除;所有者仍在运行的锁不会在短时间后被抢走,被拒绝的删除也不再让等待的进程不看期限地空转;当读取方打开文件导致轮转被拒绝时,操作日志和访问审计仍会记录操作(失败的轮转会被计数)。
- **打包关卡证明 zip 就是提交本身**: 除了把文件名与已版本化的文件比较之外,现在当已版本化的文件被编辑但未提交(它会带着改动一起发布)、两个名称仅大小写不同(在 Windows 和 macOS 上一个会覆盖另一个)、以及文件夹中的 git 不响应时都会失败,而不是默不作声地跳过比较(用 --allow-no-git 可以从解压后的 zip 构建;此时关卡会提示没有进行比较)。
- **四条小规则现在按其文字说明执行**: 为 CI 为红色的仓库预留的请求预算份额属于整小时,不再在每个周期重新发放(每小时 100 的预算在十二个红色仓库下大约花掉了 880);等待自有且已关机的 runner 的运行仍然是故障,而不会在七天后变成幽灵运行;按页读取的列表在后面的页面失败时会保留已读取的页面,并说明列表被截断(240 个作业的运行之前一个作业都不显示);在读取权限之后运行过的工作流不再被当作手动停用而搁置。
- **未修复的失败会继续计入成功率,批量读取会保留它没有提到的内容**: 评分不再仅仅因为工作流又红了一天而上升(失败的运行虽已离开窗口,但失败仍在);可选的批量读取(network.graphql_checks)也不会再抹掉在最新提交上没有运行的红色工作流(定时任务、带路径过滤的工作流)。
- **`lint_workflows.py --remote` 不再把读不到的仓库当作干净**:不存在的仓库(或令牌看不到的)、SSO 未授权的组织、无网络,或不是 `OWNER/REPO` 的名称,过去都以 `0 finding(s)` 和退出码 0 结束,因此用它写的推送前步骤在一个工作流都没看的情况下就通过了。现在这些情况退出码为 2(有发现时仍为 1),原因输出到标准错误(不存在的仓库与没有工作流的仓库会被区分),`.` 和 `..` 不再被接受为所有者或仓库名称。`--json` 的形状不变。`docs/CONSOLE_TOOLS.md` 及其翻译已说明。
- **变老的红色和不活跃的工作流不再不可见**:失败的工作流在 `ci.inactive_days` 内没有运行,或其失败早于 `ci.red_age_days` 时,会从红色列表中消失,页面上却没有任何提示,尽管这两个设置的帮助都承诺会显示为不活跃。“当前”标签页现在有一行显示不再计为红色的失败工作流数量,另一行显示休眠和不活跃的仓库(支持八种语言)。
- **`--demo` 现在遵守冻结的契约，并且不再向其所在文件夹写入任何内容**:`python bin/actions_monitor.py --demo` 在发现的回答中缺少契约的一个键,`tools/` 里的演示在更新的回答中缺少两个键,评分也没有给出账户,因此 `tools/check_api_contract.py` 对它们全都给出 `CONTRACT=FAIL`,没人能判断问题是否出在自己这边。演示还会把 `ai/LESSONS.md`(以及经验教训簿)写入它运行的文件夹;现在使用 `--demo` 时不再写入任何内容。现在有测试在两个版本中对演示检查契约。
- **修正了四份与代码行为不符的指南**:Webhook 检查清单要求从 GitHub 重新发送测试事件并在 `?view=live` 中查找(重新发送会被当作重复而忽略,`ping` 也不包含仓库名,所以永远不会列出;该步骤现在改为运行一个工作流);墙屏指南说关闭 `screens.enabled` 后所有地址返回 404(`/screen/1` 到 `/screen/3` 就是页面本身,仍然可用,精简版也提供墙屏页面);精简版指南为完整版列出六个标签页(实际有十个),并说 AI 路径返回 404(供 AI 工具使用的数据流通道在两个版本中都会响应);纯文本 README 和两个启动脚本要求 Python 3.10,而监视器需要 3.11(也缺少日文提示)。测试现在会读取标签页列表、精简版路径和启动脚本。
- **shell 启动脚本在仓库中保留可执行位,zip 也不再取决于构建它的机器**:六个 `.sh` 和 `.command` 启动脚本此前在版本库中没有可执行位,因此在 Linux 或 macOS 上克隆后,README 给出的命令会提示 "Permission denied"。zip 此前沿用构建者检出的换行符(Windows 下所有文本为 CRLF,Linux 下为 LF,同一提交会得到两个不同的 zip);现在文本一律以 LF 打包,Windows 启动脚本以 CRLF 打包。
- **命令行和“关于”窗口的五个小问题**:启用 `session_guard`(默认)的监视器总是拒绝(403)`credential reload` 和 `credential replace`,因为该命令从未请求页面所请求的一次性令牌(现在会请求);通过管道传入带 BOM 的令牌(PowerShell 会添加)会被读错;对另一台计算机使用明文 http 的警告出现在密码发送之后(现在在之前);使用 `--ca-file` 时,本机地址会经过环境中的代理;被拒绝的 HTTPS 证书被报告为“无法连接”(现在会说明证书不受信任并指向 `--ca-file`)。“关于”窗口显示的版本与其他文本一样会被转义。
- **README 中的测试数现在是测试方法的真实数量,指南不再把函数当作设置,浏览器请求图标也不再收到 404**:README 之前只统计基类名为 TestCase 的测试类,漏掉了继承自自有基类的类(3314 个方法对 2912;运行时输出的数字更大,因为每个子类都会运行继承的方法);`docs/LESSONS.md` 曾把导入失败簿写得像一个设置;页面和墙屏唯一的 404 `/favicon.ico` 现在返回 204。测试会检查指南中提到的所有设置以及文件中的 Webhook 密钥。
- **有多个账户并启用团队模式时,`/api/v1/` 下的路由需要与不带前缀的同一路由相同的角色**:监督进程按带前缀的路径判断,因此查看者可通过带版本的 API 读取只有管理员才能读的内容(监视器的暴露情况、令牌状态、操作日志)。现在会先去掉前缀再检查角色,响应仍保留 `X-API-Version` 头。
- **可见性未被读取的仓库在墙面屏幕上按私有处理**:使用手写的仓库列表或较旧的 `gh` 时,所有仓库都被当作公开,`screens.show_repo_names` 会显示私有仓库的名称。现在每隔 `discover_refresh_seconds` 用一次账户列表读取可见性,读不到的按私有显示。
- **被截获的 Webhook 投递不能通过更换投递 ID 来重放,垃圾请求也不能耗尽真实投递的配额**:除了 ID,已签名的请求体也会被记住;签名无法验证的请求与能验证的请求分开计数(`webhook.max_bad_per_minute`,每个地址每分钟 120 个,所有模式下都适用,可信代理之后按其后的地址计),能验证的为每分钟 120 个。
- **账户进程只持有自己的配置所指定的 Webhook 密钥**:其他账户和主配置的密钥以前会留在它的环境中,以及 `gh` 和它启动的每个程序的环境中。
- **密钥所用的变量不能再是系统变量或 GitHub 登录变量**:`webhook.secret_env` 和 `listen.token_env` 会拒绝 PATH、GH_TOKEN 之类的名称,Webhook 密钥的名称只在进程启动时读取一次。
- **有多个账户时,监督进程会保护每个响应不被嵌入框架**,与账户进程的做法一致。
- **含有非 ASCII 字符的游标得到普通的 400,带版本 API 的其他任何失败都会返回 500 的错误信封(`api.server_error`)**,而不再是断开连接并在控制台输出堆栈。
- **带版本的 API 先要求访问令牌,再说明自己是否开启,游标也属于请求它的人**:没有凭据的访客在开关关闭时从 `/api/v1/` 得到 404,开启时得到 401,而同一个游标对任何人和账户都有效。现在先检查令牌,某个人或账户的游标会被拒绝给其他人。
- **监督进程会以签名方式告诉每个账户的进程是谁在以什么角色操作**:有多个账户时账户并不知道角色,所以操作日志忽略了 `audit_log.maintainers_can_read`,`GET /api/v1/me` 还说团队模式已关闭。该上下文用该进程的密钥签名,30 秒内有效且只对该账户有效;没有它,仅凭用户名不会被采信。
- **重启后仍会记住 Webhook 投递,可以拒绝过旧的事件,正确请求的配额成为设置**:记忆是有上限的私有文件(`webhook.persist_deliveries`,默认开启),`webhook.reject_stale`(默认关闭)会对比 `webhook.replay_seconds` 更早的已签名工作流事件只应答并忽略,`webhook.max_verified_per_minute`(120)是一个地址签名正确请求的配额。
- **每个指定含密钥变量的设置只指定自己的变量**:AI 密钥、通知渠道、Webhook 和访问令牌都会拒绝系统变量、GitHub 登录变量以及属于其他设置的密钥,且一个名称只能写在一个设置里。
- **墙面屏幕上隐藏名称的编号遵循名称的 HMAC**:使用保存在数据文件夹私有文件中的本次安装密钥(绝不放在配置里),只为被隐藏的仓库编号,编号无法透露仓库在其他仓库中的位置。
- **操作日志可以成为操作的前提条件**:开启 `audit_log.required`(默认关闭)后,需要记录的操作在无法写入日志期间会被以 503 拒绝;设置保持开放,以便修复。
- **操作日志保留你选择数量的轮转文件**:`audit_log.keep_generations`(默认 5,范围 1 到 20)把旧的部分保存为 `.1`、`.2` 等,哈希链会跨所有文件校验。
- **GitHub 不返回的 fork 不再卡住对原仓库的跟踪**:返回为空的 fork(已删除、已改名或不可见)或失败的请求,以前会永远排在每一轮的最前面。现在它们被记为已尝试,面板将其计为不可读,下一轮会处理后面的 fork。
- **隐藏工作流查找的批量方式对每个仓库只读一次列表**:列表中没有某个工作流时,每一轮都会再次请求而始终无法解决。现在在保留响应的时间内每个仓库只读一次列表,列表没有带来的内容在同一轮中逐个查询。
- **失败的哨兵查询会先等待再重试**:隐藏的工作流、红色运行的作业和仓库的权限会在 5 分钟、30 分钟、6 小时后再次查询,读不到权限的仓库会排到队尾,不再妨碍其他仓库被读取。
- **运行列表的每小时预算(`sampling.api_budget_per_hour`)按请求计数**:对默认分支的第二次查看(`sampling.default_branch_probe`)在选择一个周期要读的仓库时计入,重新运行的时长(`ci.rerun_timing`)是一小时内的一次请求,预算用完后不再发出。
- **Webhook 指南如实描述代码的行为**:事件之后仓库仍会在下一个周期重新读取,工作流、分支和作业的名称作为第三方文本保留,实时事件可由能打开页面的人读取。
- **响应 GET 的路由不再读取 GitHub**:运行器、账户的组织、更新通知和每个来源的配额都由周期读取,路由只显示已读取的内容(`/api/runners` 和配额状态在首次读取之前会显示为待定)。
- **重新运行时长的请求对每个仓库的每次读取都有各自的配额**:此前三次请求的计数由一个周期的各线程共用。
- **对 fork 原仓库的跟踪在重启后保留最近一小时的请求,并说明遍历一次需要多久**:超过两次读取的间隔时,面板会说明跟踪永远不会休息。
- **上次运行遗留的含有 Apprise 服务地址的文件夹会在监视器启动时删除**,而不是等到可能数小时后的首次发送。
- **“叮叮”不再对大部分事件保持沉默**:以前它只看红色的工作流,因此其他哨兵的警报、报告和经验从不发声;浏览器阻止的声音会永远丢失,因为那条警报已被视为看过;所有事件共用一个三十秒的间隔,会吞掉紧随第一个之后到来的第二种事件;墙面窗口每次蜂鸣都新建一个音频上下文,而浏览器会一直阻止它,直到有人点击。现在会监视列表中的每条警报、报告的每个新发现和每条新经验;浏览器阻止的声音会等待(最多十分钟),并在第一次点击、页面回到前台或每两秒一次的下一次检查时播放;每种类型有自己的间隔,最多三个声音的一轮(最严重的先响)避免堆叠;墙面屏幕则保留一个音频上下文和一个小队列。
- **传入 Webhook 的速率限制按访问者计数，而不是按反向代理计数**：每分钟 120 次请求的限制原先按连接地址计数，而在代理之后该地址始终是代理本身，并且在校验签名之前就计数，因此一个访问者发送未签名请求，就会让其他所有人的已签名投递返回 429。现在改为按受信任代理添加到转发头中的地址计数（没有受信任代理时按连接本身计数）。
- **从容器环境中去掉代理变量会重新关闭对应设置**：空的 `MONITOR_TRUSTED_PROXY`、`MONITOR_TRUSTED_PROXIES`、`MONITOR_SECURE_COOKIE`、`MONITOR_PROXY_PUBLIC_HOST` 或 `MONITOR_ALLOWED_HOSTS` 原先会把上一次启动的值留在配置文件里，导致已不再声明的代理仍然被信任。现在空变量会清除对应的键。
- **不带访问令牌的请求仍会被拒绝，但不再算作错误尝试**：不带令牌加载页面十次，就会把访问者的地址锁定五分钟。现在只有提交了但不正确的令牌才会计数。
- **指南和 Compose 文件把登录文件交给容器的用户**：模式为 600 且属于创建者的文件，容器的用户 10001 无法读取，账户因此一直处于盲态，原因为 missing。现在命令也会把该文件交给那个用户。
- **监督进程的健康应答包含冻结契约的键，契约还标出只有监视器所在电脑才能使用的路由**：容器中的 `/api/health` 缺少版本、运行时间、周期和凭据，契约工具对容器会失败。现在工具从网络发起查询时，会接受被标记为仅限本机的路由所返回的拒绝。
- **哨兵一次 tick 的调用对其所有阶段是同一个计数,持续读取失败的仓库会被搁置**:此前 tick 的上限分别应用于每个阶段(上限 70 的 tick 中发出 150 次调用),服务器返回错误的仓库在每个周期都会被重新读取。现在各阶段共享计数,这类仓库会被搁置 30 秒(翻倍,最多 10 分钟)。

## [2.0.8]

### 安全

- **入站 Webhook 的共享密钥只通过环境传递（`webhook.secret_env`，默认 `MONITOR_WEBHOOK_SECRET`）**：它以前是 `actions_monitor.json` 中的一段文本，备份、复制的配置或共享屏幕都可能泄露它。接收器现在从 `webhook.secret_env` 指定的环境变量读取（或从该变量名加 `_FILE` 指定的文件读取，容器就是这样交付 secret 的），监视器读取后会把它从自己的环境中移除，使其启动的程序不会继承它，而写在文件中的密钥会被忽略。旧方式可用 `webhook.allow_config_secret` 临时保留以便迁移（仅限文件，默认关闭），使用期间实时视图会发出警告。设置标签页只显示变量名和密钥是否已定义，绝不显示密钥。

- **模型默认识别的其他公司付费 runner 现在包含 `codspeed`**（`runners.model.thirdparty_labels`）：公开仓库用它做基准测试，其作业以前被当成无人认识的 runner。你自己写的列表不会被改动。

### 修复

- **文档不再声称 macOS 在 CI 中运行**: README 及其七种译文曾说测试在 CI 的三个系统上运行,并且 Linux 和 macOS 在 CI 中测试;由于 CI 目前只在 Ubuntu 和 Windows 上测试(macOS 以后会重新启用),文档现已如实说明。

- **从未被推送过的 fork 不算“最近推送”**：fork 在创建时会继承上游的推送日期（在被测量的账户中，722 个 fork 里有 693 个的推送日期早于自己的创建时间），所以哨兵把每个新 fork 都当成账户中最活跃的仓库并按热仓库处理。现在只要 fork 的推送日期不晚于其创建时间，就会被忽略。

## [2.0.5]

### 新增

- **fork 只有在有自有 CI 时才会进入卫生检查、工作流 lint 和评分（设置 `ci.forks_need_own_ci` 和 `ci.fork_own_ci_days`，默认 90 天）**：fork 复制的是别人项目的文件、规则集、发布和工作流，所以评判它的卫生状况（没有规则集、没有发布、上游的许可证）或工作流文件，其实是在评判上游；收集 fork 的账户（所测账户中 727 个仓库里有 722 个，没有一个有规则集、保护或发布）曾显示数百条警告和一个由噪声构成的评分。现在 fork 在窗口内有过自己的推送、拉取请求、手动或合并队列运行时才算数；继承来的定时任务、另一个 fork 的拉取请求以及 GitHub 为自身创建的运行都不算。当它的运行列表已满且没有回溯到窗口开始时，fork 仍保留在内，因为自己的运行可能藏在更早的位置。被排除的 fork 会单独统计（哨兵的 `a6.forks_idle`、页眉数字 `forks_idle`、卫生面板中的一枚徽章），它们的运行不计入评分；关闭开关后，所有 fork 都像以前一样被评判。
- **休眠和不活跃的仓库成为独立的状态，既不是绿色也不是红色（设置 `ci.dormant_repos`）**：收集 fork 的账户有数百个从未运行过任何内容的仓库（所测账户中 727 个里有 724 个），而最新运行已是几个月前的仓库同样不算健康。每个被监视的仓库现在是活跃、休眠（从未运行过任何自身内容，运行列表完整且为空）、不活跃（最新运行早于 `ci.inactive_days`）或未知（读取失败或列表被截断）之一。它们在页眉数字（`dormant`、`inactive_repos`）、监视器数据和评分快照（`activity`）中单独统计，评分徽章的提示会说明数量。评分只根据实际运行的内容计算。GitHub 为自身创建的工作流不是仓库的运行。
- **排队多日的运行被区分为幽灵队列（设置 `ci.stuck.ghost_enabled`，天数在 `ci.stuck.ghost_days`，默认 7）**：在公开仓库中，GitHub 会让运行在队列里停留数周甚至数月（已关闭的拉取请求、请求不存在的运行器的作业；最长 280 天，在 10 个繁忙仓库中有 8 个）。这些运行会抬高排队数量，被报告为卡住的构建，并影响所有从队列学到的限值。首次尝试且超过限值的排队运行现在既不算排队也不算卡住：它离开“现在”列表和各项计数，一行文字说明有多少个，哨兵把它们单独列出，并为每个仓库给出一条信息通知（`ci.ghost_queue`），绝不是错误。开关默认开启；关闭后，所有排队运行与以前一样处理。

### 变更

- **无人处理的红色在 30 天后过期并变为不活跃（设置 `ci.red_ages` 和 `ci.red_age_days`）**：fork 会复制所关注项目的夜间任务，该任务因缺少密钥每晚失败，所有者关闭了工作流，而最后一次运行永远停留在“失败”，所以该仓库永远是红色（在所测的两个案例中，42 次运行中有 41 次失败，27 次中有 26 次失败，最后一次接近一年前）。此前只有在 `ci.inactive_days`（90）天内完全没有运行的工作流才不再是红色，仍在运行拉取请求的工作流则永远不会。现在，失败的运行早于 `ci.red_age_days` 天（默认 30）并且没有任何更新的决定性事件的运行，就会离开红色列表并列为不活跃；各行会说明它已过期。开关默认开启；关闭后，红色会一直保持，直到工作流再次变绿。
- **默认分支的卫生检查现在默认判断生效的规则（`sentinel.hygiene.ruleset_mode` 现在是 `effective`）**：以前只有存在名称完全相同（`protect-main`）的有效规则集时，分支才算受保护，而所研究的账户没有一个这样用（所研究的账户没有一个这样命名规则集，96 个仓库中还有 32 个以经典方式保护分支）。现在默认情况下，只要 GitHub 报告了针对分支的规则或保护，无论它叫什么名字，该分支都算受保护。该检查会读取分支及其规则，每次更新卫生检查时每个仓库多两次请求。设为 `name` 可恢复旧规则。要求旧规则的配置档案仍保持旧规则。

### 修复

- **默认分支的保护现在根据所有公开来源判断，而不只是规则集的规则**：在所研究的 96 个公开仓库中，有 32 个的默认分支采用经典方式保护，而 `rules/branches` 看不到这一点，因此空的规则列表曾被读成“没有保护”。在 `effective` 模式下，分支的回答现在还给出其经典的 `protection`（是否启用，以及状态检查的执行有多严格，无需管理员权限即可读取），并合并三个来源；只有当它们都回答了且没有一个提供保护时，分支才算未受保护，没有得到的回答（超时、读取被拒绝、字段缺失）仍是“无法评估”。卫生面板的每一行会说明是什么保护了分支（`protection`：ruleset、classic、both 或 none）。
- **GitHub 为自身创建的工作流既不是红色 CI，也不是文件**：路径以 `dynamic/` 开头的条目（Dependabot 更新、依赖关系图、默认的 CodeQL、Copilot 的审查和代理）在所研究的 96 个公开仓库中有 20 个一直失败，并被当作仓库的工作流计入（红色、已放弃、“已禁用”）。监视器只保留运行的文件名，所以对路径的判断从未匹配；现在读取运行时会记住完整路径。这些工作流不再决定分支的颜色，不计入待检查的工作流，也不会出现在手动或因不活跃而禁用的工作流中。失败的 Dependabot 更新会作为警告单独列出，其余（Copilot、CodeQL、依赖关系图）作为信息，位于哨兵的 `a2.services` 和页眉数字 `services_failing` 中。
- **对被隐藏工作流的查找（A2）现在遵守与红色判定其余部分相同的来源规则**：当运行样本已满时，会单独查询某个工作流的最后一次运行，而这个回答过去会接受分支上的任何运行，包括来自 fork 的拉取请求、议题或评论的运行（GitHub 的 `exclude_pull_requests` 过滤器不会去掉它们，因为 fork 的运行没有关联的拉取请求）。现在回答只保留事件属于 `ci.red_events` 且不来自 fork 的运行，GitHub 为自身创建的运行不再被当作仓库的工作流，事件也会随回答一起保存。测试使用在七个公开仓库上测得的形态。
- **提问在页面内进行，因此全屏时也能看到**：页面的五个确认（切换模式、运行 AI 建议的命令、GitHub 操作、运行本地工作流、删除用户）原先使用浏览器的对话框，全屏时不会绘制（必须按 Esc 才能看到）并且会阻塞页面。现在它们使用页面自己的单一对话框（`askConfirm`），带有确定和取消、Esc 和 Tab，危险操作时焦点先落在取消上，关闭后焦点回到原处。若原生的 `confirm`、`alert` 或 `prompt` 再次出现，测试会失败；浏览器中的测试用鼠标和键盘提问并回答。

## [2.0.4]

### 新增

- **为监控器的 AI 提供按任务选择的模型、后备链和按模型的预算**(在设置中写明之前全部关闭,且只在你指定的提供商之间选择): `ai.tasks.build.model`(`codeql`、`report`、`diagnose` 和 `alert` 同理,各自有自己的提供商和限制)让另一个模型回答这类问题;`ai.fallback` 列出主模型失败时(任何错误、密钥被拒、模型不存在、配额错误,或设置了 `ai.fallback_after_seconds` 时的缓慢响应)或已从目录中消失时按顺序尝试的模型,`ai.fallback_max_attempts` 限制整条链;每个模型每天的调用数(`ai.model_daily_limit`)以及每个模型和总计的估算成本(`ai.model_cost_limit_daily`、`ai.cost_limit_daily`,仅在价格已知时)是 `ai.daily_limit` 之外的预算,预算用尽的模型会被跳过,绝不会被超出。主模型的第一次失败会连同原因写入日志和摘要。未设置任何内容时,仍像以前一样由唯一的通用模型回答。
- **警报、报告和经验教训成为左侧菜单的三个条目**: 可选的报告和来自失败的经验教训原本是“警报”标签页底部的小节;现在各有独立条目,带有自己的图标、徽标(报告:有发现的仓库和被阻止的发布;经验教训:现在适用的)和地址(`#reports`、`#lessons`,也可用 `?view=reports` 和 `?view=lessons`)。没有任何内容丢失或重复,旧地址(`#alerts`、`#alerts/reports`、`#al/lessons`)会打开正确的面板,没有启用任何报告的面板会说明这一点而不是消失,墙屏可在 `ui.screen1_tabs`(`rep`、`les`)中列出新标签页。指南用八种语言写明了新的菜单条目。

### 修复

- **“本标签页帮助”在每个标签页都会打开当前标签页的主题**：标签页到主题的映射缺少警报和团队标签页，并把仓库和历史标签页指向帮助的第一个主题（“GitHub Actions Monitor”）。现在它是一张单一的表（`TAB_TOPICS`），侧边菜单的每个标签页都有一项；若某个标签页没有主题或主题不存在，测试会失败。浏览器中的测试会遍历所有标签页并点击该按钮。
- **历史标签页不再累积其计数**：表格工具只在排序或列变化时重绘，而“显示 N 中的 200 条”却在每次刷新时被追加到工具中，导致列列表旁边增长出数千份副本。现在计数是一个会被替换或移除的单一元素。测试在浏览器中打开页面，多次绘制表格（刷新、筛选、所有列、一种排序），并检查只有一个计数和一个提示。

## [2.0.3]

### 安全

- **页面用数据构建的每个链接都经过地址过滤器**: 指向最近一次运行、仓库、看板、issue、未解决的失败和更新提示的链接只会打开 GitHub 或所配置主机的 `https` 地址,其他一律变为无效的 `#`。

### 新增

- **墙面屏幕默认关闭**：在设置中开启之前 `screens.enabled` 保持关闭，因此全新安装时 `/screen/overview`、`/screen/now` 和 `/screen/sentinels` 返回 404。
- **墙面屏幕：地址、设置和数据**（三个页面是 `/screen/overview`、`/screen/now` 和 `/screen/sentinels`，供无人操作的显示器或电视使用）：它们只通过 `/api/screens/data` 读取监视器已有的数据（字段固定的列表：绝不包含 GitHub、链接、提交标题、作业名称或用户名），可用 `screens.enabled` 关闭（此时所有地址返回 404），私有仓库的名称遵循 `screens.show_repo_names`（默认隐藏），失败每秒闪烁不到两次并在 `screens.blink_calm_minutes` 后平静下来（`screens.blink`），窗口只能通过地址变得更安静（`?blink=off`；`?sound=on` 仅在 `screens.sound` 允许时有效），或用 `?monitor`、`?theme`、`?density`、`?refresh`、`?lang`、`?scale` 和 `?rotate` 设置。另有 `screens.default_theme`、`screens.default_density`、`screens.refresh_seconds`、`screens.rotate_seconds`、`screens.burn_in_protection` 和 `screens.night_dim`（docs/SCREENS.md）。
- **面向数百个仓库的舰队视图**:团队标签页新增一个部分,对仓库分组(按生态、标签、状态或不分组)、排序(按风险、名称、最近运行或状态),并逐页绘制,因此拥有 250 个仓库的账户也能保持页面轻快。标签是仓库名的模式(`fleet.labels`,例如 `team-*=backend`),也可用来区分组织或团队;`fleet.saved_filters` 保存现成的筛选;`fleet.group_by`、`fleet.sort` 和 `fleet.page_size` 设定默认值。它读取 `GET /api/team/fleet`(只读,与团队排名相同的健康数据);上方的排名不变。
- **运行器类型、其队列与成本、失控工作流以及宕机的自托管运行器**:开启 `runners.model.enabled` 后,作业的标签(`runs-on`)用于区分 GitHub 托管、大型、第三方付费和自托管运行器(通过 `runners.model.thirdparty_labels`、`runners.model.large_labels` 和 `runners.model.self_labels` 自定义分类)。设置 > 高级会显示按类型的队列、按类型的分钟数与成本(第三方的一分钟仅在设置了 `runners.model.thirdparty_usd_per_minute` 时才计价,GitHub 从不对其计费)、过去一小时至少启动 `runners.model.runaway_runs_per_hour` 次的工作流,以及等待自托管运行器达到 `runners.model.queue_warn_minutes` 分钟或更久的作业及原因(没有在线运行器具有其标签、所有匹配的运行器都在忙,或空闲运行器不接取)。两种警告都是警报(`runners.model.alerts`,级别为 `runners.model.alert_level`,默认 `warning`);只读、默认关闭,并通过 `GET /api/runners/model` 每周期读取 `runners.model.jobs_per_cycle` 次运行。开启 `finops.jobs_per_cycle` 时,第三方运行器上的作业不再按 GitHub 托管计价。
- **在触发任何运行之前列出手动触发工作流的输入**:批量调度器的 `plan --inputs` 会在每个目标下显示其工作流要求的输入(名称、类型、必填或可选、默认值、选择项的选项和说明),从本地克隆 `origin/main` 中的工作流文件读取。不会触发或发送任何内容;`--json` 会为每一行添加 `inputs` 列表(无法读取时为 `null`)。指南新增一节列出已知限制:运行抽样、私有和免费仓库中保持 `unknown` 的套餐、每个监视器一个所有者以及合并队列。
- **如实的运行列表覆盖范围**:仓库表新增一列“样本回溯范围”,说明每个仓库的运行列表向过去回溯了多久。已满但回溯时间少于 `sampling.min_coverage_minutes`(默认 30,0 为关闭)的列表会标记为“覆盖不足”,而不是看起来完整;比请求数量短的列表为“完整”;GitHub 停止计数的总数(2,500 或 40,000)显示为“至少”。表格上方的提示会统计覆盖不足的仓库数;`GET /api/data` 的 `sampling` 块带有同样的数字。
- **对默认分支再看一次**(`sampling.default_branch_probe`,默认关闭):当仓库的运行列表已满时,再发出一次请求,获取默认分支的推送(不含拉取请求),使决定 main 是否为红色的运行不会被拉取请求和定时任务挤出。仅由第二次查看找到的运行,不会让列表被视为已满。
- **每小时请求预算**(`sampling.api_budget_per_hour`,0 = 无):超出后先读取有红色工作流的仓库,其余等待下一小时,页面会说明有多少个在等待。页面还会显示仓库数量和间隔所需的每小时请求数(达到 3,500 或设置了预算时),让大账户在用完额度之前得到提醒。
- **长列表读到末尾,被截断时会说明**:仓库的工作流(148 个或 348 个都是真实情况)、运行的作业(超过 100 个的矩阵)以及仓库的未关闭议题和拉取请求,现在只要上一页是满的就逐页读取,最多 `pagination.workflow_pages`、`pagination.job_pages` 和 `pagination.collab_pages` 页(每页 100 条)。一页放得下的仓库,请求数与以前相同。仍有遗漏时页面会显示“M 个中看到 N 个”:作业显示在运行下方,工作流显示在仓库的卫生检查中,团队标签页页脚则显示未关闭项多于已读数量的仓库,以及搜索 API 结果超过 1000 条的账户。
- **使用合成账户的负载测试**:250 个仓库和 1,250 个工作流,无需网络,测量一个周期的请求数、周期和团队健康的耗时、所保存数据的内存,以及 A2 查询所需的请求数;界限设得较宽,负载较高的电脑也能通过。
- **Renovate 与 Dependabot 同等对待，检查器区分自有 action 与第三方 action**：`renovate` 的拉取请求在 A4 中作为依赖更新列出（`sentinel.dependency_bots` 指定账户），带有 Renovate 配置的仓库不再被报告为缺少更新机器人。`lint.own_owners` 和 `lint.unpinned_own` 会把未固定的 action 标为自有或第三方，并可降低或隐藏自有的；三条默认关闭的可选规则分别发现没有 `timeout-minutes` 的作业（`lint.rules.no_timeout`）、`secrets: inherit`（`lint.rules.secrets_inherit`）和跟随 `@main` 的自有 action（`lint.rules.own_action_main`）。
- **机器人与人分开统计**：开启 `sentinel.bots_apart` 后，GitHub 自己标为机器人的账户（Bot 类型，而非按名字猜测）的拉取请求在 A4 中单独计数（`other_bots`），并不计入对等待人处理的旧拉取请求的检查；运行记录现在带有 `actor_bot`。默认值不改变任何行为。
- **配置档案**：设置 > 基本 以及首次启动向导的第三步提供三组现成的设置（所有者或团队、开源组织、独立开发者），一键设定卫生检查、fork 与已归档仓库、检查器、发布文件检查以及机器人单独统计；这些值与保存按钮走同一条经过校验的路径，选择之前不会有任何变化，`GET /api/settings` 以 `presets` 列出它们。大型账户的做法见新指南 `docs/LARGE_ACCOUNTS.md`。
- **面向 AI 的技能不提任何助手名称,按工具类型说明如何连接,并带有监控器的版本**: 新的参考文档和指南《连接 AI 工具》中的表格说明哪种方式适合哪种工具;`GET /api/skills` 返回 `monitor_version`。
- **AI 提供商的模型改为读取、核对和度量,而不是盲目输入**: 设置 > 外部 AI 用一次只读请求加载提供商的列表,核对名称,保存每个模型的上下文窗口、价格和工具,并可用合成故障测试模型;`monitor_cli.py ai models`、`ai test` 和 `ai doctor` 也能做同样的事。
- **同一根因的红色只报一次,红色运行会说明哪些作业失败**(默认关闭): `ci.group.reusable` 把调用同一可复用工作流的红色工作流合并为一行和一条通知;`ci.failed_jobs` 按平台列出失败的作业。
- **长时间的构建不会仅因为长就算“卡住”,卡住的运行会说明等待原因**: `ci.stuck` 可以从各工作流自身的运行中学习其上限,按工作流或运行器标签设定上限,并给等待运行器的运行单独的上限;全部默认关闭。
- **告警很多时减少噪音**(`alerts` 块,默认关闭): 带原因和复查日期、按模式匹配的永久静默,偶尔失败的服务专用类别,同一提交只发一条通知,以及定期摘要。
- **工作流检查器和表面检查无需克隆仓库即可工作**: `lint.source` 设为 `auto` 时通过 contents API 读取 `.github/workflows`,`sparse` 使用稀疏克隆;默认仍是 `clone`;A13 面板会说明读取了什么以及哪些无法评估。
- **`lint_workflows.py --remote OWNER/REPO`** 通过 `gh` 从 GitHub 读取仓库的工作流文件,无需克隆,读不到时会说明原因。
- **面向组织和大型账户的帮助**: `--doctor` 会说明组织读取为空的原因,并按配额估算每小时的读取量;新的指南 `ORGANIZATIONS.md` 给出最小令牌和 SSO 步骤。
- **合并队列**: 默认分支合并队列中失败的运行是独立的红色,显示为“(merge queue)”,队列下一次绿色运行后自动清除。
- **维护分支**: `ci.extra_branches` 接受 `release-*` 这类模式的额外分支,其最近一次运行也会计入;这类分支的红色会带上分支名。

### 变更

- **仓库的测试暂时不再在 macOS 上运行**：macOS 任务已从 CI 工作流中移除（每个拉取请求、每次推送到 main、每个标签以及夜间运行都在 Ubuntu 和 Windows 上测试），工作流中注明将在以后重新支持 macOS。监视器本身没有任何变化。
- **A2 用一次请求解决许多工作流**:需要查询的工作流不少于 `sentinel.a2_resolve_batch_min`(默认 2;0 = 逐个)的仓库,只请求一次其默认分支(不含拉取请求)最新已完成的运行,其中出现的工作流一并解决(最多 `sentinel.a2_resolve_batch_pages` 页,每页 100 条);列表中没有的仍像以前一样逐个查询,因此拥有 100 个以上工作流的仓库只需几个周期即可收敛,而不是每个周期四个。
- **fork 和已归档仓库可通过设置选择，在维护的 fork 绝不丢失**：`discovery.skip_archived`（默认开启）决定是否监视已归档仓库；`discovery.fork_policy` 可排除 fork（`skip`），或只保留有自己 CI 的 fork（`skip_unless_ci`：已启用的工作流且在 `discovery.fork_ci_days` 内有运行），`auto` 对组织账户把时间窗口加倍，账户类型每天读取一次；`discovery.fork_checks_per_pass` 限制为此花费的请求数。默认值（`show`）不改变任何行为。
- **发布文件检查可适应项目**：`sentinel.surface.checks.release_assets.require_sha256` 和 `.require_signature` 不再要求校验和或签名文件，`.allow_empty` 接受没有文件的发布（向包注册表发布的项目），`sentinel.surface.checks.tag_vs_version.prefixes` 会把 `cli-v1.2.0` 这样的标签与清单比较，`.prerelease_ok` 把日期版本号同一天的测试版视为同一版本；`sentinel.require_verified_signature` 原本就可关闭。默认值与以前要求相同。
- **数千个仓库时团队健康也很快**:运行、红色工作流、进行中的运行和警报只按仓库分组一次,因此团队健康请求不再为每个仓库遍历全部数据(2,000 个仓库曾耗时约八秒);单个仓库的健康只构建它自己的视图。
- **API 的冻结形状深入一层**: 读取响应中嵌套对象的键、未知仓库错误的 `code` 以及哨兵响应的外层结构都属于契约;检查工具会遍历嵌套对象。
- **默认分支上的红色只有在仓库自身造成时才计入**: 只有 `push`、`schedule`、`workflow_dispatch` 和 `merge_group` 事件的运行起决定作用(`ci.red_events`),来自复刻的拉取请求运行从不起作用(`ci.count_fork_runs`)。
- **等待批准的运行是独立状态,既不是红色也不是排队**: `action_required` 和被环境保护暂扣的作业不再使工作流变红;“现在”标签页显示单独的“等待批准”一行。
- **被弃用的工作流是“不活跃”,而不是永远红色**: 最近一次运行失败且已 `ci.inactive_days` 天(默认 90)未运行的工作流会离开红色列表。
- **只响应 issue、评论或标签的工作流不算红色 CI**: 通过它们的事件加以区分(`ci.automation_counts`,默认关闭);每个红色行都会说明工作流的类型。
- **发布关卡会把 zip 与受版本控制的文件对照**: zip 必须恰好包含仓库在产品文件夹中受版本控制的文件;受版本控制却不会被打包的文件,或多出来的文件,都会阻止发布。
- **卫生检查(A6)不再假定某一位所有者的惯例**: 规则集名称成为设置项(`sentinel.hygiene.ruleset_names`),默认分支可按生效的规则判断,可跳过某项检查,令牌无法得知的内容显示为“无法评估”;默认值保持旧规则。

### 修复

- **就绪度标签的分组会说明为何没有数字，完全没有工作流的仓库不再拉低其覆盖率**：克隆中没有工作流文件且没有运行的仓库属于“不适用”：它不计入所在组的覆盖率（五个仓库中两个是新建的空仓库，则按其余三个衡量），并在提示和表格中单独列出。仍低于 `sentinel.readiness.min_coverage` 的组会显示“数据不足”字样（不再是无声的“?”），提示中说明有数据的仓库数量与最低值相比如何，以及哪些仓库缺少数据。默认最低值不变。
- **账户评分会说明校准持续多久以及缺少什么**：校准期间，标签显示 `score.calibrating_hours` 还剩多少，附带进度条以及数字出现的日期和时间（新增 `data_quality.calibrating_hours`）；“数据不足”会说明哪项条件未满足（运行数或覆盖率），`GET /api/score` 带有 `missing_detail`，给出某部分不计入的原因（其哨兵已关闭、尚未完成首次扫描及已读取的仓库数、读取太少、数据源无法读取，或数据已就绪等待下一次计算）。
- **最近 24 小时的圆环只从一个来源计数，不再显示负数**：中心的总数和图例中的三个数字（成功、失败、已取消或其他）均来自服务器（新增 `figures.done24`），总和始终一致；以前总数是按页面收到的运行列表（只包含最新的运行）计算的，“已取消或其他”会变成负数。负数或非数字的值按 0 绘制；如果服务器没有发送总数，则三个数字都按列表计数，卡片会说明这是样本。各仓库的成功率在其列表为样本时也会给出同样的说明。
- **时钟被调回不再使评分、清理和定时报告停止**:保存在未来的时刻(没有电池时钟、以旧日期启动的电脑,或被手动校正的时钟)不再被相信;该任务立即到期并写入正确的时刻,而不是等上几天直到旧时钟追上。
- 现在能找到作业超过 30 个的运行中失败的那个作业:AI 通知、助手和批处理工具读取的作业列表原来在 30 处被截断,现在在 100 处截断(仍是同一次请求)。
- **读不出来的评分账本绝不会被覆盖**: 账本存在但重试后仍无法读取时,每小时的处理什么也不做,并把问题记入健康状态;保留最后一个完好的账本。
- **报告计划的边界情况**: 秋季重复的那个小时不再产生两份报告,监控器停止超过八天而欠下的月报或年报仍会写出,第二种格式写不出的报告不会留下第一种格式的文件。
- **操作日志也记录在 GitHub 和本机上确认的事情**: 重新运行、取消、触发和合并,使用 `act` 的运行,令牌的变更,发现,经验教训,报告,登录变更以及 AI 的操作;每个 POST 路由要么被记录,要么列为豁免,否则测试会失败。
- **多个进程写同一个文件在 Windows 上又能正常工作**: 锁文件的所有者会重试约一秒来删除它,不足一秒的锁文件不会被打开读取;事件流、操作日志和报告的写入方在负载下不再失败。
- **已死亡写入方留下的锁文件会被立即接管**: 锁里记录进程号;该进程不存在时,下一个写入方立即接管并记录(无法确定时按文件年龄判断,可用 `MONITOR_LOCK_STALE` 调整)。
- **重新运行的工作流的时长和排队时间不再荒谬**: 按最后一次尝试(`run_attempt`)计算;超过一次运行最长 35 天的时长留空;`ci.rerun_timing`(默认关闭)会向 GitHub 询问真实时长。
- **批准之后的一次尝试不算“不稳定”**: 需要批准后通过的运行,以及来自复刻的拉取请求运行,不再计为不稳定的工作流。

## [2.0.2]

### 安全

- **AI 可读取的一切都经过同一个清理器**:内置助手发给提供商的文本、每条告警的仓库、工作流、链接和结论、`GET /api/ai/state`、`GET /api/ai/alerts`、`GET /api/ai/brief?fmt=json`、订阅源文件、其状态文件以及钩子的正文,现在都经过同一个清理器(以前 `DB_PASSWORD=...` 中的密码、地址里的用户和密钥、`sk-` 密钥、令牌、电子邮件地址、IP 地址或主目录都可能外泄)。测试会植入每一种机密,只要其中任何输出里出现就会失败。
- **内置助手保留其密钥并留在本机**:对提供商的调用不再跟随重定向(密钥原本会被送到另一个地址;重定向会作为提供商的响应报告),也不再使用环境中的代理变量,因此像 Ollama 这样的本地服务器真正被直接调用。远程提供商仅在 `network.use_proxy` 时才经过代理。
- **清理器认识更多形式的机密**:PGP 密钥块、命令行中的 `--password 值` 和 `mysql -phunter2`、Cookie、`Authorization: Basic ...`、`ENCRYPTION_KEY=`、`SENTRY_DSN=` 和 `AWS_CREDS=`、带转义引号的值、`password:` 之后的短语、被换行截断的令牌、`sk_live_` 密钥、压缩的 IPv6 地址、网络共享以及 root 的目录;隐藏在编码之后的文本(百分号编码、零宽字符、全角字母)也会被清理,键名表明是机密的键值对(`{"password": ...}`)会被整体替换。它是按模式工作的清理器:指南和技能不再承诺什么都不会漏过。
- **第三方文本是数据,不是指令**:AI 工具的门禁脚本为每条告警复制的那一行,只有在确实是仓库名时才保留仓库名,并把工作流名截短为简短的纯文本;AI 写的经验教训放在内置助手提示词中不可信数据的分隔符之间;陌生人的文本(议题标题)在 Discord 中不会提及任何人,并为 Slack 做转义。
- **Apprise**:带有服务地址的残留文件夹会在首次发送时清扫,地址中的逗号不再将其截断,每个地址都带引号书写。
- **预设文件像设置页面一样接受校验**:只提供列出的字段,地址必须被页面接受,云端预设不能指向本机或私有地址,密钥的变量不能是系统或监视器的变量(`GH_TOKEN`、`PATH`、`MONITOR_*`...);同样的规则适用于设置 `ai.api_key_env`。
- **每个账户的进程不再在环境中保留监督器的密钥和访问令牌**:两者在每个进程(监视器、监督器和账户)一开始就离开环境,早于启动第一个 `gh` 或其他程序,访问令牌用别的名字时也一样。那条承诺向 Linux 进程列表隐藏机密的注释,现在说明了它真实的限度。
- **镜像不再可能带上构建者的数据**:构建上下文排除了旧布局中零散的文件,却没有排除现在存放令牌、用户、会话和设置的 `config/`、`data/`、`logs/` 和 `ai/` 文件夹;它们现在被排除,Dockerfile 的应用阶段也会将其删除,并有测试对照产品的文件夹列表检查这两点。
- **三个带错误令牌的访客不再能在反向代理后面把所有人锁在门外**:整个代理共享的锁只统计到达时没有可用 `X-Forwarded-For` 的请求;带有访客地址的请求只针对该地址计数,共享锁在锁定时间之后结束,并且绝不会拦住携带正确访问令牌的请求。
- **登录所花的时间不再暴露哪些名字是用户**:被锁定的用户与不存在的名字耗费相同的工作量,因此“已锁定”对两者的响应时间相同。
- **`/api/accounts/` 下监督器不过滤的路径与其他路由同样被审查**:只有账户的列表、状态和凭据跳过门禁的账户检查,而账户的凭据会被拒绝给看不到该账户的用户。
- **多个进程写同一个文件时,操作日志保持一条链**:每一行都链接到文件中真正存在的最后一行,在进程间的锁下读取(只读文件末尾),并且当另一个进程删除锁文件时 Windows 返回“拒绝访问”,该锁也会等待。
- **操作日志按账户各用一个文件**:在带多个账户的完整版中,不同账户的进程写入同一个 `audit_actions.jsonl`(一个账户的管理员可以读到另一个账户的行);现在每个账户在自己的文件夹中保存自己的文件,`GET /api/audit-log` 只保留响应账户的行。此前写入的行留在旧的共享文件中,监督器仍会读取它。
- **操作日志的检查也涵盖轮转后的文件**:`chain` 会验证 `audit_actions.jsonl.1` 以及它与当前文件之间的衔接,在某一行断裂时指出分段(`segment`),说明检查了多少个分段(`segments`)以及链是否从第一个环节开始(`complete`)。
- **操作日志不再能被查看者读取,并且记录更多重要内容**:该路由在入口处至少要求维护者角色(管理员,或在启用 `audit_log.maintainers_can_read` 时的维护者,仍在内部决定),关闭日志会写下它自己的最后一行,无法写入的行会被计数并显示(`GET /api/audit-log` 中的 `write_failures`、`last_write_error_at`,以及降级通知),自己密码修改失败的记录留在访问审计中,而不是塞满操作日志。

- **通知事件 `ai_alert`**:来自面板或监视器信号的新真实告警可以到达通知渠道(把 `ai_alert` 加入 `notify.events`;默认关闭)。红色工作流保留其自己的事件 `red_new`。

### 变更

- **评分现在会惩罚未修复的故障**:恢复部分会把窗口结束时仍为红色的工作流按其迄今为红色的时间计入(随红色持续而增长的下限),而不是将其排除。以前,从不修复红色的账户可能比一天内修复的账户得分更高。更新时,有红色工作流的账户请预期较低的数值。`docs/SCORE.md` 用八种语言说明了这一点。

### 修复

- **评分与评分账本**:一次运行的重新运行被计为多一次执行(GitHub 保留 id,所以第一个结论曾永远留着);当没有任何部分有数据时,计算不再除以零(响应是 `insufficient_data`,原因为 `no_data`);当账本丢弃超过 20000 条的运行并涉及当前窗口时,快照会注明(`data_quality.truncated`);`GET /api/score/global` 的平均值排除过期快照(计入 `accounts_stale`),`/metrics` 不为它们导出 `ghamon_score`;评分指南现在用八种语言描述五个部分,并包含 `score.weights.security`。
- **安全哨兵不再把“无法读取”当成“干净”**:当对惩罚有分量的来源(Dependabot、代码扫描、机密)大多对每个仓库都返回 403 或 404 时,级别是 `unknown` 而不是 `ok`,评分的安全部分被排除而不是按 100 计(状态带有 `sources_readable` 和 `sources_total`)。在有告警未关闭时停止响应的来源会把该告警保留一周并标为未读,绝不会宣布它已修复;不输出任何内容的 `gh` 属于读取失败,名称中带斜杠的默认分支会以编码形式请求。
- **少数总是失败的仓库不再让安全哨兵“挨饿”**:读取失败的仓库在下次尝试前依次等待 5 分钟、30 分钟、然后 6 小时,尚未尝试的排在前面,因此账户的其余部分会被查看。
- **哨兵无法查看的仓库不再在团队健康中显示为 OK**:当每个哨兵都处于错误、暂停或降级状态(或全部关闭且一周内没有运行过),安静的仓库为 `unknown`(“未查看”),排名行带有 `not_fully_seen` 以及未能读取它的哨兵名称,合计会统计它们,团队标签页用星号和提示标出该状态。红色工作流或告警仍会使其成为 `warn` 或 `bad`。
- **事件订阅源中一个损坏的字节不再停止通知**:超过 512 KB 后,订阅源会以严格 UTF-8 重新读取以便裁剪,单个无效字节就会引发一个逃逸的错误,订阅源无限增长,每个新事件在到达渠道之前就失败。现在裁剪以容错方式读取,绝不会停止渠道。
- **正在使用的文件在文件存储中不再被读成空**:在 Windows 上,备份、杀毒软件或编辑器可能短暂占用文件;读取者把它当成空文件,下一次保存就写在上面(用户、评分账本记录、评分快照、分析数据)。存在的文件现在会被多次重读,为了修改并保存而读取的一方会以错误停止,而不是覆盖。多个进程向同一个事件订阅源追加时会取进程间的锁,因此在 Windows 上不会丢失或截断任何行。
- **重复运行 `migrate_storage` 不再替换目标中较新的数据**:目标有较新事件或快照的账户会报告为 `target newer`,不写入任何内容即被拒绝,退出码为 1;`--force` 让源获胜。运行时还会打印警告,给出无法复制的事件订阅源中损坏行的数量(源保留它们)。
- **恢复写入任何内容之前,先完整检查备份**:副本中任何位置的无效账户 id 或名称都会使 `verify` 失败,因此恢复不会再在前几个账户已写入后中途停止。
- **超出上限的 MCP 服务器响应仍是有效文档**:会从最长的列表中省略若干行,而不是截断文本,响应注明 `truncated` 以及缺少多少行,健康信号(旧数据、降级的监视器、配额)最后才被去掉。
- **不是数字的数字不再切断连接**:`?since=`、`?limit=` 和 `Last-Event-ID` 只接受数字 0-9(且最多 15 位);其他内容一律使用默认值。
- **计划报告的状态由多个账户安全共享**:每个账户在锁下修改自己的条目,在 Windows 上读取者短暂阻塞的替换会被重试。
- **技能的表格说明哪些调用仅限本机**:该表由服务器使用的同一批列表生成,`/api/ai/failures` 列出其 POST。报告不再带有原始标题:告警标题经过清理器,Markdown 不会自行把地址变成链接。
- **API 契约现在涵盖 `/api/data` 且无法被削减**:提供运行、仓库和配额的路由原本不在冻结的契约中。现在在其中,可读但未冻结的路由连同原因列在 `unfrozen` 下,新的 GET 路由不在任何一个列表时测试会失败,另一个测试把契约与第一个 2.x 版本的契约比较,使路径、键或类型不会在破坏 API 的同一次提交中消失。
- **从团队标签页打开的仓库窗口什么也不显示**:排名行只带名称,页面用空的所有者去查询仓库健康;现在使用页面的所有者。深层链接 `?view=repo&repo=owner/name` 也不再用该仓库填充“现在”标签页的文本过滤器(那会使该标签页为空)。
- **带方括号的工作流、作业或仓库名称不再破坏终端视图**:`test [ubuntu, 3.13]` 被显示为 `test`,`docs [/api]` 使视图以错误结束,名称还可能携带终端的样式或链接。现在两种视图都把名称绘制为纯文本,无法绘制的图片会被跳过,而不是结束视图。
- **Windows 批处理启动器菜单中的空回车会重复上一个选项**:选择 2 后再按一次回车会让整个批处理第二次运行,因为未输入任何内容时 `set /p` 保留旧值。现在每次提问前都会清除该变量,并有测试运行真实的启动器。
- **带 shebang 的脚本在发布的 zip 中是 Windows 换行符**:以 `#!` 开头的 33 个 `.py` 文件(包括 `bin/` 的入口点)在 Windows 上构建 zip 时无法在 Linux 或 macOS 上直接运行。现在 zip 以 LF 携带它们,若有任何一个首行仍有 CR,发布门禁就会失败。

### 新增

- **官方 Docker 镜像与服务模式**：`deploy/Dockerfile` 为多阶段构建（来自其已签名 apt 仓库的 GitHub CLI、不含测试的已编译代码，以及仅含 Python、`gh`、CA 证书和代码的最终镜像，只读且属于 root）。它以用户 10001（从不以 root）运行，带两个卷（`/config` 和 `/data`），以 `tini` 作为 init，健康检查即深度检查。`python -m github_actions_monitor.service` 根据有文档说明的环境变量准备好人在首次启动前手工要做的一切：配置、第一个账户（或用 `MONITOR_ACCOUNTS` 创建多个）、`listen` 和 `auth` 的键，以及只生成一次、以 600 权限保存且从不打印的访问令牌。`MONITOR_CONFIG` 把配置文件放在代码之外。

- **带反向代理的 Compose 与 systemd**：`deploy/compose.yaml`（代码只读、无 capability、登录作为 Docker secret），前面可选 Caddy（`deploy/Caddyfile`；公开域名自动 TLS，私有名称用自有机构，或不用 TLS）、`deploy/.env.example`，以及针对传统安装的 `deploy/github-actions-monitor.service` 及其 env 文件（已加固、失败时重启、启动后检查深度健康、`systemctl reload` 时重新读取凭据文件）。八种语言的指南 `DEPLOYMENT.md` 列出了每个环境变量、作为服务的首次启动、备份、升级以及镜像来源证明的校验。

- **`linux/amd64` 和 `linux/arm64` 镜像发布到 ghcr.io**：工作流 `release-image.yml` 在发布版本时（或手动）构建并发布，每个作业使用最小权限、每个 action 按提交固定、每个作业设时间限制，标签为 `X.Y.Z`、`X.Y` 和 `latest`，并附带来源证明。推送是单独的一步，只有发布版本才会执行：同一个工作流在手动启动且关闭 `push` 时只构建不推送，CI 在每次变更时构建镜像。

- **深度健康检查**：`/api/health?deep=1`（见上），供容器或服务管理器使用的 `python -m github_actions_monitor.cli.healthcheck`（退出码 0、1、2、3），以及可在任何计算机上使用的 `monitor_cli.py health --deep`。GitHub 登录无效的账户会被点名，但不算故障：重启无法修复丢失的登录。

- **GitHub 撤销或让登录过期，只会让该账户失明**：连续两次被拒绝，且拒绝表明登录本身无效（401、`Bad credentials`、令牌过期或被撤销、账户被停用、没有登录）后，该账户失明；其他账户继续运行。页面、`/api/accounts`（`state: blind`）、健康检查和命令行都会说明，严重的系统警报（`system.credential_blind`）只打开一次，渠道只通知一次（`credential_blind`，恢复时为 `credential_back`），账户会继续尝试。仅某一项权限被拒绝（某个仓库的 403）不会让账户失明。以已失效的登录启动的服务不会放弃，而是保持运行并处于失明状态。

- **无需重启任何东西即可替换登录**：端点 `/api/accounts/<id>/credential`（团队模式下需 `admin` 会话；否则为监视器所在的计算机）、`monitor_cli.py credential replace --account ID --new-token-file 文件`（`-` 表示标准输入；令牌绝不会从命令行选项中读取），以及系统支持时的 SIGHUP（每个账户重新读取其凭据文件）。新令牌在保存之前会先向 GitHub 验证，因此 GitHub 拒绝的令牌不会改变任何内容；有效的令牌只保存在该账户的文件夹中（权限 600）并立即使用。`GH_TOKEN_FILE` 指定一个供所有账户使用的登录文件，在启动时和收到 SIGHUP 时读取。令牌绝不会出现在响应、日志、警报或审计中。

- **多账户监督进程以网络模式监听**，与单账户监视器一样：每个请求都带访问令牌（Cookie、请求头或 `/api/access`）、令牌错误后锁定、`Host` 检查、可选的使用您证书的 TLS、本机操作者使用的第二个端口（`listen.local_port`），而决定暴露范围的键、GitHub 登录和对 GitHub 的操作只能来自监视器所在的计算机（账户把来自网络的请求视为远程请求）。

- **页面和工具会说明监视器在哪里监听**：本机、网络或代理之后（`listen.proxy_public_host`、`listen.secure_cookie`、`listen.trusted_proxy`），显示在页面底部栏、`/api/accounts`、`/api/health` 以及 `monitor_cli.py status` 和 `monitor_cli.py accounts` 的前几行。

- **命令行可对另一台计算机上的监视器工作**：`--url` 或 `MONITOR_URL`，用 `--ca-file` 或 `MONITOR_CA_FILE` 信任自有 HTTPS 证书的颁发机构；在团队模式下，用 `--user` 配合 `--password-file`（或 `MONITOR_USER`、`MONITOR_PASSWORD_FILE`）以 Bearer 会话登录（`auth.allow_bearer`）。对于失明的账户，`status` 和 `accounts` 以退出码 3 结束。

- **测试**：CI 中的容器测试会构建镜像，以只读且非 root 方式启动，撤销两个账户之一的登录，并检查只有该账户失明、严重警报打开、深度健康检查保持正常、被拒绝的令牌不改变任何内容、有效令牌无需重启即可让账户恢复，以及 SIGHUP 也能做到；此外，对已撤销登录的每种行为（计数、其他账户、警报、通知、替换、文件、SIGHUP、角色、审计以及绝不出现的令牌）各有一个回归测试。

### 新增

- **存储层**(`src/github_actions_monitor/storage/`):一个 `Storage` 接口(配置、哨兵状态、事件流、分析、小型文档,以及用户、其账户和会话的全局记录),对每种后端都遵守“写入是原子的,损坏的项目按空处理”的规则。第一个后端 `FileStorage` 完全保持原来的 `accounts/<id>/` 布局(以及启动器旁边的扁平安装):同样的文件、同样的名称,通过先刷到磁盘再改名的临时文件写入。`create_storage` 是唯一选择后端的地方;精简版始终使用文件。

- 任何后端都能恢复的存储备份:一个 `.zip`,包含转储和清单(账户数、大小、SHA-256);恢复前先校验副本,并且除非强制,否则拒绝写入已有账户的存储。

- **SQLite 后端**(可选,默认关闭):同样的数据放进数据库,每个账户一个文件(`accounts/<id>/storage.sqlite3`),只有该账户的进程会写它。WAL 日志和等待时间,每次写入都是短事务,带版本的架构迁移与版本号更新在同一个事务中执行(被中断的迁移让数据库保持原样;更新版本的数据库会被拒绝),按时间为账户事件建立索引,中途被终止的进程在下次启动时恢复。迁入数据库的有:事件流、事件流已通报的内容、分析、哨兵状态、静音设置和更新提示;配置仍是 JSON 文件,缓存和日志仍是文件。精简版没有此选项。

- 整个安装共用一个数据库(多个账户和进程使用同一个文件)已经备好并经过测试:WAL、等待时间、两个进程同时运行周期,以及页面通过 HTTP 应答而不必等待写入方。

- `tools/migrate_storage.py` 在文件与 SQLite 之间双向迁移状态:默认试运行;`--apply` 一步复制每个账户,然后比较每一项和每条事件;你的文件绝不会被修改或删除;被中断的运行让每个账户要么完整、要么保持原样,再次运行同一命令即可继续。`tools/backup_storage.py` 为两种后端创建、检查和恢复备份。

- **保留与轮转**(完整版):`retention.events_days`(90)和 `retention.analytics_days`(180)决定事件和分析历史日期的保留时长;`retention.mode` 为 `archive`(默认;旧事件先写入账户 `events/archive/` 中的 `.gz`,再从事件流中移除)或 `delete`;`retention.enabled` 是开关,`retention.interval_hours`(24)决定在刷新结束时多久快速执行一遍。每次清理都会留下一行审计记录(时间、删除和保留的事件数、归档文件、分析天数、错误)。清理绝不会改动配置、哨兵状态、静音设置或没有时间的事件。`retention.events_max_kb`(512,与以往相同)是事件流文件的大小上限。这些设置在“文件夹与文件”标签页;精简版没有。

- `--doctor` 新增两项检查:存储(SQLite 数据库存在、通过完整性检查、架构为当前版本所能理解;只读)和保留(每个账户事件的大小与 `retention.warn_events_mb` 比较,并对没有保留区块却作为服务运行的监视器发出警告)。

- **团队模式：用户、角色与会话**（`src/github_actions_monitor/security/auth.py`、`auth_http.py`、`auth_cli.py`；通过 `auth.enabled` 默认关闭，因此一个人使用时毫无察觉）：第一位管理员（在 `/login` 或控制台创建，只能在运行监视器的电脑上、只能一次）存在后，每个请求都需要会话。角色 `viewer`（只读）、`maintainer`（还可静音、确认、更改工作模式）和 `admin`（还可更改设置、用户以及一切可触及 GitHub 的内容）；无人列出的路由对除 admin 外的所有人关闭。每个用户有可查看的账户：用 `?account=`、`X-Account-Id` 或导出请求其他账户会返回 403。密码以加盐的 scrypt 哈希保存；会话是 HttpOnly、SameSite=Strict（HTTPS 时加 Secure）的 Cookie，每个 POST 都带 CSRF 令牌，或是供脚本和应用使用的 Bearer 令牌（`auth.allow_bearer`）；错误密码达到 `auth.max_failed_logins` 次后用户被锁定，每个地址有请求频率限制，新的密码、角色或状态会结束该用户的会话，并且始终保留一位有效管理员。端点 `/api/auth/login|logout|me|bootstrap|password`、`/api/auth/users` 和 `/api/auth/audit` 以 `{"error", "code"}` 返回错误；`auth_audit.jsonl` 记录登录、锁定、被拒绝的请求和用户变更，不含任何机密。lite 版从不登录，页面的一次性令牌仍然适用，`python -m github_actions_monitor.security.auth_cli` 可找回丢失的管理员密码。七项设置（`auth.*`）及其八种语言的帮助，以及八种语言的 `docs/ADVANCED.md` 一节；`tests/test_auth.py` 在真实服务器上覆盖规则、各类路由的角色、账户之间的范围、Cookie、CSRF、Bearer、锁定和审计。

- 账户监督器按用户过滤：`GET /api/accounts`、`/api/accounts/<id>/status`、账户页面以及所有带 `?account=` 或 `X-Account-Id` 的请求只显示并访问分配给该用户的账户（admin 可看全部），账户的监视器会知道是谁在操作。“警报”标签页的静音现在会记录是谁做的：`GET /api/alerts` 中的 `muted_by` 和静音历史。

- **团队模式的页面显示当前登录的用户**：页眉中的一个框显示名称和角色（文字，而不只是颜色），点开后可修改密码、查看并管理用户和审计（仅管理员）以及退出登录；开启模式但尚无用户时，首次会指向 `/login`。页面发出的每个更改都带有 CSRF 令牌，会话结束时跳转到 `/login`，错误的令牌会被更新并重试一次。在个人模式和 lite 版中，页面不绘制也不发出任何新请求；`tests/test_auth_page.py` 在 Node 中针对假网络运行 `fetch` 的包装器。

### 安全

- **错误令牌的锁定重新起到限制作用(网络模式)**:不是本机且已被锁定的地址,会在判断其令牌之前就被拒绝,无论令牌以何种方式出示(请求头、Cookie、`?access=` 和 `POST /api/access`);此前被锁定的地址仍可继续猜测,正确的令牌依然能进入。本机上的使用者永远不会被锁在自己的监控之外。

- **声明了反向代理后,回环地址不再等同于“本机”**(`listen.proxy_public_host`、`listen.secure_cookie` 或 `listen.trusted_proxy`):忘记转发请求头的代理不能再把互联网上的任何客户端变成所有者。在监控所在电脑前的人使用新增的、只监听 `127.0.0.1` 的第二个端口(`listen.local_port`,0 = 关闭,需要重启,使用同一个访问令牌)。启用 `listen.trusted_proxy` 时,代理所有客户端的错误令牌还会合计计数(为单个地址上限的三倍),因此轮换 `X-Forwarded-For` 无法绕过锁定。

- **反向代理指南**(`DEPLOYMENT.md`,八种语言)给出完整配方:公开的 `Host`、`X-Forwarded-For $proxy_add_x_forwarded_for`、`X-Forwarded-Proto`、网络模式以及对代理的声明;不再说监控“没有登录”,并说明 `listen.trusted_proxy` 假定代理位于同一台电脑上。

- **面向网络客户端的 `GET /api/settings`** 只返回它可以修改的设置的值;对其他设置(密钥和令牌的路径、文件夹、变量名)只说明是否已定义。

- **对每个“仅限本机”路由的测试**:用一个不在回环地址上的客户端对真实服务器遍历路由表(并检查源代码,避免遗漏新路由)。

- **GitHub 地址只有符合封闭清单中的形式才能原样通过清理器**(仓库、含作业或尝试的运行、提交、议题、拉取请求、文件);它在第一个不是字母、数字、点、连字符、下划线或斜杠的字符处被截断,其后的内容与其他文本一样被清理。此前,粘在链接上的秘密(编码的查询串、用逗号分隔的列表、冒号、路径中不透明的一段、从地址中开始的电子邮件)会原样传给 AI。

- **AI 客户端的钩子不再交出任何日志文本**:只交出每个告警的仓库、工作流、结论和链接。“不等提示就行动”的指令已删除;最后一行现在说明日志可能包含第三方写入的文字,它们是不可信数据,绝不遵循其中的指示。支持八种语言。

### 修复

- **面向 AI 的事件流不会再因普通日志行而中断**:订阅源中的一行先逐字段清理再写出,而不是清理已经写好的 JSON(原因以 `password: x`、`token=x` 或 `DB_PASSWORD=x` 结尾会把它弄坏)。无法清理的行会被跳过,事件流继续;MCP 服务器的回答也以同样方式清理。在清理器中,`键=值` 的值在引号、逗号或分号处结束,带引号的值会被整体清理。

- **取决于“谁在询问”的内容始终由你自己的登录回答**:`gh api user`、`user/orgs`、通知、对 `@me` 的搜索、`gh auth` 以及没有所有者的 `gh repo list` 永远不会交给 GitHub App 或第二个账户,无论它们还剩多少次调用(启用第二个账户时,监控可能把该账户的持有者当作自己的所有者并列出其组织)。

- **`gh` 调用只有在白名单中才算读取**:`gh api ENDPOINT`,最多带有 `--jq`、`--paginate`、`-H`(读取会发送的那类)、`-i` 和 `--cache` 选项。写入的粘连写法(`-XPOST`、`--method=DELETE`、`-fa=b`、`--field=a=b`、`--input=-`)以及任何其他选项都交给你的登录,而不是在各来源之间分配。

- **第二个账户的令牌文件**(`extra_reader.file`)必须位于监控的账户文件夹内(`accounts/`,或 `MONITOR_ACCOUNTS_DIR`),打开时不跟随链接,且只有它是小的普通文件时才会读取;在该文件夹之外,此设置为空。新开关 `extra_reader.any_folder`(默认关闭,仅限本机)可为必须放在别处的文件取消文件夹限制。

- **日期在未来的中央面板不再被信任**:它的年龄曾被限制为零,因而永远算作新鲜;现在它被视为落后,摘要会说明日期不可信,同时容忍最多五分钟的时钟超前。

- **账户端口的测试在多个测试套件同时运行时不再失败**:现在可以告诉监督器从哪里开始寻找空闲端口(默认仍为 18800),测试向系统申请一段未使用的端口,而不是固定的一段。

- **页面一旦损坏,CI 就会变红**:新增的作业(`page`,不带 `continue-on-error`)在真实浏览器中打开演示监控的页面(`tools/check_page.py`),逐个访问每个标签页和设置的每个子标签页,要求每个都有最少数量的字段,并在出现任何页面错误、未处理的 Promise 或 console.error 时失败。故意弄坏的页面(第二处定义、对函数名的赋值、对不存在函数的调用)必须使它失败。查找重复定义函数的测试现在还能发现带缩进的声明、带 `async` 的声明以及对函数名的赋值。

- **用于读取的可选 GitHub App**(`github_app.enabled`,默认关闭,带 `app_id`、`key_path` 和可选的 `installation_id`,八种语言):监视器的读取使用 App 的安装令牌,其配额与用户的分开,覆盖的仓库越多越大;JWT(最长十分钟)由 `openssl` 根据密钥路径签名,监视器从不读取、复制、打印或记录密钥;令牌有效一小时,保存在内存中并提前五分钟续期;写入和操作仍使用用户的令牌;若 App 失败或缺少权限,会用用户的令牌重新读取;`GET /api/github-app/status`(仅限本机)显示 App 的名称、安装、已授予的权限和配额,绝不显示密钥或令牌;数据中在 App 配额旁带有用户的配额,doctor 会检查 openssl、密钥文件及其权限。
- **两份新指南,八种语言**:`docs/AI_CONNECTION.md`(连接 AI 工具:它能看到什么、五个通道、逐步操作、安全、故障排除、各版本显示的内容)和 `docs/QUOTA.md`(“更多配额,更少消耗”:配额如何运作、监视器节省配额的所有办法、GitHub App 逐步设置、在工具之间共享配额、不要做什么);两者都从 README 和帮助索引链接,并有测试检查其中引用的每个设置都存在。
- **帮助在每次变更时都会被检查**:缺少八种语言的标签和帮助的设置、没有帮助主题的标签页,或更新日志中提到但帮助和指南里没有的设置或端点,现在都会使测试失败;帮助检查清单在 CONTRIBUTING 和拉取请求模板中。
- **设置中的“配额”标签页**(八种语言,lite 版也有):模式和节省模式数值(`modes.*`)、节省(`network.etag`,与 `cache.etag.enabled` 一起生效的别名)、中央面板、GitHub App 和用于读取的第二个账户集中在一处,按钮可显示每个来源的配额和恢复时间、测试 App 和第二个账户、列出 App 缺少的权限,并应用推荐值或默认值。
- **用于读取的第二个只读账户**(`extra_reader.enabled`、`extra_reader.file`):设置中只保存含细粒度令牌的文件**路径**,监视器在使用时读取,保存在内存中,绝不存储、打印或记录;读取按各来源的剩余调用数在你的登录、App 和第二个账户之间分配,被拒绝的来源排除五分钟并用下一个重试,写入和操作从不使用它。
- **读取的统计**:状态、简报和数据会说明进行了多少次条件调用、其中多少次返回 304(不消耗配额),以及每个来源的配额。
- **谁在消耗配额**:监视器在每个小时窗口内,把整个账户的消耗与自己的调用数比较,并在“配额”标签页、状态和简报中说明其他工具消耗了多少,在它们消耗大部分时给出警告(GitHub 不会说明是哪个工具)。
- **事件流也携带其他信号**:配额用尽、连接中断、数据过期、中央面板滞后以及健康警告,在出现、变化或解决时会成为信息流(以及事件流和钩子)的事件,而不仅限于红色工作流和哨兵标签页的面板。
- **批量分发会记录所找到运行的尝试次数**(批次记录中的 `run_attempt`,来自 `gh run list` 的 `attempt` 字段;`gh` 不提供时为空),并且 AI 工具连接指南和配额指南补充了对第二个只读账户的说明。

### 变更

- **重新设计底部状态栏**:每个项目都是带边框的小标签,连接和配额采用其状态颜色,时钟是带框的大号粗体等宽数字,上方为日期,时区为小字,窄窗口中栏的顺序保持不变。
- **每个框都让文字换行而不是溢出**(磁贴、标签、徽章、单元格、标题、窗口按钮):最近一次读取的时间将时区以小字单独显示,警报行在窄窗口中变为两列,磁贴网格可以缩小到内容以下。
- **同一行的磁贴高度一致**,无论其小字需要多少空间。

### 修复

- **未解决故障只有一个数字**:“main 上的红色”磁贴、警报列表、底部状态栏和简报统计的是同一件事,即默认分支上最后一次运行失败的工作流(工作分支上的失败不再显示为未解决警报);只要还有未解决的警报,状态栏就不会显示“无通知”。
- **启动时只显示一次版本**:重复标题的“GitHub Actions v...”一行已去掉,作者和许可证保留在一行中。
- **损坏的状态文件**(形状不对的协作状态、哨兵缓存和历史)会逐条被忽略,不会传到读取它们的代码。
- **GitHub 配额用尽现在是一条通知,而不是每个仓库一个错误**:仓库读取会暂停到配额恢复(并自动继续),警报列表和底部状态栏会显示“GitHub 配额已用尽,HH:MM 恢复 ...(N 个仓库未刷新)”,不会变红,也不会作为失败进入信息流、声音或简报;`gh` 的错误文本被截成一行(不含法律段落和请求 ID),许多仓库的同类错误合并为一行。
- **“关于”(以及所有页面)不再等待网络**:当监视器新版本检查的结果超过一天时,它会在 /api/about 请求内部读取,因此未登录的 `gh` 或缓慢的网络会让“关于”窗口耗时 10 到 25 秒;现在会立即返回缓存的结果,读取由后台线程完成,一次只有一个。

## [1.7.6]

监控器与 AI 工具的联动: 信息流始终与页面一致, 每条告警都说明为何变红, 事件流和三个 MCP 工具推送新消息, 一条命令即可安装联动脚本, 底部栏显示是否有 AI 已连接, 所有状态文件仅其所有者可读。

### 新增

- **摘要和信息流跟随告警页的每次刷新** (以及信息流的每次读取和每个周期): 以前它们落后一个周期, 因此页面显示 6 条时 AI 可能读到 10 条。`ALERTS_BRIEF.md` 现在带有你所在时区的 `Updated:` 和供机器读取的 `updated_epoch:` 行, `GET /api/ai/brief?fmt=json` 另外提供 `updated`、`updated_local` 和 `age_seconds`。数据尚未加载的周期绝不会解决告警。
- **`ai_alerts.diagnose`** (默认关闭, 设置页, 八种语言): 新红色运行的每条告警带有 `diagnosis`, 即第一个失败的步骤和日志中约十行相关内容, 用只读调用读取, 已清除机密, 并限制大小和每周期读取的运行数; 日志中的基础设施错误会使该告警视为临时性。
- **`ai_alerts.cascade`**: 因另一个仓库变红而变红的告警 (在日志或规则 `ai_alerts.cascade.map` 中点名) 会在摘要中列在它之下, 并带有 `origin`。
- **`GET /api/ai/stream`** (`ai_alerts.stream`, 默认关闭): 服务器推送事件, 只读, 网络模式下需要访问令牌, 限制监听者数量和时长, 可用 `Last-Event-ID` 续传; lite 版没有它。
- **MCP 工具 `alerts_open`、`alert_diagnose` 和 `alert_ack`** (最后一个仅在 `--allow-ack` 时提供), 以及 AI 连接时的提示: 在 `instructions` 中并通过一条通知说明有多少真实告警未处理。
- **`monitor_cli.py ai-hook install|status|uninstall [--assistant|--cursor|--generic] [--scope project|user] [--dry-run]`** 和联动脚本 `ai_hook.py` (仅用标准库): 把摘要加入 AI 会话, 并且仅在 `ai_alerts.client_hook.block_on_stop` (默认关闭) 开启时, 在回合结束前提示 AI 查看未处理的真实告警。工具的设置是合并而非替换, 会保留文件备份, 不是有效 JSON 的文件会被拒绝且不改动, 写入的内容全部是纯 ASCII。相关数值在 `ai_alerts.client_hook` 中 (设置页, 八种语言)。
- **AI 心跳** (`ai_alerts.heartbeat`): 事件流、MCP 服务器、联动脚本和端点把最近一次读取记录在一个本地小文件中, 底部栏显示是否有 AI 已连接以及多久前读取过。
- **`monitor_cli.py --token-file FILE`**, 以及在使用 `--token` (它会出现在进程列表中) 或令牌文件可被其他用户读取时在 stderr 发出警告。
- 每项更改都有测试, 在临时文件夹中离线运行, 包括宽松 `umask` 下每个状态文件的模式。

### 变更

- **监控器的所有状态文件都以 0600 模式创建** (创建的文件夹为 0700), 通过唯一的辅助模块 `private_io.py`: 静默记录、事件、信息流、摘要、缓存、设置以及联动脚本安装程序写入的文件。在 Windows 上程序无法强制设置模式 (文件夹继承其父文件夹的权限)。
- **启动网络模式** 时若 `listen.query_access` 仍开启, 现在会打印第一步 (关闭它; 使用 HTTPS 或 VPN), `listen.network` 的帮助和高级指南也用八种语言说明了同样的事。
- **面向 AI 的告警信息流现在默认关闭** (`ai_alerts.enabled`, 以前是开启的): 新安装在你开启之前不会写出任何信息流。文件夹中已有信息流的安装保持开启, 控制台会在启动时说明一次, 因此有意使用它的人不会被关掉。

### 安全

- **发出的通知会忽略环境中的代理变量** (`http_proxy`、`https_proxy`): 有代理时检查判断的是代理的地址而不是目标地址, 而用重定向回应的代理可能把请求引向本地网络 (包括云的元数据地址)。新设置 `network.use_proxy` (默认关闭, 在设置页, 八种语言) 可重新使用它们, 此时会在代理收到任何内容之前检查目标地址和每次重定向的目标。已用一个重定向到元数据地址的代理测试。
- **`/api/ai/actions/confirm`、`/api/ai/actions/unlock`、`/api/ai/test` 和 `/api/notify/test` 在网络模式下仅限本机** (403 `local_only`), 与其他会执行操作的端点一致。
- **`act` 的计划与其工作流绑定**: 计划保存解析后的路径和文件的 SHA-256, 并在启动 `act` 之前再次核对; 确认之后被编辑、替换或删除的工作流不会运行 (`workflow_changed`, 附八种语言的文字)。
- **macOS 钥匙串不再通过命令行接收令牌**: `security -i` 从标准输入读取命令, 因此令牌不会出现在进程列表中。
- **`gh` 输出的所有内容在保存前都会清理**: 面向 AI 的操作日志和被拒绝操作的详情都经过清理器, 现在也覆盖旧的 40 位十六进制令牌以及监控器保存的令牌。
- **被拒绝地址的列表有上限** (`localguard`): 下一次锁定会清除所有已结束的锁, 而不只是发起请求的地址, 并且最多保留 2000 项。
- **未能保存的静默不会被报告为已保存**: 文件无法写入时, `POST /api/alerts/mute` 和 `unmute` 返回 `ok: false`。
- **面对形状错误的响应, 命令行绝不显示回溯**: 用列表、`null` 或数字代替对象, 或字段类型错误, 都以退出码 4 和一条消息结束。
- **网络客户端只能写入一个很短的允许列表中的设置** (语言、时区和页面的刷新节奏): 每个通知渠道、每个路径、每个环境变量名以及签名和分发流程所信任的文件, 都必须在监控器所在的电脑上更改。之后新增的设置在被有意列入之前仅限本机。
- **在同一台机器上的反向代理之后**, 带有转发头 (`Forwarded`、`X-Forwarded-*`、`X-Real-IP`) 或代理公开名称的请求绝不会被当作“这台电脑”, 并且访问令牌先于按地址的封锁被判断, 因此大量错误令牌不会把所有者锁在门外。
- **对本机的调用绝不经过环境中的代理** (`netguard.local_open`, 供命令行、MCP 服务器、终端视图和钩子使用), 命令行也不跟随重定向, 因此访问令牌不会被转发到别的地址。
- **每个响应都禁止被嵌入框架** (`X-Frame-Options: DENY`、`frame-ancestors 'none'`、`nosniff`), 页面像 API 一样检查 `Host`, 通过已弃用的 `?access=` 地址认证的响应都带有 `Deprecation` 头。
- **分发与签名**: 分发之前已存在的运行会被记录, 只有新的运行才可能被认作自己的 (不依赖时钟); 出现两个新候选需要复核; 输入 `ref` 是已检查的提交; 必需的工作流按其文件而不是显示名称匹配; 批次名称使用 UTC。
- **面向 AI 的信息流清理器覆盖更多格式**: 以 `PASSWORD`、`PWD`、`SECRET` 或 `TOKEN` 结尾的名称、地址中的凭据、Slack 和 Discord 的 Webhook、Telegram 机器人令牌、`glpat-`、`npm_` 和 `pypi-` 令牌、私钥、长十六进制字符串以及本监控器的访问令牌。MCP 服务器的 `get_run_failure` 只读取监控器所监视的仓库 (或 `ai.allowed_repos`)。
- **手工编辑的文件** (静默记录、更新状态) 只会丢失其中无效的条目, 无效的更新状态不再阻止启动。
- **时区**: 内置表中的开罗自 2023 年起遵循夏令时, 系统不认识的时区名称会在设置页被拒绝。完整版像 lite 版一样在页头报告红色工作流数量, 没有数据时 `monitor_cli.py status` 像 `health` 一样以退出码 4 结束。

## [1.7.5]

命令行以专用名称读取访问令牌，网络模式默认更安全（对网络隐藏本机地址、可关闭旧的 ?access= 地址、拒绝本地网络上的通知目标、对明文 HTTP 发出警告），面向人的时间使用你自己的时区，警报可以静音到该项目发生变化为止，并修正了给出错误结果的计数和检查。

### 新增

- **`monitor_cli.py --token TOKEN`**,命令行的访问令牌现在使用监视器自己读取的名称:先是 `MONITOR_ACCESS_TOKEN`,再是其别名 `MONITOR_TOKEN`,最后是 `--token`(命令行选项会出现在进程列表中,因此是最后手段)。被拒绝客户端的消息会指出变量名。已针对要求该请求头的模拟监视器测试。
- **stderr 警告**:当 `monitor_cli.py` 指向另一台计算机的未加密 `http` 时(令牌和响应将以明文传输)会打印警告;响应和 `--json` 不受影响。
- **`listen.query_access`**(默认开启,位于设置页,八种语言):关闭后,已弃用的 `?access=` 地址会被拒绝,会话只能通过 `POST /api/access`(正文中的令牌)或请求头打开。仍可用的地址会以 `Deprecation` 响应头回应,控制台会说明它已弃用。
- **“直到该项目发生变化”的静音**:`POST /api/alerts/mute` 对单条警报接受 `until_change`;静音会记住 issue 或拉取请求当时的 `updated_at`,当它变化(新评论、推送)或小时数结束时(以先到者为准)立即结束。Collab 的警报现在带有 `details.updated`。
- **针对多个账户共用同一令牌的 doctor 检查**(`credential`):只比较各账户读取 GitHub 所用令牌的简短指纹(监视器保存的令牌,或环境中的 `GH_TOKEN` / `GITHUB_TOKEN`),并列出共用同一令牌的账户;绝不显示令牌本身。
- 每项改动都有测试,包括一个 webhook 卫生测试:带有密钥、电子邮件、提交信息和令牌的载荷不会到达实时列表、动态流或通知,实时列表现在由允许字段列表过滤。

- **`notify.allow_private_targets`**(默认关闭,在“设置”标签页,八种语言):拒绝属于或解析到回环、私有(10.x、172.16-31.x、192.168.x、fc00::/7)、链路本地(169.254.x,含云元数据地址,fe80::/10)、共享(100.64.0.0/10)或保留地址的通知目标。名称只解析一次,套接字连接到已检查的地址(改变应答的名称无法通过),每次重定向也遵循同一规则。`mqtt` 和 `http_local` 按定义仍仅限本机。已用假服务器和假解析器测试。
- **网络模式下纯 HTTP 的警告**:开关 `listen.network` 的帮助现在以八种语言说明,没有 HTTPS 时令牌和数据以明文传输;在没有证书的情况下以网络模式启动时,控制台已会发出警告。
- **为人而写的时间采用您自己的时区**：`monitor_cli.py` 的 `Last read` 行和静音、日志 `actions_monitor_log.txt`、哨兵的报告、给 AI 的摘要以及通知，以前都以 UTC（`...Z`）显示且不加说明，与墙上的时钟相差一两个小时。现在它们显示为 `11:43:07 CET (10:43:07 UTC)`：计算机的时区、其名称，旁边是 UTC 时间。夏令时也会跟随（已围绕一年中的两次切换，并针对马德里、UTC、东京和纽约测试）。
- **`display.timezone`**（默认 `local`，位于“设置”标签页，支持八种语言）：`utc` 或如 `Europe/Madrid` 的 IANA 名称会让页面的文本和时钟按该时区显示；环境变量 `MONITOR_TIMEZONE` 优先于文件。系统没有时区数据库时（没有 `tzdata` 的 Windows），使用内置的常用时区表。
- **面向机器的字段保持 UTC，并新增一个易读的对应字段**：`ci_red.json` 和本地队列导出中的 `generated_local`，`monitor_cli.py status --json` 和页面数据中的 `updated_local`，以及 `ALERTS_BRIEF.md` 中的 `Updated:` 行。页面的时钟和底部栏会显示时区（`CET`、`JST` 等）。

- **保存的 GitHub 令牌只交给 `gh`。** 它不再放入监视器的环境中,因此 `act`、你的通知命令和其他子进程都无法继承它。

- **`--doctor`**:Python、`gh`、登录、剩余额度、网络、文件夹的写入权限、空闲端口,以及可选的 Docker、Rich 和 Textual;每个失败都附带修复它的准确命令,提供八种语言。

- **三步欢迎页**,首次打开页面时显示(它做什么、在你的账户中发现了什么、接下来去哪里)。
- **自动发现**:新增、消失、已归档或取消归档的仓库事件(控制台、设置 > 基本,在完整版中还有通知);当三个或更多未分类仓库共享同一前缀时给出建议分组,仅在你确认后添加,并保留文件副本;用于排除 fork、空仓库和私有仓库的生命周期规则;可选的自动刷新频率,在调用预算内跟随真实活动。

- **适用于各种账户的配额和套餐**:在 设置 > 基本 中选择你的套餐;各项数字(包含分钟数折算的金额、各系统的费率、并发数、作业和运行的限制、API 的额度)保存在 `quotas.json` 中,无需新版本即可编辑;可计费分钟与时钟分钟分开(公开仓库不收费,私有仓库使用 Windows 或 macOS 的倍率),每月预测标注为估算,在包含分钟数的 75 % 和 90 % 时每月通过通知提醒一次,正在运行和排队的作业对照套餐上限,接近 6 小时上限的作业,以及从 GitHub 自己的响应头读取的令牌类型(每小时只剩 60 次调用时会建议登录)。真实用量只来自可选的只读账单报告(`quota.billing_api`,默认关闭,遇到 403 或 404 时保持安静)。`GET /api/quota`。
- **工作模式:正常、快速和极速**(`modes.py`,指南 `MODES`):页眉中带仪表图标的选择器,以及控制台中的 `--mode` / `--mode-minutes`,两个版本都有。预设保存在配置的 `modes` 块中;启动前页面会显示最坏情况下每小时的调用次数、条件读取通常能节省多少,以及剩余额度能撑多久;时间到或额度低于 `min_rate_remaining` 时会自动回到正常并给出提示;未登录(每小时 60 次调用)时会说明原因并拒绝快速和极速;它需要一次性令牌,只存在于内存中,并且控制台横幅会点名它。`GET` 和 `POST /api/mode`。

- **交互式终端应用** `tui_textual.py`(可选,`pip install textual`):概览、仓库、构建、性能、脚本和设置(基本开关)标签页,一个过滤器、检查器的级别、刷新、在浏览器中打开、关于和帮助;`--lite` 显示精简版的标签页。简单的 Rich 视图(`tui.py`、`--once`)依然保留,同样提供 `--about` 和 `--help-topics`。

- 八种语言的新指南:**哨兵及其检查 A1-A13**(它是什么、如何启动、写入哪些文件、如何阅读、每项检查的确切规则、设置和操作,以及 A10 的二十五项检查;一项测试让指南与代码保持一致)、**配额与套餐**和**你的前五分钟**(`FIRST_STEPS`);迁移指南新增了从 1.5.x 到 1.6.x 的部分,README 中有两个版本之间的选择表。

## [1.6.0]

### 新增

- **条件读取（ETag）**：每次读取运行列表都会发送 `If-None-Match`；返回 `304 Not Modified` 不消耗配额。页头和 `ghamon_etag_saved_total` 统计节省的读取次数；设置标签页中有 `cache.etag.*`。
- **应对网络中断**：当一个周期内所有读取都因连接问题失败时，页面保留最后的画面并显示离线横幅，并自动恢复；`offline` 和 `online` 事件（可通知）以及 `ghamon_offline`。
- **分析**（哨兵标签页的 A12 部分、`/api/analytics`、`/metrics`、Grafana 的 JSON 数据源）：每个工作流的耗时、其作业的排队时间以及每个步骤的 p50 / p95；变得比平时慢的工作流；**不稳定**的工作流（失败后在同一提交上通过，或需要再次尝试），这只是一个标签，绝不改变什么算红色。
- **实时传入 Webhook**：已签名的 `workflow_run` 事件无需读取 GitHub 就能更新其仓库的运行列表，`workflow_job` 事件带来排队和步骤时间；只保留经过验证的简短字段（`/api/live-events`）。
- **工作流检查器**：`lint_workflows.py`（未按 SHA 固定的 action、缺失或过宽的权限、明文机密、注入、使用 PR 代码的 `pull_request_target`），规则可单独开关并有各自的严重级别，日报中有一行，另有 A13 部分。注释 `# monitor-lint: ignore 规则 原因` 或设置 `lint.ignore` 可屏蔽某个发现。
- **通知**（默认关闭）：Telegram、Discord、Slack、Matrix、MQTT 和本地 HTTP 地址，每小时上限，测试按钮，以及有文档的适配器契约（`monitor/docs/schemas/notification_event.schema.json`）。
- **AI 助手**：新的提供方 `anthropic`（Messages API，模型由你选择）和 `copilot`（使用你自己登录的 `gh copilot`，仅文本，无工具）；新任务（日报、发布说明、关于某个仓库的提问）；针对事件类型、仓库、语言和上限的设置，测试按钮以及当天用量。一份封闭的操作清单（`gh run rerun`、`gh issue close`、`act`），默认只做建议。
- **页头的数字改为磁贴**：带图标、大数字和小标签，按状态着色，带提示，点击可跳转到相应标签页，数字会计数，骨架屏会立即显示最近已知的值；第二行（仓库、活跃、模式、节省的读取、带进度条和实时倒计时的 GitHub 配额、连接、最近更新和加载进度）同样由磁贴组成。
- **终端视图**：`tui.py` 在控制台绘制实时网格（只读，可选，需要软件包 `rich`；监视器及其测试不需要任何软件包）。
- **面向服务器和大型账户**：`GET /api/health`、用于 GitHub Enterprise Server 的 `GH_HOST`（页面所有链接都会跟随）、`discover_limit`、各功能的最小权限，以及作为服务（systemd、launchd、计划任务、容器）和在反向代理之后运行的指南。
- 已发布 `ci_red.json`、公开导出和通知事件的 JSON 模式（`monitor/docs/schemas`），以及公开路线图（`docs/ROADMAP.md`）。
- 八种语言的新指南：通知、AI 助手、分析、控制台工具和部署；Webhook 指南涵盖实时事件。所有截图都用 `tools/make_screenshots.py` 和虚构数据重新拍摄（浅色和深色，包括控制台工具）。

### 变更

- **设置**：新增读取与缓存、通知、分析、检查器和终端视图的子标签页；AI 和 Webhook 子标签页包含全部选项。

### 修复

- **检查器不再对占位符误报**：看起来像机密的值会被分类（已知的令牌格式或高熵长字符串为严重，`placeholder` 或 `changeme` 这类可读的占位内容仅作提示，其余为警告；引用和空值不算发现），其值从不打印或存储。
- **页面加载期间浏览器关闭或刷新标签页时不再打印 traceback**（`ConnectionAbortedError`、`ConnectionResetError`、`BrokenPipeError`）：它们计入 `ghamon_client_disconnects_total`；真正的错误仍会显示。

### 安全

- 传入 Webhook 默认保持关闭，位于 `127.0.0.1`，强制使用 HMAC。
- 通知的机密只存在于环境变量中；主机是固定的；通知从不向 GitHub 写入。
- AI 操作：执行任何操作都需要单独的开关，并且每次都要确认完整命令，只针对监视器已在监视的目标，设有每小时上限、本地日志，连续失败两次后锁定。

- `HYDRA-UMC-OS` 在 `targets.json` 中被有意标记（`"build_only": true` + `reason`）：`plan` 把它列在 BUILD ONLY 下，不再是孤儿。签名工具未改动（其工作流使用其他输入和不同的签名方案）。
- 修复：`ci_red.target_path` 曾拒绝所有用反斜杠书写的 Windows 路径（`C:\...`）；只接受正斜杠。

**B 部分 - A10 层“Actions 与发布的外围”**（`surface.py`，标签页新增部分，`sentinel.surface` 下每项检查一个开关和一个阈值）
- Actions：被手动禁用的工作流、N 天内没有运行的计划任务（仅当运行样本覆盖该窗口时）、未按 SHA 固定的 `uses:`（可复用工作流单独标记）、`permissions: write-all`、检出 PR 的 `pull_request_target`、卡住的并发队列、矩阵中仅一个操作系统上的失败、制品的成本和保留期、红色或缺失的必需状态检查（GraphQL）、带金丝雀（只先运行第一个目标，其余仅在其为绿色时）和配额闸门（`--min-rate`，默认拒绝）的 `dispatch --profile release|nightly|hil`。配置保存在 `profiles.json` 中。
- 发布：按目标类型的预期资产（发布不完整时警报）、标签与清单与 CHANGELOG 的对比、GitHub Packages、被遗忘的草稿和预发布、`release_notes.py`（根据自上一个标签以来的提交生成说明草稿；不会发布任何内容）。
- 安全：按时长排列的严重/高危警报及仓库排名、覆盖率（没有 CodeQL / Dependabot 的技术栈）、机密扫描中未解决与已解决的对比、按优先级排序的 Dependabot（运行时主要版本优先，仅 CI 的最后）。
- Issue 与 PR：对 CI 已恢复绿色的构建 Issue 建议 `gh issue close`（带文字的事件；绝不会关闭任何东西）、逾期的里程碑、陈旧的人工 PR、涉及工作流或 CODEOWNERS 的 PR、合并队列（已批准且检查为绿色）。过期的看板卡片：待定（需要逐项读取和一个阈值）。
- 清单与证据的对比（成熟度）、八种语言 README 的一致性失败、页头、报告和 A7 中按生态系统统计的 Actions 分钟数。
- `finalize --execute` 现在会通知运行中的监视器（127.0.0.1）只刷新已签名的仓库并立即重写 `ci_red.json`（`monitor_link.py`）。
- 可选的已签名 Webhook 接收器（`webhook.enabled`，默认关闭，仅 127.0.0.1，使用配置中的共享密钥做 HMAC，绝不使用 GitHub 令牌）。
- 开销：热周期中没有任何增加。冷调用分散在各个周期并在每小时预算内：每个仓库每天 2 次 REST 调用，每 15 个仓库每天一次 GraphQL 查询，Packages 3 次，另加红色运行的作业和签名队列的证明查询，并且仅当配额高于 `min_rate_remaining` 的两倍时。热 GraphQL 遍历对每个节点多请求 3 个字段（警报日期、评审决定、检查状态）：没有额外的调用。
- 闸门还会把示例文件中的 `sentinel.surface` 与默认值比较，并验证 `profiles.json`。

## [1.1.0]

签名可信度、通向仪表盘的稳定桥梁、批处理工具中的孤儿与约定，以及更实用的页面。

- 签名可信度：`sigverify.py`（标准库、只读、无网络）依据各生态系统固定的公钥（URTC 的 `release_sign.py`、ARMOR 辅助工具的 `PACKAGE_PUBLIC_KEY`、HYDRA 更新器的 `RELEASES_PUBLIC_KEY`，或 `sentinel.signature_pubkeys`）检查已签名文件夹 `_firmados/<REPO>/release-<版本>/`。每个状态现在都带有 `signature_kind`（none | dev | release）和 `signature_verified`（true | false | "unknown"）；除“已发布”外，只有能通过验证的发布签名（`trusted`）才会降低待签名警报。无法通过验证的签名会保留警报并在报告中说明。`sentinel.require_verified_signature`（默认 true；false = 1.0.0 的规则）。本模块无法检查的格式（.sig2、.hdr2、.imgsig、APK、hydra-sign）为“unknown”，绝不是“false”。构建证明仍然需要网络，由签名工具负责。
- `ci_red.json` 模式 2：每个仓库在红色工作流旁增加 `pending_sign` 列表（workflow、hours、state、signature_kind、signature_verified、last_build_at、url），另有 `schema`、`pending_sign_repos` 和阈值；格式在 `ci_red.py` 中有文档，且只会扩展。
- “main 上最后一次运行”只有一个定义（`signstate.completed_runs`），由红色检查、无发布的绿色检查和目标状态共用。
- `ci_red.target_path` 会拒绝 D: 路径、D: 的 WSL / Git Bash 形式，以及运行系统无法使用的盘符 / UNC 路径；测试模拟两种系统，整个测试套件现在在 Linux 上也能通过。
- `gha_dispatch_all.py plan` 总是以“签名孤儿”部分结束（绿色 CI + 已知的 `*-build.yml` + 没有目标）；覆盖范围按仓库和工作流计算。
- 目标的约定（生态系统前缀 -> 默认签名工具，工作流在已知列表中）；`targets.json` 只保存例外，并始终优先。`hygiene --write-candidates` 把建议的条目写入 `targets.candidates.json`（绝不会自动应用，也绝不会被打包）。
- 页面：可点击的页头计数器“main 上为红”和“未签名”（筛选仓库；后者还会聚焦签名队列）、带命令和复制按钮的签名队列、显示已构建 / 已签名 / 已发布、签名类型与验证以及建议命令的仓库面板；当分钟预算达到 80% 时页头出现徽章（超出时为红色）；“昨天与今天”的对比也包含预算警告和报告中的行。

未完成：读取构建证明 / SBOM（需要网络）；`HYDRA-UMC-OS` 有构建工作流，但其签名工具尚不支持（列为孤儿）。

## [1.0.0]

第一个带编号的版本。软件包的功能：

- 面向四个生态系统的 GitHub Actions 监视器（本地网页、运行缓存、卡住的构建、build-failed / build-stuck Issue）。
- 哨兵 A 层（只读，无需 AI）：A1 卡住的构建，A2 红色 CI（唯一标准：每个工作流在默认分支上最后一次完成的运行），A3 CodeQL / Dependabot / 机密警报，A4 Dependabot 拉取请求，A5 发布（候选、没有发布的绿色构建、待签名），A6 卫生，A7 消耗（分钟数和 API 配额），A8 审计与轮次，A9 路线图看板。
- 每个构建目标的明确状态：built_on_gha -> signed_local（none | dev | release）-> published，带有 `last_build_at`、`last_signed_at`、`signature_kind` 和实际等待小时数；本地批处理记录和已签名文件夹记录无需等待 GitHub 就会降低待签名警报。
- 当日签名队列（`a5.sign_queue`）：最紧急的在前，附每个目标确切的 finalize 命令。
- 每个生态系统的 Actions 分钟预算（`sentinel.minutes_budget`，默认为空）：达到 80% 时在报告中警告并产生事件。
- 事件流（`events_monitor.jsonl`）和 `ci_red.json`（仓库 -> 红色工作流 + 待签名小时数），以原子方式写入。
- 批处理工具：`gha_dispatch_all.py plan|dispatch|status|finalize|hygiene`，带 `--only` 或 `--ecosystem`、`plan --json`、`finalize --json`，批次结束时对失败的 dispatch 重试一次，目标作为数据保存在 `targets.json` 中。
- `read_report.py`：从运行中的监视器获取纯文本报告，不消耗 API 配额。
- `make_release.py`：质量闸门（单元测试、干净的 zip、完整的示例配置、版本与更新日志一致）和 SHA256SUMS。

此版本未完成：由哨兵根据公钥验证发布签名以及构建证明（各生态系统的签名格式不同；证明需要网络；签名工具在发布前会验证两者）。
