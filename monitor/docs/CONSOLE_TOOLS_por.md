# Ferramentas de consola: linter de workflows e vista de consola

Duas ferramentas de linha de comandos, opcionais. O monitor em si não precisa de nenhum pacote; a vista de consola usa o Rich quando a pede.

## O linter de workflows: `bin/lint_workflows.py`

- `py -3 bin/lint_workflows.py [CAMINHO ...] [--json] [--fail-on info|warn|bad]` verifica `.github/workflows/*.yml` antes do push. Sem caminho olha para a pasta atual. Só abre ficheiros. `--remote PROPRIETÁRIO/REPO` (repetível) lê os ficheiros de workflow de um repositório a partir do GitHub com `gh`, sem clone, e diz porquê quando não consegue (SSO não autorizado, sem acesso).
- `--remote OWNER/REPO --anon` lê um repositório PÚBLICO (de um terceiro, por exemplo) sem qualquer credencial, quando `lint.anonymous_public` está ativada (desativada por defeito): a listagem da pasta de workflows é um pedido anónimo e cada ficheiro vem de `raw.githubusercontent.com`, que não gasta nada da quota do teu token. Um ficheiro que não mudou não é lido de novo, um ficheiro com mais de 256 KiB é saltado, um repositório privado ou inexistente diz «não encontrado» (nunca «limpo») e um monitor isolado da rede nunca lê. Nunca se envia um cabeçalho com um segredo.
- Regras (cada uma pode ser desligada e ter outra gravidade no separador Definições, subseparador Linter de workflows): `unpinned_uses` (uma ação não fixada a um SHA de commit completo), `permissions` (sem bloco `permissions:`, ou `write-all`), `secrets_in_clear` (o que parece um token ou chave escrito no ficheiro), `injection` (texto de terceiros colado num script `run:`) e `pr_target` (`pull_request_target` com obtenção do código do pull request).
- Regras opcionais, desativadas até as ativar: `no_timeout` (um job sem `timeout-minutes`), `secrets_inherit` (`secrets: inherit` na chamada de um workflow reutilizável), `own_action_main` (uma ação da sua própria conta que segue `@main`) e `permissions_top` (sem bloco `permissions:` no topo do ficheiro embora os jobs tenham o seu). `unpinned_uses` diz se a ação é sua ou de um terceiro (`lint.own_owners`), e `lint.unpinned_own` pode baixar ou ocultar as suas.
- A regra informativa `archived_action` (desativada até a ativar; precisa do GitHub): lista as ações e fluxos reutilizáveis do GitHub que os ficheiros usam cujo repositório está **arquivado** e, com `lint.maintenance.inactive` ativado, os que não recebem alterações há `lint.maintenance.inactive_years` anos (2 por predefinição). Consulta o GitHub uma vez por ação (`--check-actions` e `--inactive-years N` fazem-no na linha de comandos; o monitor lê com a sua própria quota, no máximo `lint.maintenance.max_calls_per_tick` ações por análise, e guarda cada resposta durante `lint.maintenance.refresh_seconds`). Apenas informa: é sempre de nível de informação, nunca faz falhar `--fail-on` nem altera o código de saída. Se não for possível chegar ao GitHub, as ações não são avaliadas, não se avisa sobre elas e a saída diz quantas não se conseguiram ler.
- O código de saída é 1 quando uma deteção atinge `--fail-on` (predefinição `bad`), por isso serve de hook antes do push. Quando o monitor vê os seus clones, acrescenta também uma linha ao relatório diário. Com `--remote`, o código de saída é 2 quando um repositório não pôde ser lido (não existe ou não é visível para o token, SSO não autorizado, sem rede) ou o seu nome não é `OWNER/REPO`: um repositório que não foi lido nunca é dado como limpo. O mesmo vale para uma pasta ou ficheiro indicado que não exista, e para um ficheiro de workflow que não possa ser lido: é nomeado na saída de erros, os outros são verificados na mesma e o código de saída é 2.
- Um valor que parece um segredo é classificado sem nunca ser impresso nem guardado: um formato de token conhecido ou uma cadeia longa de alta entropia é grave (`bad`), um enchimento legível como `placeholder`, `dummy`, `changeme` ou `ci` é só informação, todo o resto é um aviso, e `${{ secrets.X }}`, `${X}` ou um valor vazio não é deteção. Para silenciar uma deteção escreva um comentário na sua linha ou na anterior: `# monitor-lint: ignore secrets_in_clear porque é um enchimento para docker compose config` (um nome de regra ou `all`); ou liste padrões `repositório:ficheiro:regra`, com `*`, na definição `lint.ignore`.


## A vista de consola: `bin/tui.py`

- `pip install rich` e depois `py -3 bin/tui.py [--port 8765] [--refresh 5] [--once] [--theme dark|light]`. Desenha uma grelha em direto com o que está a correr, os workflows vermelhos, a fila de assinatura e o relatório, lidos do monitor em execução em `127.0.0.1` (não gasta quota do GitHub).
- É só de leitura: nenhuma tecla volta a executar, fecha ou escreve nada. Sem o Rich diz como o instalar e sai com o código 3; o monitor e os seus testes nunca precisam do Rich.
- A aplicação interativa de terminal `bin/tui_textual.py` (`pip install textual`; acrescente `--lite` para a edição lite) edita no separador Definições as definições simples dos grupos que lista, as **listas** (itens separados por vírgulas: `a, b, c`) e os **mapas de números** (`name=3, other=5`); o servidor volta a verificar cada valor, e as opções de segurança só se alteram na página.

## Regra `container_input_name`: entradas com hífen numa ação de contentor

Opcional (`lint.rules.container_input_name.enabled`, desligada por predefinição, gravidade `warn`). Para um repositório que tem uma ação executada num contentor (`runs.using: docker` em `action.yml`) procura a armadilha das entradas com hífen: o GitHub passa `fail-on-findings` ao programa como `INPUT_FAIL-ON-FINDINGS`, com os hífenes, pelo que um script que lê `INPUT_FAIL_ON_FINDINGS` nunca vê o valor (e um modo que só avisa deixa de funcionar em silêncio). O achado nomeia o script, a linha e a entrada; a forma de shell `$INPUT_FAIL-ON-FINDINGS` também é nomeada porque a shell corta o nome no hífen. Leia o valor com `printenv` ou a partir do ambiente da sua linguagem.
