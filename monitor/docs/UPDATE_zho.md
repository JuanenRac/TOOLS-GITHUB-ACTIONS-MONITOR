# 更新监视器（更新器）

[English](UPDATE.md) · [Español](UPDATE_spa.md) · [Français](UPDATE_fra.md) · [Italiano](UPDATE_ita.md) · [Deutsch](UPDATE_deu.md) · **简体中文** · [日本語](UPDATE_jpn.md) · [Português](UPDATE_por.md)

更新器可以把安装从任一已发布版本升级或降级到另一版本，同时迁移您的配置并保留退路。它只是一个文件 `monitor_updater.py`，只需要 Python，对任何已安装的版本都适用；它也放在产品中（`tools/monitor_updater.py`），并作为命令 `monitor_cli.py update` 提供。它绝不会自行更新：只在您要求时运行，也不会删除任何东西（被替换的内容会放进备份文件夹）。

## 三种打开方式

- `py -3 monitor_updater.py` 在浏览器中打开一个页面。该页面只在更新器运行期间于 127.0.0.1 提供服务，地址中带有一次性令牌，其他程序无法使用。
- `py -3 monitor_updater.py --tk` 在窗口中打开同样的界面（需要 Tkinter）。
- `py -3 monitor_updater.py --console` 是面向服务器、SSH 和容器的文本菜单。
- `py -3 bin/monitor_cli.py update` 是从产品中运行的同一个文件；`update plan`、`update apply` 以及下面的其他命令都接受表中的选项。

## 监视器内的“更新”菜单

完整版在其页面中带有同一个更新工具：**系统 > 更新**。它显示已安装的版本和检查发现的版本（设置 `updates.check`；关闭期间或监视器离线时不会向 GitHub 请求任何内容）、每个发布的说明，以及通过“查找版本”按钮显示的已发布版本列表。不按按钮就不会下载或应用任何内容。应用更新需要在运行监视器的计算机上的管理员（`/api/updates/*` 路由从网络访问会返回 403），并且需要一次说明将发生什么的确认：zip 的 SHA-256 与 SHA256SUMS 的对照、先做的副本（含其文件夹）、配置迁移和重启。更新在单独的进程中运行：监视器自行停止，应用更新，监视器以新版本重新启动，页面重新连接；若新版本无法启动，则恢复并启动之前的版本。“回到上一个版本”反向做同样的事。步骤、历史和结果会显示在页面上并记入操作日志。Lite 版、容器中或服务管理器下不提供此功能（它们会自行重启进程：请使用命令行），并且同一时间只运行一个更新。你的配置、数据、密钥和日志不会被替换。当监视器无法启动时，独立文件仍是回退的途径。

在服务管理器下，页面默认不会应用更新。如果监视器作为 systemd 的“用户”服务（`systemctl --user`）运行，可以开启 `updates.systemd_helper`（默认关闭）：页面随后会提供更新，应用更新的进程会停止该服务、应用更新并再次启动该服务，始终使用 `systemctl --user`，从不使用 `sudo`。系统服务（需要管理员权限的服务）不会被触碰，仍然是“请使用命令行”。命令行中用 `--systemd-unit 单元`（`apply` 和 `rollback`）也能做到同样的事；如果无法停止该服务，则不会启动任何操作；如果新版本无法启动，则恢复之前的版本并再次启动该服务。

**信任.** 该检查将 zip 与 SHA256SUMS 进行比对，二者来自同一个 GitHub 发布：它能发现损坏或不完整的下载，但发现不了在源头被替换的发布。对发布的信任取决于 GitHub 以及您在那里的账户。

## 逐步说明 支撑它的路由是 `/api/updates/status`、`/api/updates/progress`、`/api/updates/history`（只读）以及 `/api/updates/check`、`/api/updates/plan`、`/api/updates/apply`、`/api/updates/rollback`（管理员，仅限本机）。 进度也会通过 `/api/updates/stream` 以服务器发送事件的方式推送（更新期间页面使用它；当浏览器或连接不支持时，回退为每 1.5 秒查询一次）。

1. 检测安装：文件夹、版本、版本类型（完整版或 Lite）、配置、数据、端口、监视器是否在运行、是容器还是服务。
2. 列出 GitHub 上已发布的所有版本（无需令牌），附日期和说明，并标出已安装的和最新的。没有网络时，用 `--zip` 提供一个 zip。
3. 由您选择目标版本。较低的版本属于降级：需要 `--allow-downgrade`。
4. 以演练方式显示计划：两个版本之间的步骤链（取自迁移注册表）、您的配置会有哪些变化、您会注意到的行为变化，以及发现的每一处不一致。
5. 执行：先备份，对照 SHA256SUMS 校验 SHA-256，把 zip 解压到新文件夹并检查（含 `..` 的路径、链接、大小），复制产品，恢复您在启动脚本中的自定义行，迁移配置，迁移目录结构，并可按需启动监视器、检查 `/api/health`。
6. 如有任何失败，它会自动回到先前状态并写出报告。每次更新都会记入历史（`update_history.jsonl`），最近一次可用命令 `rollback` 撤销。

## 命令

不带命令时会打开页面。命令只回答一次（加上 `--json` 得到一份文档）：

| 命令 | 含义 |
|---|---|
| `status` | 已安装的内容以及检查发现的问题 |
| `releases` | 所有已发布的版本 |
| `plan` | 针对某个目标的演练 |
| `apply` | 执行（`--dry-run` 只显示计划） |
| `migrate` | 只迁移一个配置文件，见下文 |
| `rollback` | 回到最近一次更新之前的版本 |
| `history` | 此安装上进行过的更新 |

## 选项

| 选项 | 含义 |
|---|---|
| `--dir` | 安装位置（默认：该文件所在位置，向上查找） |
| `--to` | 目标版本（默认：最新版） |
| `--from` | migrate：文件所来自的版本 |
| `--config` | migrate：一个配置文件 |
| `--zip` | 使用此 zip 而不是 GitHub |
| `--sha256` | zip 预期的 SHA-256 |
| `--dry-run` | 只显示计划 |
| `--apply` | migrate：写入结果 |
| `--yes` | 不要求确认 |
| `--json` | 以一份 JSON 文档作答 |
| `--keep-old-defaults` | 为您从未设置过的每个设置写入旧默认值，使行为保持不变 |
| `--adopt-new-defaults` | 同时把仍为旧默认值的设置改为新默认值 |
| `--start` | 之后启动监视器并检查 |
| `--handover` | 启动此进程的监视器会自行停止：等待它、应用更新、再启动它（启动失败则恢复之前的版本） |
| `--status-file` | 把进度写入此 JSON 文件（“更新”菜单会读取它） |
| `--edition` | complete 或 lite，无法推断时使用 |
| `--allow-downgrade` | 允许较低版本 |
| `--allow-container` | 仍然在容器内工作（镜像不会被替换） |
| `--no-gh` | 不使用 `gh` 程序，只用公开 API |
| `--backups` | 备份文件夹（默认：安装目录中的 update_backups） |
| `--restore-data` | yes、no 或 auto：回滚时如何处理数据 |
| `--port` | 页面端口 |
| `--no-browser` | 不打开浏览器 |
| `--tk` | 窗口界面 |
| `--console` | 文本菜单 |
| `--lang` | 语言：en es de fr it ja zh pt |

## 您的配置与变化的默认值

- 迁移注册表（随每个发布版本版本化的 JSON 文件，位于 `assets/migrations/`）说明每个版本改变了什么：设置被重命名、移除或新增、新的默认值、文件被移动、行为变化。更新器会应用您所跨越版本的整条链。
- 默认情况下，它保留您明确设置的内容，只在您从未定义的设置上采用新默认值。行为变化（例如某功能现在默认关闭）会写进报告；`--keep-old-defaults` 固定旧行为，`--adopt-new-defaults` 把一切改为新行为。
- `migrate` 可单独处理一个文件：`monitor_updater.py migrate --from 2.0.1 --to 2.0.8 --config my.json` 显示结果，`--apply` 写入（先备份）。任何报告中的机密都会被遮蔽。

## 应用之前的检查

- 阻止：监视器正在运行、SHA-256 不匹配、zip 不安全、磁盘空间不足、数据的架构比目标更新、容器、已有另一个待处理的更新。
- 警告：已不存在或类型、范围已变的设置、超出范围的值、重复的键、端口被其他程序占用、您改过的启动脚本、需要先执行另一步的步骤。每条警告都附有建议的操作。

## 安全与退路

- 它只在 127.0.0.1 上监听并使用临时令牌，拒绝来自其他站点的请求，不执行 zip 中的任何内容，不使用 shell，只在安装目录和备份文件夹内写入。
- 更改任何内容之前，它会备份程序包、配置和数据；某一步失败时会恢复备份并写出报告。若连回滚也失败，备份保持完好，报告会说明如何手动恢复。
- 离线：`--zip 文件` 加 `--sha256`（或旁边放一个 SHA256SUMS）。Docker：更新的是数据卷，不会从内部替换镜像（可用 `--allow-container` 强制）。

## 退出码

| 代码 | 含义 |
|---|---|
| 0 | 完成，或无事可做 |
| 2 | 用法错误 |
| 3 | 被某项检查阻止，未做任何更改 |
| 4 | 下载、SHA-256 或 zip 失败，未做任何更改 |
| 5 | 失败，已恢复先前状态 |
| 6 | 失败且回滚也失败：请手动恢复备份 |
| 7 | 无法连接 GitHub 且未提供 zip |
| 8 | 未确认 |

## 服务助手的防护

使用 `updates.systemd_helper`（或 `--systemd-unit`）时，更新程序现在会在触碰服务之前先检查：工作目录和命令未指向“此”文件夹的单元属于另一个安装，既不会被停止也不会被启动；当其他程序（前台运行的监视器）占用其端口时不会启动该单元；进程仍是旧进程时不会把重启视为完成（单元必须显示新的 PID）；`update status --systemd-unit 单元` 只列出该服务自上次启动以来的错误。这些都是对 `systemctl --user show` 和 `journalctl --user` 的只读查询；无法回答的查询不会阻止任何操作。
