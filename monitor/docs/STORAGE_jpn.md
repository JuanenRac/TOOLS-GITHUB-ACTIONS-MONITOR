# 保存と保持

完全版が学んだ内容をどこに保存するか、それをどう変えるか、そして自動で何を削除するかを説明します。ライト版は常に通常のファイルだけを使い、データベースも保持ジョブも持たず、ここにある項目は何も表示しません。

## 保存されるもの

アカウントごと:設定(`actions_monitor.json`)、センチネルの状態、イベントフィード、フィードがすでに通知した内容、分析のサンプル、ミュート、更新のお知らせ。インストール全体:ユーザー、見られるアカウント、セッション(チームモードが使います)。条件付き読み取りのキャッシュとログは常に通常のファイルです。

## 2つの保存方式

|  | `file`(既定) | `sqlite` |
|---|---|---|
| 場所 | `accounts/<id>/`(`accounts/` がなければランチャーの横) | `accounts/<id>/storage.sqlite3`、アカウントごとに1つのデータベース |
| 書き込み | 一時ファイルをディスクに書き出してから名前を変更 | 短いトランザクション、WALジャーナル |
| 向いている用途 | 1人で使う場合。読んで編集できるファイル | 何か月も動かすサービス。イベントが多い場合 |

アカウント(またはモニター)の設定で選びます:`"storage": {"backend": "sqlite"}`。設定そのものは、保存方式を指定するものなので、常にJSONファイルのままです。SQLiteではイベントフィードは `events_monitor.jsonl` ではなくデータベースに入ります。開けないデータベースがあると起動を止めます。モニターが黙ってほかの場所に状態を書くことはありません。

## 決定:アカウントごとに1つの保存先(モデルA)

*背景。* 完全版はアカウントごとに1つのプロセスを動かします。*決定。* 各プロセスは自分専用の保存先を持ちます(自分のファイル、または `accounts/<id>/` の中の自分の `storage.sqlite3`)。2つのプロセスが同じファイルに書くことはないので、プロセス間のロックは不要で、1つのアカウントの問題がほかを壊すこともありません。*代償。* アカウントをまたぐ問い合わせは複数のデータベースを読むことになります。

*用意だけしてあるもの:モデルB(共有データベース1つ)。* すべてのアカウントの `storage` ブロックに同じパスを書きます(`"path": "/data/monitor.sqlite3"`)。すべてのテーブルがアカウントを持ち、WALによりセンチネルが書き込み中でもページが読め、トランザクションは短く、データベースがビジー状態なら最大5秒待つため動作します。テスト済みです(2つのプロセスが同時に動く、書き込み中にHTTPで応答するページ)が、既定ではありません。Aより壊れやすく、アカウントをまたぐSQLが必要な場合にだけ意味があります。

## 保証されること

- 書き込みはアトミックです。読む側には古い値か新しい値のどちらかが見えます。途中で強制終了(`kill -9`)されたプロセスは古い値を残し、SQLiteでは次の起動で自動的に回復します。
- スキーマにはバージョン(`schema_version`)があります。各マイグレーションはバージョンの更新と同じ1つのトランザクションで実行されるため、中断してもデータベースは元のままで、次の起動でやり直されます。新しいバージョンが書いたデータベースは拒否され、ダウングレードされることはありません。
- 壊れている項目や無い項目は空として読まれます。モニターはディスクにあるものだけで起動します。

## データの移行とバックアップ

```
python tools/migrate_storage.py --from file --to sqlite              # ドライラン:コピーする内容を表示
python tools/migrate_storage.py --from file --to sqlite --apply      # コピーし、すべての項目とイベントを比較
python tools/backup_storage.py backup backup.zip --backend sqlite    # マニフェストとSHA-256付きの.zip
python tools/backup_storage.py verify backup.zip
python tools/backup_storage.py restore backup.zip --backend file     # 空の保存先へ(既存のアカウントに上書きするなら --force)
```

移行はあなたのファイルを変更も削除もせず、中断後は再開でき(アカウントは丸ごとコピーされるか、まったくコピーされないかのどちらか)、両側が一致しなければ失敗で終わります。成功したあとで初めて保存方式を切り替えて再起動してください。ファイルから作ったバックアップはSQLiteに復元でき、その逆もできます。`--db FILE` はモデルBの共有データベースを選び、`--flat` は `accounts/` のない構成です。`--doctor` はデータベースを変更せずに調べます(存在、整合性、スキーマ)。

## 保持

何か月も動かし続けるモニターは際限なく大きくなるため、更新の終わりに短い処理(`retention.interval_hours` ごと、既定は24)が古いものを削除します。

| 設定 | 既定 | 意味 |
|---|---|---|
| `retention.enabled` | オン | スイッチ |
| `retention.events_days` | 90 | これより古いイベントを削除 |
| `retention.analytics_days` | 180 | これより古い分析履歴の日を削除 |
| `retention.mode` | `archive` | `archive` は古いイベントを先に `events/archive/` の `.gz` に書き出す |
| `retention.events_max_kb` | 512 | ファイル保存でのフィードファイルのサイズ上限(従来どおり) |
| `retention.warn_events_mb` | 20 | このサイズを超えると `--doctor` が警告 |

整理は、期限より古いイベントと分析の日だけを対象にします。設定、センチネルの状態、ミュート、時刻のないイベントには決して触れません。処理のたびに監査ドキュメントに1行(いつ、削除・保持したイベント数、アーカイブファイル、分析の日数、エラー)が残ります。`--doctor` はイベントのサイズを警告し、サービスとして動くモニター(ネットワークモード、ブラウザなし、コンテナ、または `MONITOR_SERVICE=1`)で設定に `retention` ブロックがない場合にも警告します。期限を短くする前にバックアップを取ってください。

既定の `archive` は取り除いた内容を読み戻せる圧縮ファイルに残し、`delete` は完全に削除します。
