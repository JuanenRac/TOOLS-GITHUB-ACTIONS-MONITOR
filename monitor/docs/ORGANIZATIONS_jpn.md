# 組織と大規模アカウント

モニターを組織や数百のリポジトリを持つ個人アカウントに向ける方法と、読み取り結果が空で返ってきたときの対処を説明します。

## 1. 動作する最小のトークン

モニターは読み取りしかしません。`gh` のログイン(`gh auth login`)または `GH_TOKEN` のトークンを使い、必要最小限の権限だけを与えます。

| トークンの種類 | 与えるもの |
|---|---|
| **クラシック**(個人アクセストークン) | 非公開リポジトリには `repo`(すべて公開なら `public_repo` で足ります)、組織のリポジトリとチームの一覧には `read:org`。任意:`security_events`(コードスキャンのアラート、パネル A3)、`read:project`(Projects ボード、パネル A9)。`workflow` や書き込み系のスコープは不要です。 |
| **細粒度** | *リソースの所有者*は1つだけ:組織ごと(または個人アカウントごと)にトークンを作ります。リポジトリへのアクセス:すべて、または選択したもの。読み取り専用の権限:Metadata、Actions、Contents、Pull requests、Issues、Administration(ruleset とブランチルール)、Code scanning alerts、Dependabot alerts、Secret scanning alerts。組織によっては、所有者が先にトークンを承認する必要があります。 |
| **GitHub App** | あなたの枠ではなく App の枠で読み取ります(`QUOTA.md` を参照)。 |

**個人アカウント**(`github_owner` がユーザー)は、自分のリポジトリなら上記以上は不要です。所属する組織のリポジトリは、リソースの所有者(細粒度)またはスコープ(クラシック)にその組織を含むトークンで読み取ります。

## 2. シングルサインオン(SSO)と非公開リポジトリ

組織が SAML シングルサインオンを強制している場合、クラシックトークンはその組織に対して承認されている必要があります。GitHub で *Settings > Developer settings > Personal access tokens* を開き、トークンを選んで *Configure SSO > Authorize* を押します。`gh auth login` で作ったログインは、ブラウザーで組織を承認すると承認されます。それまで GitHub は `403`(*Resource protected by organization SAML enforcement*)を返すか、さらに悪いことに非公開リポジトリを除いた `200` を返します(ヘッダー `X-GitHub-SSO: partial-results`)。これはリポジトリの少ない組織のように見えます。

非公開リポジトリが見えないトークンは、存在しない場合とまったく同じ `404` を受け取ります。つまり空の応答は、SSO 未承認、スコープまたは権限の不足、ログインから見えない非公開リポジトリ、あるいは Actions がまったくない、のいずれかを意味します。次の節で区別できます。

## 3. `--doctor` が説明します

`py -3 bin/actions_monitor.py --doctor`(`bin/monitor_cli.py doctor` でも可)は3回の小さな読み取りを行い、2行を報告します。

- **ログインでアカウントまたは組織を読み取れる**(`access`):`ok`(ログイン名とスコープ付き)。または詳細に原因を示した `warn`:`sso`(未承認、または非公開リポジトリが隠れている)、`rate_limited`、`scope`(権限不足)、`not_found`(アカウントが存在しない、または見えない)、`forbidden`。GitHub が認証情報を拒否した場合は `fail`。細粒度トークンには一覧できるスコープがなく、その旨が表示されます。
- **1時間あたりの読み取りが枠に収まる**(`estimate`):アカウントのリポジトリ数と、現在の設定で必要になる1時間あたりの読み取り数を、個人トークンの1時間 5,000 回と比較します。呼び出しを使わない推定です。run のポーリング(リポジトリの10分の1がホットで `refresh_seconds` ごと、残りは `cold_refresh_seconds` ごと)、センチネル(最大 `sentinel.budget_per_hour`)、クローンなしでワークフローファイルを読む場合はその分を含みます。60% を超えると `warn`。下げるには、`cold_refresh_seconds` を大きくする、Low モードを有効にする、監視するリポジトリを減らす(`repos`)、または GitHub App で読み取ります。

モニターがワークフローファイルを読めなかった場所では、同じ原因がリポジトリ名とともに書かれます。センチネルのパネル A13 は、それらを理由付きの*評価不可*として一覧し、黙って「データなし」にすることはありません。

## 4. 自分のものではないアカウントを監視する(権限のない観察者)

どのトークンでも任意のアカウントの公開リポジトリを読めるため、スコープのないトークンでオープンソースの組織を監視できます。観察者が得られず、モニターが*不明*として扱い決して*問題なし*とは扱わないもの:ruleset とブランチ保護、Dependabot・コードスキャン・シークレットスキャンのアラート、設定、Actions が無効なリポジトリの run 一覧。これらに依存するパネル(A3、A6 の一部)は、そのリポジトリでは空になるか評価不可と表示されます。何も書き込まないため、書き込み権限は不要です。

## 5. 既知の制限

- 個人トークンの枠は1時間あたり 5,000 回の読み取りです。大きな組織にインストールした GitHub App はそれより多くなります(`QUOTA.md` を参照)。収まるかどうかは上の推定が最も手早い方法です。
- モニターは各リポジトリの直近の run のサンプルを読みます。1時間に数百の run を起動するリポジトリは、そのサンプル越しに見え、run を1つずつ見るわけではありません。
- GitHub は run のログとアーティファクトを既定で90日間保持します。GitHub が削除したものはモニターでは読めません。
- 細粒度トークンは1人の所有者に属します。2つの組織を監視するには2つのトークン(モニターの2つのアカウント、`ACCOUNTS.md` を参照)が必要です。
- トークンの承認を求める、またはクラシックトークンを禁止している組織では、先に所有者の操作が必要です。モニターの設定ではこれを回避できません。
