# モニターの更新（アップデーター）

[English](UPDATE.md) · [Español](UPDATE_spa.md) · [Français](UPDATE_fra.md) · [Italiano](UPDATE_ita.md) · [Deutsch](UPDATE_deu.md) · [简体中文](UPDATE_zho.md) · **日本語** · [Português](UPDATE_por.md)

アップデーターは、公開済みのどのバージョンからでも別のバージョンへ（上げ下げとも）インストールを移し、設定を移行し、戻る道を残します。必要なのは Python だけの 1 つのファイル `monitor_updater.py` で、インストール済みのどのバージョンでも動きます。製品内（`tools/monitor_updater.py`）にもあり、コマンド `monitor_cli.py update` としても使えます。自分で勝手に更新することはなく、求めたときだけ動き、何も削除しません（置き換えられたものはコピーのフォルダーへ移されます）。

## 開き方は 3 通り

- `py -3 monitor_updater.py` はブラウザーでページを開きます。ページはアップデーターの実行中だけ 127.0.0.1 で提供され、アドレスに 1 回限りのトークンが付くため、ほかのものは使えません。
- `py -3 monitor_updater.py --tk` は同じ内容をウィンドウで開きます（Tkinter が必要）。
- `py -3 monitor_updater.py --console` はサーバー、SSH、コンテナー向けのテキストメニューです。
- `py -3 bin/monitor_cli.py update` は製品から起動する同じファイルです。`update plan`、`update apply` など以下のコマンドは表のオプションを受け付けます。

## モニター内の「更新」メニュー

完全版は同じ更新ツールをページ内に持っています: **システム > 更新**。インストール済みバージョンと確認で見つかったバージョン (設定 `updates.check`。オフの間、またはモニターがオフラインの間は GitHub に何も問い合わせません)、各リリースのノート、そして「バージョンを探す」ボタンで公開済みの一覧を表示します。ボタンを押さない限り、何もダウンロードも適用もされません。適用には、モニターが動作しているコンピューターの管理者が必要です (`/api/updates/*` はネットワーク経由では 403 を返します)。確認では、zip の SHA-256 と SHA256SUMS の照合、先に作るコピー (フォルダー付き)、設定の移行、再起動といった内容が示されます。更新は独立したプロセスで実行されます。モニターは自動的に停止し、更新が適用され、新しいバージョンで再起動してページが再接続します。新しいバージョンが起動しない場合は、以前のバージョンを戻して起動します。「前のバージョンに戻す」は逆方向に同じことを行います。手順・履歴・結果はページに表示され、操作ログにも記録されます。Lite 版、コンテナー、サービスマネージャーの下では提供されません (これらは自らプロセスを再起動するため、コマンドラインを使ってください)。同時に実行できる更新は 1 つだけです。設定・データ・鍵・ログは置き換えられません。モニターが起動しないときの戻り道として、単体ファイルは残ります。

サービスマネージャーの下では、ページは既定で更新を適用しません。モニターが systemd の「ユーザー」サービス（`systemctl --user`）として動いている場合は、`updates.systemd_helper`（既定はオフ）をオンにできます。ページが更新を提供し、適用するプロセスがそのサービスを停止して更新を適用し、サービスを再び起動します。常に `systemctl --user` を使い、`sudo` は使いません。システムサービス（管理者権限が必要なもの）には触れず、これまでどおり「コマンドラインを使う」ままです。コマンドラインでも `--systemd-unit ユニット`（`apply` と `rollback`）で同じことができます。サービスを停止できなければ何も開始されず、新しいバージョンが起動しなければ前のバージョンが戻されてサービスが再び起動されます。

**信頼.** この確認は zip を SHA256SUMS と照合しますが、どちらも同じ GitHub リリースのものです。破損または不完全なダウンロードは検出できますが、配布元で差し替えられたリリースは検出できません。リリースへの信頼は GitHub と、そこにあるご自身のアカウントに依存します。

## 処理の流れ これを支えるルートは `/api/updates/status`、`/api/updates/progress`、`/api/updates/history`、`/api/updates/log`（プロセスのログの最後の行。token や secret の後の値は隠されます）、`/api/updates/copies` (読み取り専用) と `/api/updates/check`、`/api/updates/plan`、`/api/updates/apply`、`/api/updates/rollback`、`/api/updates/discard` (管理者、このコンピューターからのみ) です。 進行状況は `/api/updates/stream` でサーバー送信イベントとしても配信されます（更新中はページがこれを使い、ブラウザーや接続が対応しない場合は 1.5 秒ごとの問い合わせに戻ります）。

1. インストールを検出します：フォルダー、バージョン、エディション（Complete または Lite）、設定、データ、ポート、モニターが動作中か、コンテナーかサービスか。
2. GitHub で公開されているすべてのバージョンを（トークン不要で）日付とノート付きで一覧し、インストール済みのものと最新のものに印を付けます。接続できないときは `--zip` で zip を渡してください。
3. 移行先のバージョンを選びます。低いバージョンはダウングレードで、`--allow-downgrade` が必要です。
4. ドライランとして計画を表示します：2 つのバージョン間の手順の連なり（移行レジストリから読み取り）、あなたの設定で何が変わるか、気づくはずの動作の変更、見つかったすべての不整合。
5. 適用します：事前コピー、SHA256SUMS との SHA-256 照合、新しいフォルダーへの zip 展開と検査（`..` を含むパス、リンク、サイズ）、製品のコピー、起動スクリプトに加えたあなた自身の行の復元、設定の移行、フォルダー構成の移行、そして希望すればモニターの起動と `/api/health` の確認。
6. 途中で失敗すると自動的に元の状態へ戻り、レポートを書きます。更新はすべて履歴（`update_history.jsonl`）に残り、直近のものはコマンド `rollback` で取り消せます。

## コマンド

コマンドなしではページが開きます。コマンドは一度だけ答えます（`--json` を付けると文書で返します）：

| コマンド | 意味 |
|---|---|
| `status` | 何がインストールされ、チェックで何が見つかったか |
| `releases` | 公開済みのすべてのバージョン |
| `plan` | 指定した移行先のドライラン |
| `apply` | 実行（`--dry-run` は計画の表示のみ） |
| `migrate` | 設定ファイル 1 つだけを移行（下記参照） |
| `rollback` | 直近の更新より前のバージョンへ戻す |
| `history` | このインストールで行った更新 |
| `copies` | コピーのフォルダーにあるコピー：名前、状態、バージョン、サイズ、ロールバックに必要なもの |
| `discard` | `discard --name コピー名` は確認後にコピーを 1 つだけ削除します（`--yes` で質問を省略）。ロールバックに必要なコピーは `--force` が必要で、実行中の更新のコピーは決して削除しません |
| `log` | 最後の更新のプロセスのログの最後の行（`--lines N`、最大 2000）。token、secret、password の後の値は隠されます |

## オプション

| オプション | 意味 |
|---|---|
| `--dir` | インストール先（既定：ファイルのある場所から上へ探索） |
| `--to` | 移行先バージョン（既定：最新） |
| `--from` | migrate：ファイルの元のバージョン |
| `--config` | migrate：設定ファイル |
| `--zip` | GitHub の代わりにこの zip を使う |
| `--sha256` | zip の期待される SHA-256 |
| `--dry-run` | 計画を表示するだけ |
| `--apply` | migrate：結果を書き込む |
| `--yes` | 確認を求めない |
| `--json` | 応答を 1 つの JSON 文書で返す |
| `--keep-old-defaults` | 一度も設定していない項目に旧既定値を書き込み、動作が変わらないようにする |
| `--adopt-new-defaults` | 旧既定値のままの項目も新既定値へ移す |
| `--start` | その後モニターを起動して確認する |
| `--handover` | このプロセスを起動したモニターが自動的に停止します。それを待ち、適用し、再起動します (起動に失敗すると以前のバージョンに戻ります) |
| `--status-file` | 進行状況をこの JSON ファイルに書き出します (「更新」メニューが読みます) |
| `--edition` | complete か lite（判別できないとき） |
| `--allow-downgrade` | 低いバージョンを許可する |
| `--allow-container` | コンテナー内でもあえて実行する（イメージは置き換えられない） |
| `--no-gh` | `gh` プログラムを使わず公開 API のみ使う |
| `--backups` | コピーのフォルダー（既定：インストール内の update_backups） |
| `--restore-data` | yes、no、auto：戻すときのデータの扱い |
| `--port` | ページのポート |
| `--no-browser` | ブラウザーを開かない |
| `--tk` | ウィンドウ版 |
| `--console` | テキストメニュー |
| `--lang` | 言語：en es de fr it ja zh pt |

## あなたの設定と変わる既定値

- 移行レジストリ（各リリースにバージョン管理された JSON ファイル、`assets/migrations/`）は、バージョンごとに何が変わったかを示します：設定の名前変更・削除・追加、新しい既定値、移動したファイル、動作の変更。アップデーターは飛び越えるバージョンの連なりを適用します。
- 既定では、あなたが明示的に設定した値を保ち、一度も定義していない設定にだけ新しい既定値を採用します。動作の変更（たとえば機能が既定でオフになった場合）はレポートに記されます。`--keep-old-defaults` は旧動作を固定し、`--adopt-new-defaults` はすべてを新しい動作へ移します。
- `migrate` は単独のファイルにも使えます：`monitor_updater.py migrate --from 2.0.1 --to 2.0.8 --config my.json` は結果を表示し、`--apply` で（コピーのあとに）書き込みます。シークレットはどのレポートでも伏せられます。

## 適用前のチェック

- ブロックするもの：モニターが動作中、SHA-256 の不一致、安全でない zip、ディスク容量不足、移行先より新しいスキーマのデータ、コンテナー、保留中の別の更新。
- 警告するもの：存在しなくなった、または型や範囲が変わった設定、範囲外の値、重複したキー、他のプログラムが使っているポート、あなたが変更した起動スクリプト、先に別の手順が必要な手順。警告ごとに推奨される対処が付きます。

## 安全性と戻る道

- 127.0.0.1 でのみ一時トークン付きで待ち受け、他サイトからの要求を拒否し、zip の中身を実行せず、シェルを使わず、インストール先とコピーのフォルダーの中にしか書き込みません。
- 何かを変える前に、パッケージ・設定・データをコピーします。手順が失敗するとコピーを復元してレポートを書きます。戻す処理まで失敗した場合でもコピーは無傷で、レポートが手動での復元方法を示します。
- オフライン：`--zip ファイル` と `--sha256`（または隣に SHA256SUMS）。Docker：ボリュームが更新され、イメージは内側から置き換えられません（強制するには `--allow-container`）。
- ページにはコピーの一覧と、各コピーの **コピーを破棄** ボタンがあり（先に確認し、ロールバックに必要なコピーでは 2 回確認します）、最後の更新のプロセスのログ全体を読むボタンもあります。破棄は、そのコピーだけを削除し、インストールやデータには触れず、履歴に記録されます。
- モニターなしで動く単独のアップデーターにも同じ機能があります。ブラウザーのページ (**コピー** と **プロセスのログ** のボタン、各コピーの **コピーを破棄**。確認の質問は同じ)、テキスト メニュー (7 から 9 の項目)、ウィンドウ (Tkinter) です。

## 終了コード

| コード | 意味 |
|---|---|
| 0 | 完了、または何もすることがない |
| 2 | 使い方の誤り |
| 3 | チェックにより停止、何も変更なし |
| 4 | ダウンロード、SHA-256、zip の失敗、何も変更なし |
| 5 | 失敗し、元の状態へ復元済み |
| 6 | 失敗し、戻す処理も失敗：コピーを手動で復元 |
| 7 | GitHub に接続できず zip もない |
| 8 | 確認されなかった |

## 通知はインストール方法に合ったコマンドを示します

新しいバージョンの通知（コンソール、このツールについて、`/api/about`）は、このモニターのインストール方法に合った正確なコマンドを `channel` の隣の `command` フィールドで示します：展開した製品（`py -3 monitor/bin/monitor_cli.py update`）、サービスマネージャー（`... update apply --systemd-unit <ユニット>`）、コンテナー（`docker pull ghcr.io/juanenrac/tools-github-actions-monitor:<バージョン>`）、pipx、uv、`gh` コマンドの拡張。通知自体は何も実行しません。
## サービスヘルパーの安全確認

`updates.systemd_helper`（または `--systemd-unit`）を使うと、アップデーターはサービスに触れる前に確認します。作業ディレクトリとコマンドが「このフォルダー」を指さないユニットは別のインストールのものとして停止も起動もしません。ポートでほかのもの（フォアグラウンドのモニター）が応答している間はユニットを起動しません。プロセスが古いままの間は再起動を完了とみなしません（ユニットは新しい PID を示す必要があります）。`update status --systemd-unit ユニット` はサービスの前回の起動以降のエラーだけを一覧します。これらは `systemctl --user show` と `journalctl --user` への読み取り専用の問い合わせで、答えが得られなくても何もブロックしません。
