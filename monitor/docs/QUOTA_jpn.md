# クォータを増やし、消費を減らす

GitHub はアカウントごとに**API 呼び出しの限られたクォータ**を与え、それを使うすべてのツールで共有します。このガイドでは仕組みと、モニターが消費を減らすすべての方法を説明します。

## クォータの仕組み
- **REST**:ユーザーあたり 1 時間 5000 回(ログインなしは 60 回)。**GraphQL** には別のクォータがあります。Actions のワークフローの `GITHUB_TOKEN` にも独自のクォータがあります。**GitHub App** にはあなたのものとは別の独自クォータがあり、インストールされたリポジトリが多いほど増えます(130 リポジトリで 1 時間あたり約 10 000 回)。
- 数えられるもの・数えられないもの:`304 Not Modified`(ETag)を返す条件付き読み取りは数えられません。`rate_limit` の取得は無料です。`git push`、`git fetch`、`git clone` は API を使いません。

## モニターが節約する方法
1. **条件付き読み取り**(ETag と `304`):`cache.etag.enabled`(既定でオン)。節約できた読み取り数をページに表示します。
2. **節約モード**:アクティブなリポジトリだけを 4 分ごと、その他を 30 分ごと。`modes.auto_low`(オン)は残り 1000 回未満で入り、2500 回超または更新で戻ります。プリセットは `modes.low`。バーに数値が古い可能性とその経過時間が表示されます。
3. **ベースラインとしての中央パネル**:`central.source`(`off`、`git`、`http`)は、ワークフローが独自のトークンで更新するプロフィールリポジトリの `data/sentinel.json` を読みます。あなたのクォータは消費しません。`central.max_age_minutes`(120)より古いと「遅延」とされ、信頼されません。
4. **クォータ切れは 1 つの通知に**:更新まで読み取りを止め、ページは「クォータは HH:MM まで使い切り」と 1 回だけ表示し(リポジトリごとのエラーではなく)、自動で再開します。
5. **読み取り用の GitHub App**(`github_app.*`)、下記。
6. **静かなリポジトリ向けの GraphQL(既定でオン)**:`network.graphql_checks` は、ホットでないリポジトリを専用の枠を持つ GraphQL でまとめて(`network.graphql_batch`、既定 20)読みます。1 回の呼び出しで多数の REST 呼び出しの代わりになります。見えるのは既定ブランチの最後のコミットだけ(そこで動かなかったワークフローは表示されません)で、実行時間・試行回数・他のブランチは得られないため、ホットなリポジトリと GraphQL が応答しないリポジトリは同じサイクルで REST で読みます。集計(バッチ数、リポジトリ数、ポイント、REST に回ったリポジトリ)は概要と AI ツール向けの状態にあります。実際のアカウントでの測定の後、既定でオンです。40 件のリポジトリを 2 回のバッチで読み、呼び出しは 40 回ではなく 2 回(95 % 減)で、すべてのリポジトリに応答があり、エラーはありませんでした。すべてを REST で読むには `network.graphql_checks` を false にします。

## GitHub App の手順
1. GitHub で *Settings*、*Developer settings*、*GitHub Apps*、*New GitHub App*。Webhook は不要。**読み取り専用**の権限:Actions、Checks、Code scanning alerts、Commit statuses、Contents、Dependabot alerts、Issues、Pull requests、Secret scanning alerts、Metadata。
2. *Generate a private key* で、`.pem` を**どのリポジトリの外**にも置き、自分だけが読めるようにします。
3. *Install App* でアカウントの監視したい全リポジトリにインストールします。
4. モニターで `github_app.enabled` をオン、`github_app.app_id`(App の番号)と `github_app.key_path`(鍵の**パスのみ**)を設定します。`github_app.installation_id` は空で構いません。
5. `GET /api/github-app/status`(このコンピューターのみ)で確認します。App の名前、インストール、付与された権限、クォータを表示し、鍵やトークンは表示しません。doctor は `openssl`、鍵ファイル、その権限を確認します。

セキュリティ:モニターは、最長 10 分の JWT に署名するときだけ鍵をメモリに読み込み(標準ライブラリで署名するため `openssl` は不要で、`openssl` は代替手段です)、コピー、表示、記録は一切しません。インストールトークンは 1 時間有効でメモリに保持され、5 分前に更新されます。**読み取りだけ**がこれを使い、書き込みとアクションはあなたのトークンを使い続けます。App が失敗したり権限が足りない場合は、あなたのトークンで読み取りをやり直します。ページには 2 つのクォータが表示されます。

## 複数のツールが同じクォータを共有するとき
アカウントのすべてのツールが同じ 1 時間 5000 回を消費します。良いパターン:数分間の**共有キャッシュ**を持つ小さな `gh` ラッパー、**予約分**(残りが約 1000 回未満なら緊急以外は呼び出しを拒否)、新鮮なデータが必要な作業は**更新の直後**に行うこと、そして `gh run watch` は使わないこと(ポーリングするため)。たとえば、各読み取りの応答をコマンド名の一時ファイルに保存して 120 秒間再利用し、他の呼び出しの前に `gh api rate_limit` を確認するラッパーです。

## してはいけないこと
制限を回避するために、同じユーザーの複数のアカウントや複数のトークンを使わないでください。GitHub の規約に反し、アカウントがブロックされる可能性があります。App、中央パネル、節約モードを使ってください。

## トラブルシューティングと FAQ
- *「クォータは HH:MM まで使い切り」*:待ってください。モニターは自動で再開します。他のツールが消費している可能性があります。
- *数値が古い*:節約モードが有効です(選択または自動)。バーに表示されます。
- *App が動かない*:`/api/github-app/status` と doctor(openssl、鍵のパス、権限)を確認してください。
- *`git fetch` はクォータを消費しますか?* いいえ。[QUOTAS_jpn.md](QUOTAS_jpn.md)(プランと分)と [MODES_jpn.md](MODES_jpn.md) も参照してください。

## 「クォータ」タブと 2 つ目のアカウント
クォータに関することはすべて 1 か所にあります:*設定*の*クォータ*タブ。モード(`modes.auto_low`、`modes.auto_low_enter`、`modes.auto_low_exit`、`modes.low.*` の節約モードの値)、節約(`network.etag`、`cache.etag.enabled` と併用)、中央パネル(`central.source`、`central.max_age_minutes`)、GitHub App(`github_app.*`)、そして**読み取り用の 2 つ目のアカウント**をまとめています。タブのボタンは、各ソース(あなたのログイン、App、2 つ目のアカウント)のクォータと更新時刻を表示し、App と 2 つ目のアカウントをテストし、App に不足している権限を一覧し、推奨値または既定値を適用します。

2 つ目のアカウント(`extra_reader.enabled`、`extra_reader.file`)は読み取り専用で、そのファイングレイン トークンはリポジトリの外のテキストファイルにあり、あなただけが読めます。設定にはそのファイルの**パスだけ**が入ります。モニターは使用時にトークンを読み取り、メモリに保持し、保存・表示・記録は一切しません。読み取りは、各ソースの残り回数(無料の `rate_limit` 呼び出しの値から、その後の読み取りを引いた数)に応じて、あなたのログイン、App、2 つ目のアカウントに分散されます。拒否されたソースは 5 分間除外され、読み取りは次のソースでやり直されます。書き込みとアクションでは使いません。これはあなた自身のアカウント(たとえばリポジトリへの読み取りアクセスを持つ自分の 2 つ目のアカウント)用であり、他人のアカウントで制限を回避するためのものではありません。ファイルは、モニターのアカウントフォルダー(`accounts/`、または `MONITOR_ACCOUNTS_DIR` が指すフォルダー)の中になければならず、リンクをたどって読まれることはありません。`extra_reader.any_folder`(既定はオフ)でこのフォルダー規則を外せます。誰が尋ねるかに依存するもの(あなたのアカウント、その組織、通知、`@me` の検索、`gh auth`、所有者なしの `gh repo list`)は常にあなた自身のログインが処理します。ソース間で振り分けられるのは、単純な `gh api ENDPOINT` の読み取り(オプションは多くても `--jq`、`--paginate`、`-H`、`-i`、`--cache`)だけで、それ以外の呼び出しはあなたのログインに回ります。

## opensslプログラムとポートごとに1つのモニター

モニターは `openssl` をPATHで探し、なければGit for Windowsが置く場所（Program Filesおよびユーザーのプログラム内の `Git\usr\bin`、`Git\mingw64\bin`）とmacOS・Linuxの通常のフォルダーを探すため、`.bat` やサービスから起動したモニターでも見つかります。`github_app.openssl_path`（プログラムへの絶対パス）で手動指定もできます。`/api/github-app/status` は `openssl` と `openssl_path` を示し、PATHのものでない場合はdoctorがどれで署名するかを表示します。

Windowsではモニターのポートを排他的に開きます（SO_EXCLUSIVEADDRUSE）。2つのプロセスが同時に8765で待ち受けることはできません。別のモニターがすでにそのポートで応答しているときに起動したモニターは、別のポートを探さずにそのことを表示して終了します。

## クォータの配分：優先ソースと予約

既定では、各読み取りは空き呼び出しが最も多いソース（ユーザー、GitHub App、2つ目のアカウント）に送られます。`readpool` ブロックは、設定のクォータタブで、従来どおりの控えめな既定値（`auto`、予約0）のままこれを変更します。

- `readpool.prefer.<種類>`（`auto`、`user`、`app`、`extra`）：読み取りの種類ごとに最初に応答するソース。種類は呼び出しから判定されます：`runs`（実行、ワークフロー、チェック）、`security`（コードスキャン、Dependabot、シークレットスキャン）、`issues`（イシューとプルリクエスト）、`history`（リリース、コミット、タグ、コンテンツ）、`discovery`（組織、検索、リポジトリ一覧）、`other`。優先ソースが失敗するか予約を下回る場合は他のソースが応答し、最後がユーザーです。
- `readpool.reserve.<ソース>`（0〜4000）：そのソースで空けておく呼び出し数。ソースの残りが予約以下の間は、他のソースが使えるならそのソースでは読み取りません。`readpool.reserve.user` で、ツールやエージェントのghのためにユーザーの呼び出しを残せます。
- `quota.failover`(既定はオフ):429 または「rate limit exceeded」と答えた読み取りは、読み取り可能な別のソースで 1 回だけやり直され、尽きたソースは次の無料チェックまで使用済みとして扱われます。すべてのソースが使用済みのときは、エラーの代わりにその読み取りの最後の正常なコピーが経過時間つきで表示されます(`quota.failover_max_age_minutes`、既定 60、1〜1440。これより古いコピーは表示されません)。制限が権限の拒否と取り違えられることはなく、書き込みはソースを切り替えず、`GET /api/quota-pool/status` のブロック `failover` に作動回数があります。

書き込みと操作は常にユーザーのトークンを使います。クォータバーと作業モード（高速とターボ）はすべてのソースの合計で数えます。タイルは合計を表示し、ツールチップに各ソースの値を示します。クォータタブ（状態）には、ユーザー、App、2つ目のアカウントのクォータの横に合計の行が加わります。

## 読み取りを減らす:Webhook優先と無料のソース

どちらの方法も**既定ではオフ**で、静かなリポジトリ(直近の実行がすべて完了して緑のもの)にだけ作用します。実行中、赤、またはイベントがあったリポジトリは、いつも通り読み取ります。

- `savings.webhook_first`:受信 Webhook が生きている間(直近 `savings.webhook_window_minutes` 分以内にイベントを受け取った場合)、静かなリポジトリは低速ターンでも読み取られません。何かあれば GitHub が知らせます。それでも `savings.webhook_full_minutes` 分ごとに全体を読み取ります。生きた Webhook がなければ何も変わりません。
- `savings.webhook_live_per_repo`:「稼働中」の判断をリポジトリごとに行います。直近 `savings.webhook_window_minutes` 分以内にそのリポジトリ自身のイベントが届いた静かなリポジトリだけが低速の読み取りを省略し、Webhook が未設定または故障しているリポジトリは、ほかが節約されている間も通常どおり読み取られます。節約できる読み取りは少なくなり、Webhook パネルは単独で稼働しているリポジトリを数えます。既定ではオフで、`savings.webhook_first` と併用します。
- `savings.feeds.enabled`:静かなリポジトリを API で読む前に、デフォルトブランチの最新コミットを、利用枠を消費しないソース(コミットの公開 Atom フィード、`git ls-remote`、またはその両方。`savings.feeds.method`:`atom`、`git`、`auto`)に問い合わせます。前回の全体読み取り時のコミットと同じなら、そのままにします。`savings.feeds.max_age_minutes` 分ごとには必ず全体を読み取ります。公開リポジトリのみ:非公開リポジトリ、エラー、不審な応答の場合は、いつも通り API で読みます。コンピューターの外へ出るのは github.com への GET リクエストだけで、パスワードは決して送られず、何も書き込みません。モニターがネットワークから隔離(air-gapped)されている場合は使いません。

代償:静かなリポジトリで、プッシュなしに始まった実行(スケジュール、再実行)は、すぐにではなく次の全体読み取りで分かります。クォータタブ(状態)には、モニター起動以降に各方法が節約した読み取り回数(それぞれ API 呼び出し約1回分)が表示されます:条件付き読み取り、GraphQL、Webhook優先、Atom フィード、git、中央パネル。

## 大きなアカウント: 実行一覧が覆う範囲と予算

1時間に数百回の実行を起こすリポジトリでは、20〜100件の一覧が数分で埋まり、古い失敗やまれにしか動かないワークフローは一覧に入りません。モニターは緑に見せかけず、そのことを表示します。

- **カバー範囲**: リポジトリ表に各一覧がどこまでさかのぼるかを表示します。満杯でも `sampling.min_coverage_minutes` より短い期間しかさかのぼれない一覧は「カバー範囲が狭い」、要求より短い一覧は「完全」(履歴全体を含む)、合計が 2,500 または 40,000 なら GitHub が数えるのをやめた値なので「少なくとも」と表示します。`GET /api/data` の `sampling` ブロックにも同じ数値があります。
- **二度目の確認**: `sampling.default_branch_probe` をオンにすると、満杯の一覧は読み取りごとにもう1回、プルリクエストを除くデフォルトブランチへのプッシュも問い合わせ、main の赤を決める実行が押し出されないようにします。
- **実行中の run の確認**: `sampling.active_probe` をオンにすると、満杯の一覧は軽量な 2 回のリクエストで `in_progress` の run と `queued` の run も取得し、一覧の範囲より前に始まった長い run が失われたり完了と表示されたりしないようにします。満杯のリポジトリごと・読み取りごとに 2 リクエスト増えます。既定はオフです。
- **A2 をまとめて**: 調べるワークフローが `sentinel.a2_resolve_batch_min` 件以上あるリポジトリには、デフォルトブランチの最新の完了した実行を1回だけ問い合わせ(最大 `sentinel.a2_resolve_batch_pages` ページ、各100件)、まとめて解決します。その一覧に現れないものは1件ずつ調べます。100 以上のワークフローでも、1サイクル4件ではなく数サイクルで済みます。
- **予算**: `sampling.api_budget_per_hour`(0 = なし)は、1時間あたりの実行一覧のリクエスト数を制限します。超えると、赤いワークフローのあるリポジトリを先に読み(予算の10分の1は常に確保)、残りは待機し、待機数をページに表示します。リポジトリ数と間隔から見積もった1時間あたりのリクエスト数は、3,500 以上(GitHub の上限は1時間 5,000)、または予算を設定したときに表示されます。

既定値では、リポジトリが少ないアカウントには何も変わりません。二度目の確認と予算はオフで、カバー範囲が狭いという表示は、満杯の一覧が30分未満しかさかのぼれないときだけ現れます。

## App が有効なのに使われないとき

`github_app.enabled` が有効でも App がトークンを出せない場合、読み取りはあなたのトークンで続き、上限はユーザーの小さい方になります。黙って起きることはありません。doctor が原因付きで黄色になり、失敗は飲み込まれた失敗の一覧に一度だけ記録され、クォータタブに原因と使用中の上限を示す `GitHub App` の行が出ます。原因: 鍵が読めない、またはパスフレーズなしの RSA 鍵ではない(`key_unreadable`)、鍵で署名できなかった(`sign_failed`)、App がアカウントにインストールされていない(`app_not_installed`)、GitHub がトークンを拒否した(`token_refused`)、App が有効なのに番号または鍵ファイルがない(`not_configured`)。同じ内容は `GET /api/quota` の `app`、`GET /api/github-app/status` の `signer` と `code` にあります。
