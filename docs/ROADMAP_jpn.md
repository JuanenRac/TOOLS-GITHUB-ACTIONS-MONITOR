## 予定(この順序で)

各バージョンは計画の自分の区間のすべてを含みます。前のバージョンに積み残すことも、次のバージョンへ先送りすることもありません。1.8.3 の後と 1.9.3 の後に、製品は独立したレビューを受け、その指摘は直後の安定化バージョンで解消します。1.8.1 は 1.8.0 の修正版です。「リポジトリを読み込み中」のボックスは最後のリポジトリとともに消え、ページの再読み込みですぐにデータが届きます。

### 1.8.2 - 公式 Docker イメージとサービスモード

非特権ユーザーのマルチステージイメージ、データと設定のボリューム、文書化された環境変数、任意のリバースプロキシと TLS を含む compose の例、従来のインストールを好む人向けの systemd ユニット、スーパーバイザーやアカウントのサイクルが固まると失敗する詳細なヘルスチェック。GitHub が失効させた、または期限切れにした認証情報は、そのアカウントだけを「見えない」状態にし、重大なシステムアラートを出し、スーパーバイザーを再起動せずに差し替えられます。バックアップ、アップグレード、サービスとしての初回起動を文書化し、ページはこのコンピューター・ネットワーク・プロキシの背後のどれで待ち受けているかを示し、コマンドラインはリモートのモニターに対して動作します。lite 版はローカルのままです。

### 1.8.3 - ユーザーごとの通知

ユーザーごとの設定(チャンネル、センチネル、最低レベル)、設定とロールから通知先を決めるディスパッチャー、シンプルなプラグインとしてのチャンネル、未読アラートのダイジェスト。さらに: ランナーごとのジョブのキュー待ち時間のレポートと、監視するパスのためにスキップされたジョブを赤いジョブとは別に表示すること。

### 1.8.4 - 安定化

大きな機能はありません。アカウント間の分離、ページ、ストレージ、ログインとロール、通知、ときどき不調になる GitHub、中断された移行後の起動、強制終了後の復旧、拡張された doctor、GitHub に書き込む箇所、トークンを含まないログ、チームモードのセキュリティチェックリスト、挙動と一致するドキュメント。必要な場合のみ 1.8.9 まで続きます。

### 1.9.0 - 単一のスコア

アカウント別・センチネル別のメトリクス収集(成功率、所要時間、復旧時間、スループット)、変更可能なしきい値を持つスコアエンジン、前期間との比較、ストレージに保存するスナップショット、スパークライン付きスコアウィジェット、スコア低下時のアラート、スコアを表示するコマンドライン動詞。

### 1.9.1 - セキュリティセンチネル

3 つ目のセンチネル: Dependabot、コードスキャン、シークレットスキャン、ブランチ保護、ワークフローの権限、コードオーナー。信号の種類ごとのルール、アラートタブでの同じフィルター、未解決の重大アラートによるスコアの減点があります。任意で同じリリースに: ワークフローの衛生チェック(コミットに固定されていないアクション、時間制限のないジョブ、権限や並行制御のないワークフロー、pull_request_target の危険な使い方)。プロジェクトが既に持つワークフローチェッカーを土台にします。

### 1.9.2 - リポジトリとチームの健全性

各リポジトリの健全性ビュー(CI、イシューとプルリクエスト、セキュリティ、リリース準備、アクティビティ)と、順位・合計・フィルター付きのチームビュー。壁掛けスクリーン向けのディープリンク付きページ。任意で同じリリースに: 予算に対する夜間ベンチマークのパネル(マシン区分ごとの基準に対する中央値)と、各リリースのソフトウェア部品表および証明のパネル。

### 1.9.3 - 定期レポートと監査ログ

スコア、主要アラート、変更を載せる HTML と Markdown のレポートテンプレート(PDF は任意)、スケジューラー、誰がいつ何をしたかの追記専用の監査ログ(秘密情報は含みません)。任意で同じリリースに: 各リポジトリの最後のグリーンコミットを示す「リリース準備完了 / ブロック中」ビュー。

### 1.9.4 - 第 3 段階の安定化

スコア、セキュリティセンチネル、健全性ビュー、レポート、監査ログに対する、1.8.4 と同種の仕上げ。3 つのセンチネルが動作する際の API 呼び出しコスト。センチネルがオフでも一貫性を保つスコア。

### 2.0.0 - 成熟

技術的負債を整理し、公開インターフェース(センチネル、ストレージ、アラート、イベントスキーマ、読み取り API)を凍結するメジャーバージョン。クライアントがどのリリースに対しても実行できる契約テストスイート付き。利用形態ごとのガイド(lite、個人、サービス、チーム)と、設定・イベント・メトリクス・API のリファレンス。2.0.1 以降は、長期の実運用でしか現れない問題のための余裕です。

モニター自身のワークフローも、衛生センチネルが他に求めることを守ります。コミットに固定されたアクション、最小限の権限、すべてのジョブの時間制限です。

## 次に

1.6.4 で届かなかったことと理由:

- **1 つのプロセスと 1 つのページで複数のオーナー**: 1.7.0 から各アカウントは独立したモニターで、ページはそれらを並べて表示しますが、1 つのモニターの中ではリポジトリは名前だけで識別されるため、同じモニターに 2 人のオーナーを入れると混ざります。1 つのプロセスにまとめるには、すべての識別子(読み取り、アラート ID、設定のリスト、センチネル、ページ)にオーナーを含める必要があります。実在する 2 人のオーナーのリポジトリなしには検証できなかったため、1.7.0 のアカウントが引き続き分離の方法です。
- **請求レポートを読めるログインでの確認**: `user` スコープのないログインの実際の応答は「見つからない」で、モニターは推定に戻ります(確認済み)。数値そのものは請求アカウントと照合していません。
- **大型ランナーの料金**(`quotas.json`)は公開料金表の記憶に基づく未検証の値です。GitHub の請求ページと比較してファイルを編集してください。
- **`gh copilot`**: フラグは `gh copilot -- --help` で確認しますが、Copilot コマンドラインが必要です。ここには未インストールのため未検証のままです。
- **通知、Webhook、Enterprise Server、サービスの例**の実サービスでの確認: `tools/manual_check_live.py` で手動確認できます。皆様のチャネルとホストが必要なため、ここでは実行していません。
- **ターミナルアプリ**は、簡単な設定、リスト、数値のマップの編集に対応し、AI の状態を表示します。個別の赤いワークフローの説明はページに残ります。
- **実際のインストールで確認できるのはオーナーだけです**: 実在のリポジトリでの Collab センチネルを使った複数アカウント、実際のキーを使った GitHub App と読み取り専用の 2 つ目のアカウント、実際の証明書を使った HTTPS プロキシ。手動(`tools/manual_check_live.py`)で確認するもので、完了とはしていません。
- **ダウンロードやインストールまで行う新バージョン確認**: 行いません。モニターは通知するだけです。
