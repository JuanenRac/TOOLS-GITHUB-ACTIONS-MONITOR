# 路线图

已发布的、接下来的和仍只是想法的内容,按确定程度排列。它们是方向而非承诺;推动其中一项最好的办法是提交 issue 或拉取请求。

## 监视器现在的位置

版本 2.0.6。lite 版显示正在运行的和失败的内容。完整版增加三个哨兵(CI、Collab 和 Security)、一份警报列表、多个账户和带角色的团队、每个账户的评分、每个仓库和团队的健康状况、定时报告、操作日志、通知(ntfy、Teams、电子邮件和 Apprise)、带兼容服务预设的可选 AI 助手、Docker 服务模式,以及适配从手机到 4K 各种屏幕尺寸的页面。

## 计划,按此顺序

每个版本只包含真实内容:没有真实内容可加的版本会被跳过,绝不会空着发布。除非指南另有说明,这里的内容均不视为已在真实服务上得到验证。

### 2.0.2 至 2.0.9 - 冻结之后

只有长期真实使用才会出现的问题：从 1.8 和 1.9 迁移、事件和数据库数月的增长、升级后的会话、Docker 卷、多账户同时运行三个哨兵和团队模式，以及契约套件发现的问题。第四阶段（插件、广泛自动化、高级 AI）的内容不会进入这些版本；没有真实内容的版本会被跳过。

监视器自身的工作流遵守卫生哨兵将向他人提出的要求:固定到提交的 action、最小权限,以及每个作业的时间限制。

## 1.8.2 至 2.0.6 已完成

### 2.0.6 - 三个已绘制的墙屏,默认关闭

三个墙屏已绘制完成:概览(评分、车队指示灯、图表、热力图、运行器和配额)、此刻(进行中的运行、队列、待批准、近期失败和实时线)以及哨兵(每个哨兵一张带动画雷达的卡片)。页面自行绘制所有图表,新的失败只闪烁一次然后平静,要求减少动态的用户看不到任何运动,为防烧屏每分钟略微移动,夜间可调暗,一个窗口可在三个页面间轮换,浏览器测试会在 1080p、4K 和竖屏下以八种语言检查它们。墙屏默认关闭(`screens.enabled`),README 和墙屏指南现已展示它们。

### 2.0.5 - 更少的误报红色、休眠仓库和全屏下可见的确认提问

红色现在按事件来源计数:GitHub 为自己创建的工作流(`dynamic/`)既不是红色 CI 也不是文件,隐藏工作流的查询遵循同一来源规则,排队数天的运行被识别为幽灵队列(默认 7 天),无人处理的红色在 30 天后老化并变为不活跃;休眠和不活跃的仓库是独立状态,既非绿色也非红色;复刻仓库只有在最近 90 天内有自己的 CI 时才进入卫生检查、工作流检查和评分;默认分支的保护默认按所有公开来源中实际生效的内容判断;页面的五个确认操作改用页面内的对话框,全屏下也可见。

### 2.0.4 - 按任务选择的模型、独立的菜单和打开正确主题的帮助

监控器的 AI 可以为每类任务使用一个模型、在主模型失败时使用后备链,并为每个模型设置预算,在设置中写明之前全部关闭;警报、报告和经验教训成为三个独立的菜单条目,各有自己的面板、徽标、帮助主题和地址;历史标签页只保留一个计数,而不是每次刷新都累积副本;“本标签页帮助”按钮在每个标签页都会打开当前标签页的主题;工具文件夹不存在时,浏览器测试会干净地跳过。

### 2.0.3 - 大型账户、更少的误报红色、无需克隆的检查和更安全的存储

面向拥有数百个仓库的账户的车队视图、分页列表、请求预算和对运行列表的诚实覆盖;红色只有在仓库自身造成时才计入,等待批准的运行、被弃用的工作流、只响应 issue 的工作流、合并队列和维护分支各得其所;工作流检查器和表面检查通过 API 或稀疏克隆工作,无需克隆;AI 提供商的模型会被读取和核对,页面的每个链接都经过地址过滤器;锁和操作日志在 Windows 上更安全,评分账本不会被覆盖;用于显示器或电视的墙屏(默认关闭);仓库的测试暂时不再在 macOS 上运行。

### 2.0.2 - 更安全的日志、更干净的 AI 文本和更公平的评分

AI 可读取的一切都经过一个认识更多形式机密的清理器,内置助手保留其密钥且不再跟随重定向和代理,操作日志是每个账户一个文件中的一条链且查看者无法读取,镜像和账户的进程不再带有机密,评分会惩罚从未修复的故障且不再把不可读的来源算作干净,另有关于存储、备份、迁移、终端视图和启动器的一长串修复。

### 2.0.1 - 打包与缺失的键

发布的 zip 现在包含 AI 预设文件和软件包的所有其他数据文件,如果 zip 中缺少其中任何一个,发布关卡就会失败;所有账户页面不再显示未翻译的状态键,并且有一项测试检查页面使用的每个键都存在于八个语言目录中。

### 2.0.0 - 成熟

读取 API 与公共接口已冻结：一份记录每个读取端点的键、类型和错误码的契约文件，一个可对任何正在运行的监视器检查它的测试套件和工具，一个固定警报字段以及哨兵和存储方法的测试，以及针对每种用法（简易版、个人、服务、团队）和 API 客户端的八种语言指南。1.9.6 至 1.9.9 在收尾审查之后没有真实内容可加，已被跳过。

### 1.9.5 - 实时事件流

为无法轮询的客户端和墙面屏幕提供入站 Webhook 的实时事件流，默认关闭，只读，并限制监听者数量和每个监听者的时长。

### 1.9.4 - AI 预设

一张包含十二个托管服务和六个本地服务器的表,它们使用监视器已支持的协议;AI 设置中的选择器会填入地址、密钥变量的名称和一个示例模型;本地服务器无需密钥即可工作;主要服务的地址已在其公开文档中核对。

### 1.9.3 - 定期报告与审计日志

包含评分、主要警报和变更的 HTML 与 Markdown 报告模板(PDF 可选),调度器,以及只追加的审计日志,记录谁在何时做了什么,其中不含任何机密。可选,同一版本:带有每个仓库最近一次绿色提交的"发布就绪 / 受阻"视图。

### 1.9.2 - 仓库与团队健康

每个仓库的健康视图(CI、议题和拉取请求、安全、发布就绪度、活跃度)以及带排名、合计和过滤器的团队视图;两者都有页面,并提供适合墙面屏幕的深层链接。可选,同一版本:对照预算的夜间基准面板(相对于每类机器基线的中位数),以及每个发布的软件物料清单和证明面板。

### 1.9.1 - 安全哨兵

第三个哨兵:Dependabot、代码扫描、密钥扫描、分支保护、工作流权限和代码所有者,按信号类型设置规则,在警报标签页中使用同样的过滤器,并对未解决的严重警报在评分中扣分。可选,同一版本:工作流卫生(未固定到提交的 action、没有时间限制的作业、没有权限或并发设置的工作流、对 pull_request_target 的危险用法),基于项目已有的工作流检查器。

### 1.9.0 - 统一评分

按账户和哨兵的指标采集器(成功率、时长、恢复时间、吞吐量),阈值可调的评分引擎,与上一周期相比的趋势,保存在存储中的快照,带迷你折线图的评分组件,评分下降时的警报,以及打印评分的命令行动词。

### 1.8.4 - 稳定化

没有大的新功能。账户之间的隔离、页面、存储、登录与角色、通知、时好时坏的 GitHub、迁移中断后的启动、被强制终止后的恢复、更全面的 doctor、写入 GitHub 的位置、不含令牌的日志、团队模式的安全清单,以及与行为一致的文档。该系列仅在需要时延续到 1.8.9。

### 1.8.3 - 按用户的通知

按用户的偏好(渠道、哨兵、最低级别),根据偏好和角色决定通知谁的分发器,作为简单插件的渠道,以及未读警报的摘要。另外:按运行器统计作业在队列中的等待时间报告,以及因监视路径而被跳过的作业与红色作业分开显示。

## 下一步

1.6.4 没有做到的,以及原因:

- **一个进程、一个页面里的多个所有者**:自 1.7.0 起每个账户都是独立的监视器,页面把它们并排显示,但在同一个监视器里仓库仍然只用名称标识,所以两个所有者放在同一个监视器里会混在一起。要把它们放进一个进程,需要在每个标识符里带上所有者(读取、告警标识、设置中的列表、哨兵和页面);没有两个真实所有者的仓库就无法证明,所以 1.7.0 的账户仍然是把它们分开的办法。
- **用能读取账单报告的登录验证**:没有 `user` 权限范围的登录得到的真实答复是“未找到”,监视器退回估算(已验证);数字本身尚未与账单账户对照。
- **`quotas.json` 中大型运行器的价格**来自对公开价目表的记忆,标记为未验证;请与 GitHub 账单页面比对并编辑该文件。
