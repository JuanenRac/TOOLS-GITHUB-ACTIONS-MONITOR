# 路线图

当前版本放不下的想法,不承诺顺序。它们是方向而非承诺;推动其中之一的最佳方式是提交 issue 或 pull request。

## 1.8.0(下一个版本)

下面列出的内容均已编写并测试;它们要么已在主分支,要么正在拉取请求中等待。没有任何内容声称已在真实服务上证明(见"后续")。

### 已在主分支

- 新的文件夹布局(程序包在 `src/`,页面、示例和语言文件在 `assets/`),并附带迁移工具,可在不删除任何内容的前提下迁移旧的扁平安装。
- 位于单一接口之后的存储层,文件后端保持 `accounts/<id>/` 的结构,写入是原子的,备份可由任何后端恢复。
- 可选的 SQLite 后端(默认关闭):每个账户一个数据库、带版本的迁移、可设置的等待时间,以及在文件后端与 SQLite 之间双向迁移状态的工具(先试运行)。
- 变更历史已翻译成八种语言,一直到 1.0.0,并有测试保证其完整。
- 历史数据的保留与轮转(事件和分析数据保留若干天,删除或归档,每次处理一行审计记录,doctor 的体积提醒;哨兵状态和配置从不触碰)。

### 已完成,等待合并

- 网络模式:在检查令牌之前锁定制动再次生效,声明的反向代理永远不会被当作本机,对设置的远程读取仅限远程客户端可更改的内容,部署指南给出完整方案。
- 给 AI 的数据流按字段清理,只放行封闭形式的 GitHub 地址,钩子不再交付日志文本,只交付仓库、工作流、结果和链接。
- 身份读取始终使用用户本人的凭据,读取按白名单判断,第二个账户的令牌文件被限制在账户文件夹内。
- 在真实浏览器中对页面做冒烟测试,标签页损坏或函数被重复定义时 CI 会变红。
- 只说明顶部方框未说明内容的单行底部栏,与运行中监视器一致的 AI 工具简报和日志,在与监视器不同步时给出提示的页面,以及一次点击即可解锁、刷新后仍然有效的声音。
- 通过 GraphQL 对安静仓库的可选读取(默认关闭)及其计量。
- 对外部 AI 的主动通知(默认关闭,每个提供方首次确认,仅限封闭列表中已脱敏的字段,每小时调用次数和费用的上限,密钥通过变量名引用,AI 从不执行任何操作)。
- 终端应用可编辑列表和映射。
- 团队模式(默认关闭):用户、角色(admin、maintainer、viewer)和会话保存在存储中,登录页面,供非浏览器客户端使用的 Bearer 令牌,稳定的 JSON 错误,以及从本机控制台恢复管理员。个人模式无需登录继续工作,lite 版永远没有登录。
- 更有生气的页面:动画图标,运动随状态变化的状态指示灯,对悬停、聚焦和点击的响应;减少动态效果时全部关闭,lite 版保持轻量。

## 计划,按此顺序

每个版本包含计划中属于它那一段的全部内容:不把任何事留给更早的版本,也不推迟到下一个版本。1.8.3 之后和 1.9.3 之后,产品会接受独立审查,其发现在随后的稳定版本中关闭。1.8.1 是 1.8.0 的修正版:“正在加载仓库”框随最后一个仓库消失,刷新页面会立即拿到数据。

### 1.8.2 - 官方 Docker 镜像与服务模式

多阶段镜像、非特权用户、数据与配置卷、有文档的环境变量、带可选反向代理和 TLS 的 compose 示例、供偏好传统安装的人使用的 systemd 单元,以及当监督进程或某账户的周期卡住时会失败的深度健康检查。GitHub 撤销或过期的凭据只会把该账户标记为"失明",触发严重的系统警报,并可在不重启监督进程的情况下替换。备份、升级和作为服务的首次启动都有文档;页面会说明它是在本机、网络上还是在代理之后监听;命令行可针对远程监视器工作。lite 版仍为本地。另外:按运行器统计作业在队列中的等待时间报告。

### 1.8.3 - 按用户的通知

按用户的偏好(渠道、哨兵、最低级别),根据偏好和角色决定通知谁的分发器,作为简单插件的渠道,以及未读警报的摘要。另外:因监视路径而被跳过的作业与红色作业分开显示。

### 1.8.4 - 稳定化

没有大的新功能。账户之间的隔离、页面、存储、登录与角色、通知、时好时坏的 GitHub、迁移中断后的启动、被强制终止后的恢复、更全面的 doctor、写入 GitHub 的位置、不含令牌的日志、团队模式的安全清单,以及与行为一致的文档。该系列仅在需要时延续到 1.8.9。

### 1.9.0 - 统一评分

按账户和哨兵的指标采集器(成功率、时长、恢复时间、吞吐量),阈值可调的评分引擎,与上一周期相比的趋势,保存在存储中的快照,带迷你折线图的评分组件,评分下降时的警报,以及打印评分的命令行动词。

### 1.9.1 - 安全哨兵

第三个哨兵:Dependabot、代码扫描、密钥扫描、分支保护、工作流权限和代码所有者,按信号类型设置规则,在警报标签页中使用同样的过滤器,并对未解决的严重警报在评分中扣分。可选,同一版本:工作流卫生(未固定到提交的 action、没有时间限制的作业、没有权限或并发设置的工作流、对 pull_request_target 的危险用法),基于项目已有的工作流检查器。

### 1.9.2 - 仓库与团队健康

每个仓库的健康视图(CI、议题和拉取请求、安全、发布就绪度、活跃度)以及带排名、合计和过滤器的团队视图;两者都有页面,并提供适合墙面屏幕的深层链接。可选,同一版本:对照预算的夜间基准面板(相对于每类机器基线的中位数),以及每个发布的软件物料清单和证明面板。

### 1.9.3 - 定期报告与审计日志

包含评分、主要警报和变更的 HTML 与 Markdown 报告模板(PDF 可选),调度器,以及只追加的审计日志,记录谁在何时做了什么,其中不含任何机密。可选,同一版本:带有每个仓库最近一次绿色提交的"发布就绪 / 受阻"视图。

### 1.9.4 - 第三阶段稳定化

对评分、安全哨兵、健康视图、报告和审计日志做与 1.8.4 同类的收尾;三个哨兵同时运行时的 API 调用成本;某个哨兵关闭时仍保持一致的评分。

### 2.0.0 - 成熟

一个主版本,清理技术债务并冻结公共接口:哨兵、存储、警报、事件模式和读取 API,并附带客户端可针对任何发布运行的契约测试套件。为每种使用方式(lite、个人、服务、团队)提供指南,以及设置、事件、指标和 API 的参考。2.0.1 起为只有长期真实使用才会出现的问题留出缓冲。

监视器自身的工作流遵守卫生哨兵将向他人提出的要求:固定到提交的 action、最小权限,以及每个作业的时间限制。

## 下一步

1.6.4 没有做到的,以及原因:

- **一个进程、一个页面里的多个所有者**:自 1.7.0 起每个账户都是独立的监视器,页面把它们并排显示,但在同一个监视器里仓库仍然只用名称标识,所以两个所有者放在同一个监视器里会混在一起。要把它们放进一个进程,需要在每个标识符里带上所有者(读取、告警标识、设置中的列表、哨兵和页面);没有两个真实所有者的仓库就无法证明,所以 1.7.0 的账户仍然是把它们分开的办法。
- **用能读取账单报告的登录验证**:没有 `user` 权限范围的登录得到的真实答复是“未找到”,监视器退回估算(已验证);数字本身尚未与账单账户对照。
- **`quotas.json` 中大型运行器的价格**来自对公开价目表的记忆,标记为未验证;请与 GitHub 账单页面比对并编辑该文件。
- **`gh copilot`**:其参数用 `gh copilot -- --help` 检查,这需要 Copilot 命令行;此处未安装,因此仍未验证。
- **通知、webhook、Enterprise Server 和服务示例**对真实服务的验证:`tools/manual_check_live.py` 可手动检查;它们需要你的渠道和主机,所以没有在此运行。
- **终端应用**可以编辑简单设置、列表和数字映射,并显示 AI 状态;对单个红色工作流的解释仍留在页面中。
- **只有所有者能在真实安装上证明它们**:在真实仓库上用 Collab 哨兵的多个账户、使用真实密钥的 GitHub App 和只读的第二个账户,以及使用真实证书的 HTTPS 代理。它们靠手动运行(`tools/manual_check_live.py`),不当作已完成。
- **会下载或安装的新版本检查**:永不;监视器只会提示。
